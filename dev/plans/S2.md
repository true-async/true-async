# S2 notes: test system and build against the core

The extension builds out of tree with `phpize` against an installed core on
Linux and as a copy under `ext/true_async` on Windows; tests run with the installed core's
`run-tests.php` over frozen lists; the verdict of every run is computed from per-test statuses
by `tools/results.py`, never from run-tests' exit code.

## 1. Build against the core

### Linux: `phpize` against an installed prefix

Each core is installed into its own prefix, and the extension is built from `~/true-async`
with that prefix's `phpize` and `php-config`. A build is identified by a lane:
`<core>-<tree>[-cov|-mull]`.

| Axis | Values |
|---|---|
| core | `pocs` (`async-core-io`), `rfc` (`async-core-io-rfc/<date>`, section 5) |
| tree | `dbg` (ZTS debug), `asan` (ZTS debug, ASAN + UBSAN) |
| variant | none; `cov` (gcov, on `dbg`); `mull` (clang 18 with the Mull plugin, on `dbg`) |

Prefixes: `~/ta-prefix/<core>-<tree>`. The configure line in `WORKFLOW.md` gains `--prefix`;
the ASAN tree also gains `--enable-undefined-sanitizer`, which the plan requires (S2.3) and the
S1 trees lack. Both trees are rebuilt and the S1 suites rerun and diffed with
`results.py --diff`, as for a core update.

Build directories: `_build/<lane>/` (gitignored). The name `build/` is taken: `phpize` writes
its own files there and `phpize --clean` deletes the directory (`scripts/phpize.in:15`).
Whether phpize's `configure` builds from a separate directory (VPATH) is checked in S2.2; if it
does not, each lane gets its own copy of the sources under `_build/`.

The runner always runs `make` (dependency files track the core headers) and reruns `phpize`
and `configure` when the lane's `php-config` path, the installed core revision or `config.m4`
changes. A module built against one core is never loaded into another.

**Compiler flags are set by the runner, in full.** ABI defines (`ZTS`, `ZEND_DEBUG`,
`ZEND_SIGNALS`) reach the module through the installed `php_config.h`, but `-fsanitize*` lives
only in the core's CFLAGS, and `scripts/phpize.m4` adds only `-O0` when CFLAGS is given. Lane
flags:

| Lane | CFLAGS (LDFLAGS take the `-fsanitize`/`--coverage` part) |
|---|---|
| `*-dbg` | `-g -O0` |
| `*-asan` | `-g -O0 -fsanitize=address,undefined -fno-sanitize-recover=undefined -fno-sanitize=object-size -fno-omit-frame-pointer` (the core's own set, `configure.ac:1571-1619`) |
| `*-dbg-cov` | `-g -O0 --coverage -fprofile-update=atomic` (ZTS) |
| `*-dbg-mull` | `CC=clang-18`, `-g -O0 -fpass-plugin=<mull-ir-frontend-18>` |

Gate: the runner refuses an `asan` lane when a compilation unit of the module lacks
`-fsanitize=address,undefined` in its `DW_AT_producer` (`readelf --debug-dump=info`): an
uninstrumented module in the ASAN binary runs green and checks nothing. Symbols are no gate: the
S2.2 skeleton, built with UBSAN, references no `__ubsan_` handler because it has nothing to check.

Why `phpize` over a copy into `ext/true_async` on Linux:

- Mutants and coverage instrument the extension alone, while the core stays a gcc build. A copy
  builds with the core's compiler and flags, so Mull would need a clang-built core tree.
- The core trees stay merge-only checkouts; a copy adds an untracked `ext/true_async`, a
  `buildconf` and a reconfigure after every `config.m4` change, and a sync step that can drift.
- `~/true-async-server` builds this way in CI (`build-linux.yml`: core installed, extension by
  `phpize`, tests by the core's `run-tests.php`), and PIE builds this way for users.

Cost of `phpize`: seven reference tests reach php-src files through
`__DIR__ . '/../../../../…'` (`ext/curl/tests/server.inc`, `ext/ftp/tests/server.inc`,
`sapi/cli/tests/php_cli_server.inc`): `io/082`, `stream/003`, `curl/063`, `064`, `070`, `071`,
`072`, 7 of 1318 `.phpt` in `ext/async` `1fdacf8`. Outside the core tree that path resolves to
`~/..`. They belong to S6 groups; S6 ports them with the path taken from an environment variable
the runner sets to the core source tree, one `DECISIONS.md` entry for the seven (P2.2).

### Windows: copy into `ext/true_async`

As `ext/async` and `~/true-async-server` do: the repository is copied into
`php-src\ext\true_async` and the whole PHP is built with `--enable-true-async`. Staging
checkouts are removed from the php-src root before `buildconf`: `find_config_w32(".")` registers
every `config.w32` it finds, and a duplicate module resets the switch to `no`
(true-async/php-async#270). `php/php-windows-builder` is not used: it builds only against
released versions or php-src `master`, not a custom core branch. The scripts are written for
the S2.4 CI job and debugged there.

### PIE

Not in S2. PIE runs `phpize`, `configure`, `make`, `make install`, so the Linux layout already
fits it; it needs a `composer.json` of type `php-ext` and, for Windows, prebuilt DLLs (PIE does
not build on Windows). Packaging comes with the first release.

## 2. Runner

`tools/test.py` (S2.3), one entry point for every layer:

```
tools/test.py --lane pocs-asan [--stage 3] [--jobs N] [TEST...]     (--seeds N comes with S3)
```

1. Builds the lane (section 1).
2. Composes the test file list (section 3). An empty list is an error: run-tests given no tests
   scans the whole working tree (`run-tests.php:762-773`).
3. Runs `<prefix>/bin/php <run-tests> -q -p <prefix>/bin/php` with
   `-d extension=<abs path>/true_async.so`, the extension's enable switch, `--show-diff`, and
   `-r <list file>`. Paths are absolute; `-q` only turns off the interactive prompt.
4. `<run-tests>` is `<prefix>/lib/php/build/run-tests.php` (installed by `make install`, so CI
   needs only the cached prefix), copied with `tools/run-tests.patch` applied: the patch prints
   the first attempt of a retried test and its signal. run-tests retries a failing test whose
   code calls `sleep`, `usleep`, `microtime`, `hrtime` (`is_flaky`, `run-tests.php:3094`), 67
   reference files, reports a pass on retry as WARN and discards the first output; there is no
   switch to turn this off. `~/true-async-server` patches it for the same reason (its #313).
5. On `asan` lanes passes `--asan -x`, as the reference CI does: `--asan` sets `USE_ZEND_ALLOC=0`,
   `USE_TRACKED_ALLOC=1` (bailout paths free the request's memory, so tests that end in a fatal
   error do not leak), `SKIP_ASAN`, `SKIP_PERF_SENSITIVE`, only in the tested processes. The
   runner adds `ASAN_OPTIONS=abort_on_error=1`, `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`
   and `LSAN_OPTIONS` with the core's `.github/lsan-suppressions.txt` (run-tests looks for it next
   to itself, which the installed copy is not): the core checkout comes from
   `$TRUE_ASYNC_CORE_SRC`. Prefixes come from `$TRUE_ASYNC_PREFIXES` (default `~/ta-prefix`).
6. Passes the environment without secrets (names matching `TOKEN`, `SECRET`, `_KEY`, `GITHUB_`
   and the like): run-tests writes the whole environment into a `.sh` next to every failed test,
   and a GitHub token was found in 45 of them in the core trees on 2026-10-01.
7. Moves what run-tests leaves next to a failed test (`.php`, `.diff`, `.out`, `.sh`, …) into the
   run's directory, so `tests/` holds only listed files.
8. Saves the raw output under `results/<lane>/<timestamp>/` (gitignored) and computes the
   verdict with `results.py` against the expected statuses (section 3): WARN counts as FAIL; a
   SKIP that the list does not allow counts as FAIL.

## 3. Test lists

Tests live in `tests/<group>/`; a ported test keeps the reference's file name, helper files
(`.inc`, servers) sit next to it as in the reference. `.gitattributes` sets `*.phpt -text` and
the same for helpers, so a Windows checkout does not change their bytes.

**`tests/lists/S<n>.txt`** holds the tests a stage adds, one line each, in one of two forms:

```
coroutine/001-basic.phpt  ref:<sha256>
core/001-registration.phpt  own:<sha256>
```

`ref:` is a test ported from `ext/async` at the revision pinned in `tests/lists/REFERENCE`; `own:` is a test written here (the S2 registration test, S4's cross-thread
wakeup, S7's collector cases, the Mull known-answer test). Optional tags after the hash:

- `changed:<DECISIONS.md date>` with the new hash: a test changed on purpose, ported or own (own
  tests since 2026-10-02: a frozen line cannot change otherwise);
- `core:<RFC-CHANGES.md entry>`: needs an RFC change; left out of `pocs` lanes;
- `skip-on:<lane pattern>(<reason>)`: SKIP allowed on those lanes (a database fixture, `--asan`
  skipping a `USE_ZEND_ALLOC`-dependent test);
- `xfail-on:<lane pattern>(<plan step>)`: FAIL expected on those lanes only, until the step makes
  it pass there (a test that passes on Linux and waits for a Windows change); a pass there fails the
  lane until the tag is removed (2026-10-06).

Every listed test is expected to PASS on every lane it is not left out of, unless a `skip-on`
tag allows SKIP there. A test whose stage is not finished carries a `--XFAIL--` section naming the
plan step that makes it pass (2026-10-02); it is expected to give XFAIL, and the hash is taken
without the section.

**`tests/lists/S<n>.excluded`** names every reference test of the stage's groups that is not
ported, with one reason from a closed set: `component:<stage>`, `needs-core:<RFC-CHANGES entry or
upstream issue>` (no RFC change carries it yet), `fixture:<name>`, `platform:<os>`,
`rfc-rule:<DECISIONS entry>`.

Lists are cumulative: a run for stage S<n> takes S2 through S<n>. A list is frozen by the commit
that adds it, before the stage's first code commit (P3.1); after that it only gains `changed:`
tags and new lines of later work, never edits of existing hashes.

**`tools/check-lists.py`**, run by CI on every push:

- `ref:` hashes are recomputed from a checkout of `true-async/php-async` at the pinned revision,
  never taken from the list; a ported file must match that hash, or its `changed:` hash;
- a `changed:` tag must name a `DECISIONS.md` line that contains the test's path;
- every reference test of a stage's groups is in the list or in `.excluded`;
- `git diff <freeze commit> -- tests/lists/S<n>.txt` contains only added lines and added tags;
  the freeze commit is the first commit that touched the file;
- every listed file exists, every file tracked under `tests/` is listed; a helper (`.inc`, a
  server) is a list line of its own, `ref:` or `own:` like a test.

What it cannot see: whether the list was committed before the stage's first code commit. That
stays held by discipline, as P3.1 says.

**`tests/deps/S<n>.md`**: the core-dependency table (plan S3.1): test, what in the core it needs,
outcome (extension fix, RFC change, upstream fix, drop). A `core:` test must PASS on the `rfc`
lanes; while its RFC change is not yet in the `rfc` core it is an open blocker of the stage, not
a SKIP.

## 5. CI

Repository `true-async/true-async`, GitHub Actions, Linux and Windows.

- **Cores.** `pocs` is `async-core-io`. `rfc` is `async-core-io-rfc/<date>`: a merge-only branch
  of `async-core-io` and the heads of our RFC change PRs, conflicts resolved locally once, pinned
  in `WORKFLOW.md`; until the first RFC change exists it is not created and `rfc` lanes do not
  run. Both are published in true-async/php-src (answer 1).
- **Core job.** Builds and installs each core into its prefix; cache key: core revision,
  configure line, ior revision. The cache holds the prefix plus the three source files the seven
  `../../../../` tests need (section 1), taken by a sparse checkout of the same revision.
- **Windows job.** Builds the core and the extension copied into `ext/true_async` on
  `windows-latest` (section 1) and runs the lists; part of S2.4.
- **Push workflow.** `check-lists.py`; `pocs-dbg`, `pocs-asan`, and the `rfc` lanes when `rfc`
  exists.
- **Nightly workflow.** Scheduler fuzz over N seeds per list; chaos layers when they exist.

## 6. Mutants and coverage

**Mull** 0.34.1 for clang 18 (the `Mull-18` package of its release). `tools/mull.py` builds the
`pocs-dbg-mull` lane (the module by `clang-18 -fpass-plugin=/usr/lib/mull-ir-frontend-18
-grecord-command-line`, the core stays gcc) and runs `mull-runner-18 <module> --test-program
<php> -- <run-tests> …`: Mull finds the mutants in the module given as its input, and each run of
php switches one on through an environment variable named after it. Facts behind the setup,
checked 2026-10-01:

- The variable's name holds the source path (`cxx_add_to_sub:/…/known_answer.c:31:16:31:17`).
  PHP's `$_ENV` and `getenv()` array rename or drop such names, and dash, `/bin/sh` here, drops
  them; `tools/run-tests.patch` makes run-tests read `/proc/self/environ` and run each test
  through `/bin/bash`. Without it every mutant survives.
- One worker: parallel mutant runs share the files run-tests writes next to a test and kill
  mutants at random.
- Code inlined from the core's headers is mutated as part of our files; `excludePaths` drops it.
- `gitDiffRef` makes no mutant in a file the diff adds whole, so `--diff-ref` builds every `src/`
  mutant and keeps the changed lines (`git diff -U0`) in the report.
- An equivalent mutant (`<` to `<=` in a clamp) survives every test; the planted function has none.

**Known-answer check** (`mull.py --known-answer`): `src/known_answer.c`, built only with
`--enable-true-async-known-answer`, holds two identical functions; `tools/mull/known-answer.phpt`
calls the first. Holds when every mutant of the first is killed and every one of the second
survives (4 and 4 on 2026-10-01, 1.1 s). Checked to fail when the test calls both.

**Cost:** one mutant costs one run of the lists (8 mutants against one test took 1.3 s with the warm-up run, 2026-10-01). At a stage's
close `mull.py --diff-ref <Base:> --stage N` reports the changed lines' survivors; when its time
grows past what a stage close can wait for, each mutant gets the tests that cover its line (from
the coverage lane).

**Coverage.** `tools/test.py --lane pocs-dbg-cov`: the module with `--coverage
-fprofile-update=atomic`, counters zeroed before the run, `lcov` keeps `src/` only; the summary
line and `coverage.info` land in the run's directory. Recorded per stage with the date and the
list it ran.

## 7. Answers (Edmond, 2026-10-01)

1. `async-core-io` (and later `async-core-io-rfc/<date>`) is published as a branch of the same
   name in true-async/php-src, pushed by explicit refspec; no tracking upstream is set.
2. INI names take the module prefix: `true_async.*`, including `true_async.debug_deadlock`. The
   five `edge_cases` tests that set `async.debug_deadlock=0` are ported with `changed:` tags
   under one `DECISIONS.md` entry (S3). S3.4 ported three (`001`-`003`);
   `010-deadlock-after-cancel-with-zombie` and `015-deadlock-caught-still-terminates` are
   excluded as `component:S9` and get theirs there.
3. S2.4 includes a `windows-latest` job; its scripts are debugged in CI.
4. The TSAN tree waits for threads (S9).

## Critic 2026-10-01

Ten findings, all accepted and applied above: a form for own tests (`own:`); protection that
recomputes reference hashes from a checkout and checks `changed:` and the freeze; expected
statuses instead of "not all skipped", WARN as FAIL, the retry patch; lanes and `_build/` instead
of `build/<tree>`; `--asan -x`; full lane flags with `-g`; empty list refused, `-q` explained;
both halves of the Mull check and its cost; `rfc` as a published merge branch, `run-tests.php`
from the prefix, sparse checkout for the seven tests' helpers; the INI-name question (answer 2).

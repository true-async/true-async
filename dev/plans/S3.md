# S3 notes: the scheduler on the scheduler API

Agreed version, 2026-10-02. True Async registers as the core's scheduler (the 21 slots of
`zend_async_scheduler_api_t`, php/php-src#22561) and implements coroutines, the run queue, the
wait model, cancellation and the request lifecycle, with no reactor yet: a wait ends only through
another coroutine. The code adapts `ext/async` `1fdacf8` under the performance criterion of
`DECISIONS.md` 2026-10-01 and D2; section 11 lists what changes against it. The raw material
(expert reports, Critic rounds, the Sage rulings `structures-final.md` and `wait-model-sage.md`)
is in `dev/reviews/s3-structures/`; `EDMOND-DECISIONS.md` there is the record of Edmond's answers,
cited below as `D<n>` (D3 in its revised form; D25 is superseded by D28). The review of other
runtimes is `prior-art.md` there, cited as `prior-art 13.N`; only its items that change the S3
design are taken.

Sources: the RFC core `~/php-src2` `async-core-io` `834811f2d88`: `Zend/zend_async_API.h` below
`R:`, its other files by name (`zend_fibers.c`, `zend_gc.c`, `zend_async_API.c`, `main.c`); the
fork `~/php-src` `863f6dd90cf`: `Zend/zend_async_API.h` below `F:`, its other files as
`F` `file:line`; `ext/test_scheduler` in the RFC core, the reference C scheduler on the same API
(below `ts.c`); the reference `ext/async` `1fdacf8` (file names alone); the scheduler RFC text as
the reviews cite it (`RFC.md`, `scheduler_rfc.md`). "Compiled" sizes come from the Sages' probes
(gcc 13 -O2, x86-64, against the RFC headers); "measured" sizes of the reference and the fork come
from gdb (the brief). Nothing in this note was built or benchmarked.

## 1. What S3 implements of the TrueAsync API

Names, signatures and behaviour come from `ext/async/*.stub.php`; nothing new is invented.

| Kind | In S3 | Later |
|---|---|---|
| Functions (`Async\`) | `spawn`, `suspend`, `await` (a `Coroutine` only), `protect`, `current_coroutine`, `get_coroutines`, `graceful_shutdown` | `await`'s `$cancellation`, other awaitables: S5. `delay`, `timeout`: S4/S5. `await_*`, `iterate`: S5. `spawn_with`, `*_context`: S9 |
| `Coroutine` (final, `Completable`) | `getId`, `asHiPriority` (front of the run queue, D20), `getResult`, `getException`, `getTrace`, `getSpawnFileAndLine`, `getSpawnLocation`, `getSuspendFileAndLine`, `getSuspendLocation`, `isStarted`, `isQueued`, `isRunning`, `isSuspended`, `isCancelled`, `isCancellationRequested`, `isCompleted`, `getAwaitingInfo`, `cancel`; built only by `spawn`: `new` and reflection throw (S3.4, a departure from the reference) | `finally`: S9 (D21). `getContext`: S9 |
| Interfaces | `Awaitable`, `Completable`; `Awaitable` rejects classes the extension did not register (`interface_gets_implemented`, section 13, bug 10) | |
| Exceptions | `AsyncCancellation extends \Error` (D8), `DeadlockError extends \Error`, `CompositeException` (`edge_cases/013` constructs it directly), `AsyncException` | `OperationCanceledException`, `TimeoutException`: S5. IO exceptions: S6 |
| INI | `true_async.enable` (system, default 0, a boolean word: `On` enables); `true_async.debug_deadlock` (all, default 1) | |

**`AsyncCancellation` extends `\Error`** (D8): `catch (\Exception)` does not catch a cancellation,
`catch (\Error)` does. In TrueAsync its parent is `\Cancellation`, a class of the fork's core that
implements `Throwable` directly. PHP lets a class implement `Throwable` only when its root is
`Exception` or `Error`, internal classes included, and checks again on every subclass
(`zend_exceptions.c` `zend_implement_throwable`, `zend_inheritance.c:1612`). The scheduler RFC
defines no PHP-visible names (`scheduler_rfc.md:45-46, 350-353`), so the core gets no
`\Cancellation`.

**Out of S3**: `Coroutine::finally()` moves to S9 with Scope and runs there as in TrueAsync,
through an iterator in a child scope (`coroutine.c:1275-1303`), with no interim version in S3
(D21). Per-coroutine output buffers wait for S10 (D22). Context (`getContext`, `*_context`) is S9;
`Fiber::getCoroutine()` is S10 (section 8).

## 2. Coroutine state

All coroutine state is one 32-bit flags word at offset 0 of the RFC `zend_coroutine_t`: bits 0-15
belong to the core, 16-30 to the extension, bit 31 is the type bit. The TrueAsync methods are
formulas over this word plus one extension field, `deferred_cancellation`. The RFC status alone is
not enough: `coroutine/005` expects `isStarted()` false right after `spawn`, while the RFC defined
started as `status != CREATED` (R:189) and `spawn` sets QUEUED. D3 corrects the RFC with a core bit
for "the body began executing".

| Bits | Owner | Name | Meaning |
|---|---|---|---|
| 0-3 | core | status | CREATED / QUEUED / RUNNING / SUSPENDED / FINISHED (R:96-102); the scheduler is the only writer |
| 4 | core | `ZEND_COROUTINE_F_CANCELLED` | cancellation requested (D5, R:144, `scheduler_rfc.md:138`); never set while PROTECTED |
| 5 | core | `ZEND_COROUTINE_F_MAIN` | set by the core (`zend_async_API.c:737`) |
| 6 | core | `ZEND_COROUTINE_F_FIBER` | set by the core (`zend_fibers.c:1011`) |
| 7 | core | `ZEND_COROUTINE_F_OBJ_REF` | never set by True Async (the object is embedded) |
| 8 | core (S3.2) | `ZEND_COROUTINE_F_STARTED` | the body began executing (D3) |
| 9-15 | core | spare | |
| 16 | extension | `ASYNC_COROUTINE_F_PROTECTED` | inside `protect()`; fork `F_PROTECTED` (F:1803) |
| 17 | extension | `ASYNC_COROUTINE_F_EXCEPTION_HANDLED` | per notify: cleared before the notify, set by a waiter callback, read after the notify and after `extended_dispose` (`coroutine.c:667-705`); "handled" = bit 17 or `->exception` cleared by a core finish handler (R:84) |
| 18 | extension | `ASYNC_COROUTINE_F_EXC_CAUGHT` | somebody observed the exception; read by the destructor's rethrow decision (`coroutine.c:224`) |
| 19 | extension | `ASYNC_COROUTINE_F_BAILOUT` | finalize under bailout (D24) |
| 20 | extension | reserved `ASYNC_COROUTINE_F_ZOMBIE` | S9, not defined in S3 |
| 21 | extension | `ASYNC_COROUTINE_F_HI_PRIORITY` | set by `asHiPriority()`; the next enqueue pushes to the front and clears it (D35) |
| 22-30 | extension | spare | |
| 31 | type bit | 0 | coroutine (D4); 1 is an event |

- **`F_STARTED`** is set immediately before the body's first instruction by whoever runs it: the
  switch-in, the in-place run (`scheduler.c:633-641`), `launch` for main (`scheduler.c:1246`) and
  every re-minted main. A coroutine cancelled before it ran (its first entry carries an error,
  `RFC.md:169-171`) never gets it. The extension has no STARTED bit of its own; the ported
  `ZEND_COROUTINE_IS_STARTED` and `SET_STARTED` keep their meaning (D3).
- **`F_CANCELLED` means "requested"** (D5) and is never set inside `protect()`: a request there goes
  to `deferred_cancellation` (section 6). The core's terminal reading of the flag
  (`zend_fibers.c:1375` force-closes) is dropped in S3.2. A delivery leaves the bit set and
  `waker.error` NULL, so a later cancel is delivered again (section 6).
- **A yield is a status.** A coroutine that yields with `Async\suspend()` is QUEUED; no YIELD bit
  (D6). `coroutine/028` expects `isQueued()` and `isSuspended()` both true for it.
- **One queue entry per coroutine**: the queue is pushed only on a transition into QUEUED, so a
  cancel of a yielded coroutine cannot push it twice and switch into a dead context later.
- **Bit 31 = 0 is a coroutine** (D4): the coroutine allocator writes nothing, zeroed memory is a
  coroutine. Every event constructor sets bit 31 through `async_event_init()`, including ported
  code that `memset`s and then assigns `flags` wholesale (`channel.c:841-843`,
  `task_group.c:397-399`, `libuv_reactor.c:3478`, when their stages come). A debug-build assertion
  at each generic wait entry checks the object's class against the decoded type.
- The core never writes bits 16-31 (`zend_async_API.c:737-738` `|=`, R:139-141 masked
  `SET_STATUS`, `zend_fibers.c:1011` `|=`). The extension defines no `STARTED`, `YIELD`,
  `CANCEL_REQUESTED`, `IGNORED`, `RESULT`, `RESULT_USED` or `ZVAL_RESULT` bit: `IGNORED` becomes
  cancel-before-run (section 6); `RESULT` becomes the status RUNNING after a synchronous wake
  (section 4); `RESULT_USED` has one reader, `future.c:586` through F:1941; `ZVAL_RESULT` is
  constant true for a coroutine (`coroutine.c:666`).

**Methods** (S = status; `STARTED` = bit 8, `CANCELLED` = bit 4, `PROTECTED` = bit 16):

| Method | Formula | Pinned by |
|---|---|---|
| `isStarted` | `STARTED` | coroutine/005, 028 |
| `isQueued` | `S == QUEUED && !(CANCELLED && !STARTED)` | 028 (before the first run and after `suspend()`) |
| `isRunning` | `STARTED && !FINISHED` | 013, 038 |
| `isSuspended` | `S == QUEUED \|\| S == SUSPENDED` (D6); false while RUNNING (D18) | 028, 038, info/002 (five never-run coroutines), fiber/019 |
| `isCancelled` | `CANCELLED && FINISHED` | 005, 006, 028, 029, 038 |
| `isCancellationRequested` | `(CANCELLED && !FINISHED) \|\| deferred_cancellation != NULL` | 006, 028, 029, info/002 |
| `isCompleted` | `S == FINISHED` | 005, 028, 038 |
| `getResult` / `getException` | `FINISHED ? result / exception : null` | 002, 003, 004, 028 |
| `getTrace` | `(QUEUED \|\| SUSPENDED) && fiber_context && fiber_context->execute_data` → backtrace on that stack | 009, 037 |
| `getSuspendFileAndLine` / `Location` | same guard → file and line of `fiber_context->execute_data`; else `[null, 0]` / `"unknown"` (the running coroutine reads `"unknown"`, D18) | 008 (types only) |
| `getSpawnFileAndLine` / `Location` | `coroutine.filename`, `lineno` (R:124-125), captured at spawn | 007 |
| `getAwaitingInfo` | the RFC slot (section 4); `[]` when nothing is registered | 010, 026 (`is_array` only) |
| `cancel` | the cancel slot (section 6) | 006 |
| `getId` | `std.handle` | 001 |
| `asHiPriority` | sets bit 21; never enqueues; the coroutine's next enqueue puts it at the front of the run queue and clears the bit, once (D20, D35); returns `$this` | 011 (identity only) |

The reference's `isSuspended()` returns true for the running coroutine (`coroutine.c:1609-1619`,
the cleaned waker reads as "not yet resulted"); D18 calls it a bug. The reference's
`asHiPriority()` is a no-op with a TODO (`coroutine.c:1434-1439`); D20 calls it a bug. Both are
fixed in php-async too (section 13). `coroutine/038` (S5) and `fiber/019` (S10) are excluded from
the S3 list; the formulas they pin get own tests in S3 (section 9).

## 3. Data structures

The S3 coroutine is 296 B, allocated as 280 B in the 320 B bin; the reference's is 544 B, 528 B,
bin 640 (measured). The saving comes from the flat waker (40 B against the fork's 248 B), the
embedded event removed, and `finally_handlers` moved to S9. Every size below is compiled unless
marked otherwise; ZendMM bins are 256, 320, 384, 448, 512, 640 (`zend_alloc_sizes.h:47-52`).

### 3.1 `async_coroutine_t`

```c
struct _async_coroutine_s {                                   /* 296 B; allocation 280 (sizeof - 16,
                                                                 final class without properties,
                                                                 zend_objects_API.h:82-96); bin 320 */
	zend_coroutine_t coroutine;                                /*   0 144  R:104-132; flags at 0 */
	async_fiber_context_t *fiber_context;                      /* 144   8  execute_data stored at suspend entry */
	async_callbacks_vector_t callbacks;                        /* 152  16  waiters' records + finish handlers */
	async_waker_t waker;                                       /* 168  40  3.3 */
	async_scope_t *scope;                                      /* 208   8  D11; Scope logic in S9 */
	zend_object *deferred_cancellation;                        /* 216   8  the cancel that arrived inside protect() */
	async_awaiting_info_vector_t *awaiting_info;               /* 224   8  lazy; foreign RFC registrations (ts.c:387-418 shape) */
	async_coroutine_switch_handlers_vector_t *switch_handlers; /* 232   8  lazy; fork F:754-759, (handler, id) entries */
	zend_object std;                                           /* 240  56  last: properties_table tail */
};
```

- `scope` is in the struct now with a hook point at the first enqueue
  (`scope->after_coroutine_enqueue`, a no-op call site in S3); the Scope logic is S9 (D11). The name
  comes from the fork's `zend_async_scope_t *scope` (F:1767).
- `switch_handlers` stays: the core registers per-coroutine switch handlers on the current
  coroutine (`zend_objects_API.c:127`, `zend_execute_API.c:292`), which S3.10 needs.
- S9 adds `finally_handlers` back: 304 B, allocation 288, still bin 320 (compiled).
- `zend_fcall_t` stays a separate block from spawn until the Coroutine object is destroyed, as
  TrueAsync (F:1870-1871; `coroutine.c:164, 183-185`) (D17). Option O6 (`zend_fcall_t`, 104 B,
  inline) saves one allocation per spawn and is taken only if B1 measures it faster (section 12).
  The Sage computed O6 on an earlier 376 B layout as 480 / 464 / bin 512, the figure D17 quotes
  ("512 against 384 + 112"); on this layout the arithmetic gives 400 / 384 / bin 384 against
  320 + 112 (not compiled).
- No EH_THROW fields: the core saves `EG(error_handling)` and `EG(exception_class)` per switch (D1,
  16 B less per coroutine, section 5).

Dropped from the fork's and the reference's coroutine: the embedded event; the `waker` pointer (the
waker is embedded; NULL tests become `IS_FINISHED`); the fork's `internal_context` pointer (R:130
embeds 56 B); `extra_offset`, `ref_count`, `loop_ref_count`, `notify_handler` and the 8 vtable
slots (the coroutine is reached by type dispatch, 3.2); `waker.status` (folded into the RFC status);
`waker.events` (the hash), `triggered_events` and `dtor` (no writer: `F` `zend_async_API.c:1082`
has no caller; `dtor` is only reset); `inline_triggers`; `waker.filename/lineno` (computed lazily
from the parked frame); `F_YIELD`; `F_ZOMBIE` (S9).

### 3.2 The type bit, typed APIs and dispatch

```c
typedef struct _async_awaitable_s { uint32_t flags; } async_awaitable_t;   /* never instantiated */
#define ASYNC_AWAITABLE_F_EVENT            (1u << 31)                        /* 0 coroutine, 1 event */
#define ASYNC_AWAITABLE_IS_COROUTINE(p)    ((((const async_awaitable_t *) (p))->flags & ASYNC_AWAITABLE_F_EVENT) == 0)
#define ASYNC_EVENT_REFERENCE_PREFIX       (ASYNC_AWAITABLE_F_EVENT | ASYNC_EVENT_F_REFERENCE)   /* 0x80000080 */
```

Event helpers take `async_event_t *`, coroutine helpers `async_coroutine_t *`, generic wait code
`async_awaitable_t *`; all are `static zend_always_inline`. The build uses
`-Werror=incompatible-pointer-types` (`config.m4`) and `/we4133` (`config.w32`), so an event macro
applied to a coroutine fails to compile (gcc 13 only warns without the flag). Generic code branches
on bit 31 (`testl; js`, the same cost for either polarity) and calls the coroutine functions
directly; the object of a coroutine is `ZEND_COROUTINE_OBJECT` (R:166-171), of an event
`object_offset`. `async_awaitable_from_object(obj)`: `base = obj - handlers->offset`; a reference
prefix match gives `((async_event_ref_t *) base)->event`, else `base`. Debug builds assert the
class against the decoded type and `handlers->offset != 0`.

### 3.3 The waker

```c
typedef struct {                                 /* 40 B; fork zend_async_waker_t F:1706-1731 is 248 B (measured) */
	zend_object *error;                          /*  0  8  the RFC delivery channel (R:248-254) */
	zval result;                                 /*  8 16  moved out by await; cleared on the error exit */
	async_coroutine_event_callback_t *wait;      /* 24  8  first record of the current wait; NULL = none linked */
	uint32_t wait_count;                         /* 32  4  (+4 pad) the records of one wait are contiguous */
} async_waker_t;
```

The waker owns nothing but `error` and `result`. The records it points to live on the waiting
frame's C stack (section 4); `wait != NULL` only while the coroutine is parked or between its
first link and its switch out.

### 3.4 The wait record and the callback base

```c
struct _async_event_callback_s {                  /* 24 B; fork F:830-834 */
	uint32_t ref_count;                           /*  0 4  heap subscribers only; a record never reads it */
	uint32_t flags;                               /*  4 4  bit 0 F_RECORD, 1 F_COUNTED, 2 F_TYPED */
	async_event_callback_fn callback;             /*  8 8  wake function: resolve, cancel, timeout, await_* item */
	union {
		async_event_callback_dispose_fn dispose;  /* 16 8  heap subscribers (finish handlers, signal callbacks) */
		const async_wait_kind_t *kind;            /* 16 8  F_RECORD */
	};
};
typedef struct {                                  /* 40 B; fork zend_coroutine_event_callback_t F:862-868 */
	async_event_callback_t base;                  /*  0 24 */
	async_coroutine_t *coroutine;                 /* 24  8  the waiter */
	async_awaitable_t *event;                     /* 32  8  non-NULL iff linked in that target's callbacks; owns no reference */
} async_coroutine_event_callback_t;
```

`ASYNC_CALLBACK_F_RECORD` marks a wait record, so teardown never calls `dispose` on it;
`ASYNC_CALLBACK_F_COUNTED` marks a record that counts as an external wait (a Timeout, a Timer, IO:
S4+); `ASYNC_CALLBACK_F_TYPED` says `kind->unlink` is set, which spares two loads for plain kinds
(D30). A record is one wait-graph edge (`DECISIONS.md` 2026-10-01): waiter in `coroutine`, target
in `event`, kind in `kind`.

### 3.5 `async_wait_kind_t`

```c
typedef struct _async_wait_kind_s {               /* one const descriptor per wait kind, .rodata; 32 B (4 pointers,
                                                     arithmetic: the probe had 3 = 24) */
	zend_coroutine_awaiting_info_fn info;         /* R:68; data = the record */
	void (*unlink)(async_coroutine_event_callback_t *);  /* wake-time typed removal (op cancel, chunk walk); NULL = vector removal */
	void (*abort)(async_coroutine_event_callback_t *);   /* the frame never runs again: typed queue detach; NULL = nothing */
	void (*completers)(async_coroutine_event_callback_t *, void *walker); /* S7; NULL until S7 */
} async_wait_kind_t;
```

The code that links a record chooses its kind, so a target needs no PHP class and no methods
table: the kinds in S3 are COROUTINE (and the GC's await slot, which uses it); FUTURE, TIMEOUT,
TIMER, AWAIT_ITER, CHANNEL and IO come with their stages.

### 3.6 The callbacks vector and finish handlers

```c
typedef struct {                                 /* 16 B; fork F:883-890 is 24 B */
	union {
		async_event_callback_t **data;           /* capacity > 0: heap array (first growth: 4 slots, 32 B) */
		async_event_callback_t *single;          /* capacity == 0: at most one element inline */
	};                                           /* 0 8 */
	uint32_t length;                             /* 8 4 */
	uint32_t capacity;                           /* 12 4  bit 31 = a notify is iterating this vector */
} async_callbacks_vector_t;
typedef struct {                                 /* an RFC finish handler as a callback, 56 B (bin 56) */
	async_event_callback_t base;                 /*  0 24 */
	zend_coroutine_finish_handler_fn handler;    /* 24  8 */
	zend_coroutine_t *waiter;                    /* 32  8 */
	void *data;                                  /* 40  8 */
	uint32_t handler_id;                         /* 48  4  (+4 pad) from ASYNC_G(handler_id_seq), never 0 */
} async_finish_handler_callback_t;
```

A coroutine's `callbacks` holds its waiters' records and its finish handlers. The first waiter
costs no allocation (`single`); the reference allocates on a first await (2 allocations, 3 in
`ts.c`).

Every test of `capacity` masks bit 31: a notify of a one-waiter coroutine sets the bit, and the
waiter's self-removal must still read the inline case.

**Removal and cursor rule.** Outside a notify, removal swaps with the last element and decrements
`length`. During a notify of this vector (bit 31 of `capacity`) the cursor `cur`, the index of the
next callback to run, is found in the notify frame chain and corrected: removing `i < cur` does
`data[i] = data[cur-1]; data[cur-1] = data[--length]; cur--`; removing `i >= cur` swaps with the
last. Self-removal is the `i == cur-1` case. Removal is O(1), with no tombstones and no compaction,
and keeps the fork's wake order (A, C, B for a self-removing A). `async_callbacks_notify()` pushes
`{vector, cur, prev}` on its own C stack with the head in `ASYNC_G(notify_frames)`; a push whose
vector is already in the chain is the fork's nested-notify refusal (`F` `zend_async_API.c:1709-1714`).
A removal walks the chain only when bit 31 is set (depth at most 2 in practice). A thread-local
single cursor would adjust the wrong vector under a nested notify (T's notify resolves future F,
F's notify resumes W, W unlinks its record on T); the fork's per-vector pointer costs 8 B and its
adjustment is wrong (section 13, bug 7). The notify holds a reference to the awaitable for its
duration (`F` `zend_async_API.c:1689, 1739`); adds during a notify are allowed because the loop
re-reads `data` and `length` each step.

**As built in S3.3** (Critic 2026-10-02), where the text above differs:
- The notify frames are `ASYNC_G(notify_stack)[32]` with `notify_depth`, not a C-stack chain: a
  bailout out of a callback leaves nothing dangling. A notify that finds more frames than its own
  after a callback (a bailout caught inside it) drops them, clearing their bits;
  `async_callbacks_bailout_reset()` drops all of them (scheduler bailout handling, RSHUTDOWN). A
  vector freed while its bit is set clears its frame's pointer, and a notify whose vector is freed
  by a callback ends.
- A notify blocks fiber switching (`zend_fiber_switch_block()`): frames are LIFO only while no
  callback parks; a GC run inside a callback would otherwise await the GC coroutine mid-notify.
  With switching blocked the GC defers its run (`zend_gc.c:2256`).
- Every callback runs even after one throws: the RFC's finish handler "fires exactly once"
  (`zend_async_API.h:83`), and a waiter behind a throwing callback must wake. Callbacks run with no
  exception pending; their exceptions chain, the latest on top, over the one pending at entry.
- The reference held for the notify's duration is the caller's: the API has no object for a bare
  awaitable. S3.5's finalize holds the coroutine's object across its notify.
- A finish handler removed by id, or torn down, while it runs is unlinked; its call frees it once
  on return (`F_RUNNING`, `F_REMOVED`, bits 3 and 4 of the callback flags).
- Teardown with a linked wait record asserts and clears the record's `event`; waking its waiter
  with an error (section 4.4) comes with the waker in S3.5.

**Finish handlers keep stable identities.** The handle is a `uint32_t` id from one per-thread
counter `ASYNC_G(handler_id_seq)` (starts at 1, skips 0); remove scans by id. A positional handle
breaks when an earlier entry is removed (`ts.c:361-381`: A, B, C await T; removing A shifts B into
A's slot, B's removal then removes C's entry, so C hangs). The only core adder is `zend_gc.c:2134`,
one per GC run, so a finish handler is one 56 B emalloc per add. The RFC needs no change (no
`void *` handles).

### 3.7 The event header (S4 onward)

```c
struct _async_event_s {                          /* 24 B; fork event 104 B (measured) */
	uint32_t flags;                              /*  0 4  bit 31 = 1 */
	union { uint32_t ref_count; uint32_t object_offset; }; /* 4 4  ASYNC_EVENT_F_ZEND_OBJ selects */
	async_callbacks_vector_t callbacks;          /*  8 16  3.6 vector */
};
typedef struct { async_event_t base; zval result; zend_object *exception; } async_completion_event_t; /* 48 B */
```

No event methods (D28): the wake function sits on each subscriber (`callback`, as
`F` `zend_async_API.c:1727`), the per-kind behaviour on the record's kind, a Timeout's arm and
disarm behind one flag (`ASYNC_EVENT_F_ARM_ON_WAIT`), completion state in the completion block or
in `zend_coroutine_t.result/exception`. Event flags keep the fork's positions with the
`ASYNC_EVENT_F_` prefix: 0 `CLOSED`, 1 `RESULT_USED`, 2 `EXC_CAUGHT`, 3 `ZVAL_RESULT`, 4
`ZEND_OBJ`, 5 `EXTERNAL`, 6 `EXCEPTION_HANDLED`, 7 `REFERENCE` (only inside the prefix), 8
`ARM_ON_WAIT`, 9 `CLOSE_FD` (poll subtype only), 10 `HIDDEN`, 11 `BAILOUT`, 12 `COMPLETION`, 13-30
subtype bits (F:1131-1135), 31 the type bit. `NO_FREE_MEMORY` and `OBJ_REF` are cut. The fork's
`OBJ_REF` is set at `async.c:1666` (the Timeout) and read through `ZEND_ASYNC_EVENT_TO_OBJECT` at
`coroutine.c:315`, the waker's GC walk; `structures-final.md` 2.5 said no site uses it, which
`passive-edges-optimizer.md` 9.2 corrected. The walk is gone in this model (section 4, PHP GC), and
the Timeout keeps its own object pointer.

**Names.** D12: the base event is `async_event_t`; every fork type keeps its suffix and takes the
`async_` prefix (`async_waker_t`, `async_callbacks_vector_t`, `async_event_callback_t`,
`async_coroutine_event_callback_t`, `async_coroutine_switch_handlers_vector_t`). D30 accepts
`async_wait_kind_t`, `async_wait_unlink()`, `async_wait_abort()`, `async_wait_begin()`,
`ASYNC_CALLBACK_F_RECORD`, `F_COUNTED`, `F_TYPED`, the field `awaiting_info` and
`ASYNC_G(wait_unprotected)`. Accepted by D37: `async_awaitable_t`, `ASYNC_AWAITABLE_F_EVENT`,
`ASYNC_AWAITABLE_IS_COROUTINE()`, `async_event_init()`, `async_finish_handler_callback_t`. The notify
frame's struct is named with the code.

## 4. The wait model

A wait is a set of wait records on the waiting frame's C stack, each linked into one target's
`callbacks`; the waker points at the first record (D28). `suspend()` leaves no record linked on any
exit, and an enqueue unlinks the records at once, always (D26). Against the reference the model
keeps every protocol position (link before `suspend()`, generic unlink at enqueue, typed queue
state removed by the frame after resume) and removes storage: the per-coroutine events hash and
triggers, the start/stop loop, one owned reference per edge, the per-wait waker init and clean, the
event methods table. The reference keeps the same model in the fork's core API (F:830-1236,
1663-1740; `F` `zend_async_API.c:641-1375`); the RFC core has none of it, so it lives in the
extension and meets the core only through the slots.

**Invariants.**
- W: `waker.wait != NULL` only while the coroutine is parked (SUSPENDED) or is the current
  coroutine between its first link and its switch out inside `suspend()`. In both cases the frame
  holding the records is alive and unmodified.
- F: a linked record's target outlives the link because the frame keeps it alive: the call argument
  (`Async\await`, `$this` of a channel or pool method), one `Z_ADDREF` per `await_*` item (the
  reference's count, `F` `zend_async_API.c:1240-1241`), typed ownership of a classless event, the
  await slot's reference on the GC coroutine (`ts.c:542`).
- L: after the first link nothing allocates, throws or runs foreign code until the switch, except
  under a U5 `zend_try`. Links are stores into reserved capacity.
- `rec->event != NULL` exactly when the record is in that target's `callbacks`; whoever removes it
  (unlink, self-removal, typed wake code, teardown) clears it.

### 4.1 Phases of a wait

Every extension entry (`await`, `await_*`, channel and pool waits, `delay`, `Async\suspend`, the
await slot) runs the same phases; `Async\suspend` runs phase 0 without the self-await test before
its self-enqueue, so a refusal leaves it RUNNING, not QUEUED:

0. **`async_wait_begin()`**, before any side effect: refuse when there is no current coroutine; in
   scheduler context, with the reference's text "The operation cannot be executed in the scheduler
   context" (`async.c:62-66`, D31); when `zend_fiber_switch_blocked()` (D14); on self-await.
   Extension entries throw `Error`. The await slot returns false without throwing in scheduler
   context (D31) and when switching is blocked; the GC reads false as "not collected"
   (`zend_gc.c:2223-2234`). Debug builds assert `c->waker.wait == NULL`.
1. Completion checks of every target: a FINISHED coroutine gives `result`/`exception` in place; a
   closed `COMPLETION` event gives its block (and sets `EXCEPTION_HANDLED` when it delivers an
   exception); a fired Timeout or cancellation throws. `await_any` returns here; `await_all` counts.
   An `await_*` scans all items before any side effect.
2. Reservations: vector capacity per link, the `await_*` heap chunk for N > K. May bail out:
   nothing is linked yet.
3. Arms and submits: an `ARM_ON_WAIT` arm at 0 → 1 subscribers, a Timer or IO op submit. Dispatch
   happens only in a tick, never here; a synchronous failure undoes itself and returns.
4. Links: per record 5 stores (as `F` `zend_async_API.c:1140-1167`) and a push into reserved
   capacity; then `c->waker.wait = rec; wait_count = n`. Order inside a wait: items, cancellation,
   timeout.
5. `suspend()`.

An exception in phases 1-2 undoes nothing; in phase 3 it means a synchronous cancel. A bailout in
phase 3 with an op in the frame is an S4.1 constraint: the queue must not dispatch into dead
frames after a bailout.

### 4.2 The `suspend()` contract

Core callers (`zend_fibers.c:911`, `965`, `zend_gc.c:2163`) arrive with zero records; a park with
zero records is legal and parks (the core parks this way and the reference returns at once on an
empty waker, `scheduler.c:1664-1668`).

```
0. refuse (Error, return false) when: no current coroutine; ZEND_ASYNC_IN_SCHEDULER_CONTEXT;
   zend_fiber_switch_blocked(); the launch fails. Before returning: if (c->waker.wait) unlink(c).
   zend_exception_save_fast(&EG(exception), &saved)             (scheduler.c:1630 shape)
1. c->fiber_context->execute_data = EG(current_execute_data)  (one store; getTrace, GC, location)
2. if S != QUEUED: SET_STATUS(SUSPENDED)                        (QUEUED = the yield of Async\suspend)
3. ZEND_ASYNC_IN_SCHEDULER_CONTEXT = true
   tick: microtasks, deadlock resolution, in-place finalize of a cancelled-before-run coroutine,
   pool-miss context creation (S4 adds reactor dispatch). Each branch that can allocate or run PHP
   code runs under zend_try; catch: abort(c); flag cleared; re-raise (U5).
   An exception left in EG(exception) by tick work becomes the exit exception and starts the
   graceful shutdown (the reference's TRY_HANDLE_SUSPEND_EXCEPTION_BOOL, scheduler.c:79-88);
   EG(exception) is NULL again before the switch. A pool miss whose mmap fails throws, not bails
   out (zend_fibers.c:217-289): abort(c), then the same rule.
   A wake of c in the tick takes U2 (4.3: unlink; SUSPENDED -> RUNNING, a yielded c stays QUEUED).
   ZEND_ASYNC_IN_SCHEDULER_CONTEXT = false                      (after deadlock resolution, D31)
4. if S == RUNNING: goto out                                    (woken in the tick, no switch)
   next = pop(), skipping FINISHED entries
   if next == c: S = RUNNING; goto out                          (a yield with nobody ahead, B3)
   no next: not reachable (deadlock resolution woke every parked coroutine, c included); assert
   switch handlers leave; switch to next; on return: enter
   BAILOUT transfer (scheduler.c:353-355 shape): abort(c); zend_bailout()        (U4)
out:
5. if (c->waker.wait) unlink(c)        (non-NULL only on a false return without a wake,
                                        scheduler.c:1607-1611 / 1745 shape)
6. if (waker.error) { e = error; error = NULL; zval_ptr_dtor(&result); ZVAL_UNDEF(&result);
   rethrow(e) }
   zend_exception_restore_fast(&EG(exception), &saved)          (scheduler.c:1743)
   return EG(exception) == NULL
```

Every path out of `suspend()` leaves `wait == NULL`, so the frame never touches a record link after
`suspend()` returns; the exit check is one predicted-NULL compare in one place. Step 0 unlinks on a
refusal itself; step 5 catches any other return without a wake (the `scheduler.c:1607-1611` shape). An
exception pending at entry (a GC run while an exception unwinds a frame, `zend_gc.c:713-715` →
`:2223`) is saved in step 0 and restored in step 6, chained under any new one: `zend_fiber_vm_state`
does not carry `EG(exception)` across the switch (`zend_fibers.c:106-152`), and the next
coroutine's `zend_call_function` would return at once with it set (`zend_execute_API.c:923-928`).
The queue never holds a coroutine twice (4.3), so `next == c` happens only for a yield; a FINISHED
entry is a coroutine finalized in place while queued, and the tick drops it. Step 1 replaces the reference's
location capture (`scheduler.c:1713-1716`); `fiber_context->execute_data` is otherwise written only
at the switch (`scheduler.c:290-296`), after the tick has run microtasks and deadlock resolution.
The success path moves the result out (`ZVAL_COPY_VALUE` + UNDEF) instead of copying it twice.

### 4.3 Enqueue

`enqueue(c, error, transfer)`:
- FINISHED → false with an `Error`, as TrueAsync (D19). Core call sites: `zend_fibers.c:1440, 1477`
  expect false with an exception (`RETURN_THROWS`); `:1038` releases and lets it propagate; `:876,
  881, 908` ignore the result but wake a caller parked in `zend_fiber_await`, which cannot be
  FINISHED. The RFC comment (R:248) gains the FINISHED case in S3.2.
- `error != NULL` → applied to `waker.error` by the rule of section 6.
- `c == current && ZEND_ASYNC_IN_SCHEDULER_CONTEXT`, tested before the status (`coroutine.c:845-852`) →
  the U2 short path: `async_wait_unlink(c)`; SUSPENDED → RUNNING with no push; a yielded c stays
  QUEUED with its one queue entry, and the tick pops it as `next == c` (4.2 step 4). A coroutine in
  its own tick is SUSPENDED or QUEUED, never RUNNING, so a dispatch on the status alone would push it
  and later switch into the running context (`ZEND_ASSERT(to != from)`, `zend_fibers.c:483`).
- CREATED → first-enqueue bookkeeping (`first = S == CREATED`, read before the status write: the
  registry insert, the count, the `scope->after_coroutine_enqueue` hook), push, QUEUED.
- SUSPENDED → push, QUEUED, `async_wait_unlink(c)` at once, in scheduler context too (U1, D26).
- QUEUED → nothing more (one queue entry per coroutine).
- RUNNING: `c == current` (outside scheduler context, the U2 test above came first) → push, QUEUED
  (the yield `Async\suspend` performs, `async.c:232`); otherwise refuse with the reference's
  `Error("Cannot resume a coroutine that has not been suspended")`.

Every caller of enqueue goes through this order, cancel step 7 included (section 6).
`coroutine/028` reaches the `next == c` path twice (a yield while main is parked and every other
coroutine finished; main's own `suspend()`), and B3 on every iteration.

The reference deferred the unlink through `resumed_coroutines` when a coroutine was woken in
scheduler context (`coroutine.c:861-866`, `scheduler.c:426-436`), so a queued coroutine could take
a second event: a single-result wait then overwrote and leaked the first result
(`F` `zend_async_API.c:1256-1260`), and a channel value would be lost (D26). Waits that gather
several results (`await_all`, `await_any_of(n)`) keep catching through their own records until they
complete; a single-result wait takes one event.

### 4.4 Unlink, abort, and the sites that call them

**`async_wait_unlink(c)`**: for each of `wait_count` records with `rec->event` set: `F_TYPED` →
`kind->unlink(rec)`, else removal from the target's `callbacks` (a coroutine target by bit 31
directly; the cursor rule of 3.6, the cursor slot checked first so self-removal during a notify is
O(1)); `rec->event = NULL`; an `ARM_ON_WAIT` target whose length reached 0 and which has not fired
is disarmed. A record with `F_COUNTED` decrements `external_waits` and clears the bit. Then `wait =
NULL; wait_count = 0`. Idempotent; allocates nothing; runs no PHP code.
**`async_wait_abort(c)`**: `kind->abort(rec)` for each record that has one, then
`async_wait_unlink(c)`.

| Site | When it runs | Call | Records intact because |
|---|---|---|---|
| U1 | enqueue of a SUSPENDED coroutine | unlink | parked |
| U2 | enqueue of the current coroutine inside its own tick | unlink | inside `suspend()`, below the records |
| U3 | an exception in phases 1-3, or in the frame after a refused `suspend()` | unlink (the frame removes its own typed state) | own frame |
| U4 | `suspend()` returns with the BAILOUT transfer | abort, then `zend_bailout()` | nothing unwound yet |
| U5 | a bailout inside the tick on c's stack | abort in the `zend_try` catch, re-raise | the catch frame is below the records |
| U6 | RSHUTDOWN (`zend_deactivate_modules`, `main.c:1964`, before `zend_deactivate` frees the object store at `:1990`) for every registered unfinished coroutine with `wait != NULL`; a context freed for an unfinished coroutine | abort | the stack is still mapped |

U5 is an invariant: every allocation or foreign call between the first link and the switch runs
under a `zend_try` whose catch aborts the wait and re-raises; the fiber-context pool miss
(`scheduler.c:531-534, 647-650`) is such a branch. Debug builds set `ASYNC_G(wait_unprotected)` at
the first link, clear it at the switch, and assert it clear in every coroutine catch site. U6 runs
in RSHUTDOWN because after a fatal error no destructor runs (`main.c:1486`).

**Self-removal.** A record's callback fired by a one-shot target (coroutine finish, Future
completion, Timeout fire) removes its record from that vector at the cursor and clears
`rec->event` before anything else, whether or not it wakes the waiter; a Timeout fire also marks
the Timeout fired so no disarm follows. Multi-shot targets (channel close, an `ARM_ON_WAIT`
restart) leave records in place. **Teardown** of a `callbacks` vector that still holds `F_RECORD`
elements wakes each waiter with an error through the normal enqueue (U1 unlinks it), then fails a
debug assertion; no `dispose` is called on a record (prior-art 13.3). Invariant F says the case
cannot happen; where it fails in practice (a typed owner closed by another coroutine, a reactor
shutdown) a silent `rec->event = NULL` would leave the waiter parked with no edge and no wake. The
release path costs nothing on the hot path.

Debug asserts: `wait == NULL` at finish, in every coroutine catch site (the `coroutine.c:546-551`
position, `zend_fibers.c:805-828`) and before a context returns to the pool. Against stale records
on a reused stack (the next wait in the same frame, or another coroutine after the context returns
to the pool, D23), debug builds also scan the target vector for the record's address at link, keep
a per-coroutine wait sequence number in the record that the callback checks against the
coroutine's current one, and fill a pooled stack with a pattern on its return (prior-art 13.9).

### 4.5 Bailout

`bailout_all_coroutines` (`scheduler.c:949-1000`) switches into every started unfinished coroutine
with the BAILOUT transfer flag, queued ones first; each unwinds through U4. A waiter woken by a
finalize during the drain is unlinked by U1 before it is switched into. Never-started coroutines
hold no records. Main parks on the OS stack and takes U4 like any other. The core forwards a
bailout across fibers through `ZEND_FIBER_TRANSFER_FLAG_BAILOUT` (`zend_fibers.c:648, 690-691`;
`F` `zend_fibers.c:651-652, 694-697`) (D15). The catch at `coroutine.c:547` sets
`ASYNC_COROUTINE_F_BAILOUT` before finalize, and `is_bailout = bit 19 || ASYNC_G(bailing_out)`
(set in the execute catch and in `bailout_all_coroutines`) (D24). The RFC expresses bailout as an
argument (finish handler `is_bailout`, R:83-90; `suspend(from_main, is_bailout)`, R:260-261), the
fiber keeps `ZEND_FIBER_FLAG_BAILOUT` (`zend_fibers.c:803-825`), and no core code reads a
per-coroutine bailout state, so the bit stays in the extension. Running the tick and picking the
next coroutine before linking (no U5) is rejected: deadlock resolution runs inside the tick and
must see the suspender's own wait.

### 4.6 The scheduler-context flag

The fork's `ZEND_ASYNC_G(in_scheduler_context)` (F:2195, 2255-2256) is already a slot of the RFC
core: `ZEND_ASYNC_IN_SCHEDULER_CONTEXT` (R:652-666, 696), which `ts.c` writes and no core file
reads yet. True Async writes that slot and keeps no copy (D31, D38); the exit exception likewise
lives in `ZEND_ASYNC_EXIT_EXCEPTION` (R:694). The flag is set for the whole tick, deadlock
resolution included; the reference clears it before deadlock resolution (`scheduler.c:1572`). The
flag, not the core's fiber switch block, closes the window: `async_wait_begin()` refuses on it
before linking, the `suspend()` slot refuses on it, the RFC await slot returns false in it, and a
GC entered inside the tick only starts its coroutine (D13, section 7). A second wait by the current
coroutine inside its own tick is therefore refused before it links: a PHP output handler run by
the deadlock report or a destructor run by a microtask release calls `Async\await` and gets the
`Error` (section 13, bug 12). The Fiber methods change state before they reach a slot:
`Fiber::suspend()` wakes its caller and marks the fiber SUSPENDED (`zend_fibers.c:897-908`) before
`ZEND_ASYNC_SUSPEND()` at `:911`, and `start`, `resume`, `throw` enqueue the fiber coroutine
(`:1038, 1440, 1477`) first, so a refusal in the slot would leave the switch half done. The four
methods therefore refuse on the core's flag beside their `zend_fiber_switch_blocked()` checks
(`:1314, 1370, 1421, 1464`), an S3.2 change (section 10, item 13). The cost is the two flag writes
per tick the reference already makes (`scheduler.c:1525, 1572`), through the core's globals.

### 4.7 Awaiting info

The wait record is the RFC awaiting-info registration (R:60-68): created by whoever suspends,
wiped at enqueue (U1), diagnostics only. `get_awaiting_info` (R:394) walks `waker.wait` calling
`kind->info(c, rec)`, then the lazy `awaiting_info` vector of foreign registrations. A zero-record
park gets a line from the coroutine's state: a fiber from `F_FIBER` and `context.status`, the GC
coroutine, a `suspend()` yield from QUEUED. Tests pin only `is_array` (`coroutine/010`, `026`). The
deadlock report and S7 read the same records: waiter → record → (`event`, `kind`); `F_COUNTED`
marks an external root; core-owned edges (a fiber's `caller_coroutine`, a GC finish handler's
`waiter`) are read from the target side. A foreign extension parking through the RFC `suspend` slot
with an external wake has no way to say so; R:60-68 could carry an "external" bit (an S8 change
request candidate; settled by S6's `signal`/`exec` tests).

**Cancellation.** `cancel(c)` on a parked coroutine enqueues it with the error; U1 unlinks; c runs;
step 6 throws with the result cleared. On a QUEUED coroutine already woken with a result, the
error is applied (section 6) and step 6 discards the result. A cancellation token is the second
record of the wait (S5).

**Consumed values** (prior-art 13.1). Step 6 drops `result` on an error, which is harmless while the
result is a copy of state the target keeps (a coroutine's or a Future's result) and loses data
when the wake transfers ownership (a channel item, a pool resource, a permit: S9). Rule: a record
callback never moves ownership into the waker; a consuming kind keeps the value in the target
under a reservation until the frame claims it after resume, and both the frame's error exit and
`kind->abort` release the reservation and wake the next waiter. The CHANNEL kind's `abort` (D29)
therefore passes an unspent reservation on, as the reference does after resume
(`channel.c:755-778`). Test (S9): a receiver woken with an item and cancelled before it runs; the
item reaches the next receiver; the same with a bailout in place of the cancel.

**PHP GC.** Records own nothing, so the coroutine's `get_gc` reports no record (section 13, bug 6
disappears); the parked frame is reachable through the RFC execute-data slot (R:363); targets live
by F.

## 5. Execution model

Coroutines run in FIFO order from one run queue, on pooled fiber contexts, with direct switches
and no scheduler coroutine; the RFC allows this (the `await` slot's comment names "a direct
switch").

- **Run queue**: the reference circular buffer of pointers (power of two, masks, inline push and
  pop), FIFO for every coroutine, those minted by `gc_new_coroutine` included (D20; the RFC says
  only "a dedicated coroutine", `scheduler_rfc.md:570, 631`). Queue shrinking (`auto_optimize`) is
  off for the run queue. A front-of-queue GC coroutine reorders destructors: in `gc/005` a second
  iterator would run B's destructor before A's finishes (`A start, A suspended, B start, …` instead
  of `A start, A suspended, A end, …`).
- **`asHiPriority()`** puts the coroutine at the front of the run queue, as TrueAsync's internal
  priority does at spawn (`circular_buffer_push_front`, `async_API.c:155-162`) (D20). Priority is
  mainly for internal use; a reference test that depends on the old order may be changed (none
  found: `coroutine/011` checks identity only). A coroutine already in the queue is not moved (no
  scan of the ring buffer): the call sets bit 21, and the next enqueue puts it at the front and
  clears the bit, so the priority applies once, not to every later wake (D35).
- **Fiber contexts are separate and pooled.** `zend_fiber_init_context` always allocates a fresh
  stack (`zend_fibers.c:205-272, 417-419`: mmap, mprotect, a name, an emalloc), so a context cannot
  live inside the coroutine. A context is an `async_fiber_context_t` of its own; when its coroutine
  finishes, the context's loop (`fiber_entry`) picks up the next coroutine instead of returning. The
  pool follows TrueAsync's policy (D23, `scheduler.c:465-485`, `scheduler.h:22`): keep at least
  `ASYNC_FIBER_POOL_SIZE` = 4 contexts, keep more while the pool holds fewer contexts than the run
  queue, destroy the rest. The performance review found the pool of 4 missing on about 97 % of
  links in a chain of awaits; a high-water-mark pool is measured against the policy on an await
  chain before any change (section 12). A context returns to the pool only after its coroutine
  finished, when W gives `wait == NULL`; a stack freed without a switch goes through U6.
- **Direct switches.** `suspend` runs the tick inside the suspending fiber and switches straight to
  the next coroutine (`scheduler.c:1718` → `1601` → `497-546`); there is no hop through a scheduler
  coroutine per handoff.
- **In-place run.** A new coroutine runs in place on a free fiber with no switch at all
  (`scheduler.c:633-641`); `F_STARTED` is set there too.
- **EH_THROW window per coroutine** is the core's: the core saves `EG(error_handling)` and
  `EG(exception_class)` per switch in `zend_fiber_vm_state` and resets them before the jump, as the
  fork does (`F` `zend_fibers.c:515-519`) (D1, S3.2). The RFC core saves neither today. The
  extension keeps no field and no test hook: the window's test belongs to the core change in S3.2,
  through `ext/test_scheduler`; the reference tests for it (`edge_cases/016`, `017`) need S6.

**What one coroutine allocates**: the coroutine object (bin 320); the `zend_fcall_t` block (bin
112, D17); a `callbacks` heap array only when a second waiter arrives (first growth 4 slots, 32 B);
one 56 B block per finish handler; a fiber context only when the pool is empty. No waker events
table and no per-wait allocation.

## 6. Cancellation, protect(), unhandled exceptions, exit()

A cancellation is requested by setting `F_CANCELLED` and delivered by throwing `waker.error` at the
coroutine's next switch-in; inside `protect()` the request waits in `deferred_cancellation` until
`protect` returns.

**`cancel(c, error, transfer, is_safely)`**, the reference's rule (`coroutine.c:900-1003`):
1. FINISHED → release, true.
2. `error == NULL` → a new `AsyncCancellation("Coroutine cancelled")`.
3. PROTECTED → `deferred_cancellation = error` only if it is NULL, else release; `CANCELLED` is not
   set; true. Tested before the running case, so `protect(fn() => current_coroutine()->cancel())`
   defers too and `F_CANCELLED` is never set inside `protect()` (section 2).
4. `c == current && S == RUNNING` (from step 2 of 4.2 on, a coroutine inside its own `suspend()` is
   SUSPENDED or QUEUED and takes the waker path below) → set `CANCELLED`; the coroutine's
   `exception` takes `error`; the body continues; true.
5. `was = CANCELLED`; set `CANCELLED`.
6. `!STARTED` → enqueue if CREATED; apply the cancellation to `waker.error` (a cancellation
   overrides a plain error and keeps an existing cancellation, `F` `zend_async_API.c:1344-1367`).
   The switch-in sees `CANCELLED && !STARTED` and skips the body: "first entry with an error"
   (`RFC.md:169-171`; the reference's IGNORED path, `coroutine.c:466-499`). `is_safely` is a plain
   cancel in S3 (the zombie is S9).
7. Otherwise: `was && waker.error` is a cancellation → release (dropped); else apply. Enqueue by
   the order of 4.3 (the U2 test first, then a push only if SUSPENDED).

Delivery: at switch-in `waker.error` is consumed and thrown; `CANCELLED` stays, so a later cancel
finds `waker.error == NULL` and is delivered again (`coroutine.c:994-1003`). Two coroutines that
catch their cancellations and then await each other get the deadlock's cancellation instead of
having it dropped as "already requested" (`edge_cases/003`). The delivery is edge-triggered: one
`AsyncCancellation` is thrown and the next await does not raise again, so cleanup code that
catches the cancellation and awaits again can wait forever; D16's 5 s deadline bounds this for
shutdown only. Edge-triggered delivery is kept as TrueAsync's (D33; prior-art 13.13 weighed Trio's
level-triggered model and was not taken). Spawn failures after the registry
insert take the same cancel-before-run path (`F_CANCELLED` with the failure as the error, body
skipped, finalize runs); in S3 only the registry-add failure remains.

**`protect(f)`**: `was_protected = PROTECTED; set PROTECTED; call f; if (!was_protected) { clear
PROTECTED; if (deferred_cancellation) { set CANCELLED; throw it; set it NULL } }` (D7). The
`was_protected` local fixes nested `protect()` (section 13, bug 1). Deadlock and graceful shutdown
clear PROTECTED and cancel through the waker (`scheduler.c:867-868, 924-925`); an earlier
`deferred_cancellation` may then be thrown a second time at protect's exit, as in the reference,
with no test; left as is.

**Deadlock**: the run queue is empty, no microtask is pending, and parked coroutines remain. The
decision uses the scheduler's own count of parked user waits (`DECISIONS.md` 2026-10-01, review M5);
the core never reads or writes `active_coroutine_count`, so the count is the extension's. Fibers
are exempt, as in the reference (`scheduler.c:779-817`): when every remaining coroutine is a
suspended fiber (`F_FIBER`, `extended_data != NULL`, `((zend_fiber *) extended_data)->context.status
== ZEND_FIBER_STATUS_SUSPENDED`, `zend_fibers.c:899, 920`; D6), they are cancelled gracefully with
no `DeadlockError`; a Revolt-style worker fiber left suspended (`fiber/022`) is not a deadlock.
Outcome as the reference: `DeadlockError("Deadlock detected: no active coroutines, %u coroutines in
waiting")` becomes the exit exception (`ZEND_ASYNC_EXIT_EXCEPTION`, 4.6), every parked coroutine is cancelled with
`AsyncCancellation("Deadlock detected")`, protection cleared. `true_async.debug_deadlock=1` prints
the report of `dump_deadlock_info`, read from the wait records (4.7).

**Unhandled exceptions** follow the reference: an exception of a finished coroutine that nobody
can observe (refcount at most 1, or main, or a fiber, `coroutine.c:737-745`) becomes the exit
exception and starts the graceful shutdown: every other coroutine is cancelled, so its
`try`/`finally` blocks run, and `Fatal error: Uncaught` is printed after the drain
(`main.c:2632`), not at once. An observable one is rethrown from the coroutine's destructor
(`coroutine.c:219-230`) unless bit 18 says somebody observed it. Main's own uncaught exception,
still in `EG(exception)` when call 1 starts (`zend.c:1989-1993`), takes the same path. `spawn/007`
and `012` check it.

**`exit()` in a coroutine** runs as in TrueAsync (D16): the graceful shutdown, where every other
coroutine gets a catchable `AsyncCancellation("Graceful shutdown")` (`scheduler.c:891-907,
1005-1030`). After an `exit()` the scheduler gives the coroutines 5 seconds to finish; whatever is
still alive then is unwound without a catchable exception, and its `finally` blocks run. The
deadline needs a clock in the scheduler loop and a reactor timeout, so it lands with the reactor
(S4); S3 records the rule. The `shutdown` slot (called only from a fiber coroutine's entry,
`zend_fibers.c:854-859`) must leave `EG(exception)` alone: the core reads it right after
(`:872-873`), and the reference's `start_graceful_shutdown` clears it, which crashes there
(`GC_ADDREF(NULL)`); the fork's core cleared it before the call. A spawned coroutine's
unwind_exit, which `ts.c` drops (`:1012-1020`), takes the same path. No S3 candidate covers
`exit()`; own tests cover it in a spawned coroutine and in an adopted fiber.

**`graceful_shutdown()`** cancels queued coroutines with the given cancellation
(`start_graceful_shutdown_with`), or with `AsyncCancellation("Graceful shutdown")` when none is
given (`scheduler.c:891-907`).

## 7. Request lifecycle and GC

The core calls `suspend(from_main=true)` up to three times per request, and the scheduler's state
machine names each:

| Call | Where | Meaning |
|---|---|---|
| 1. `suspend(true, false)` | end of the script (`main.c:2618`) | main finishes: its finish handlers and waiters run, the queue drains; main is then re-minted in place on the same fiber context (as `ts.c`), with `F_STARTED`, so the core sees a current coroutine again |
| 2. `suspend(true, true)` | `zend_catch` around the script (`main.c:2620`) | a bailout in main or during drain 1 (all 11 `bailout` candidates hit OOM or a stack overflow there; 001, 006, 009, 012 while main is parked): every started coroutine is switched into with the bailout flag and unwinds through U4 (`ts_bailout_all`; section 4.5); never-started ones finish with `is_bailout` handlers; main may already be finished, and the call must accept that; main is then re-minted as after call 1 (`ts.c:1522-1526`), so shutdown functions that still run after a fatal error meet a current coroutine |
| 3. `suspend(true, false)` | after destructors (`main.c:1938`) | drain 2: coroutines spawned by shutdown functions and destructors run; the core checks `IS_ACTIVE` before this call, so the state stays ACTIVE between the drains (the reference's reset to READY after main, `scheduler.c:1385`, would skip it) |

The contract of 4.2 is the `from_main=false` path. Every `from_main` call moves the exit exception
into `EG(exception)` before it returns: `main.c` prints only `EG(exception)` (`main.c:1942, 2632`).

| Point | True Async |
|---|---|
| Script start | `launch`: wraps `EG(main_fiber_context)` as main and sets `F_STARTED` (the core sets MAIN and RUNNING, `zend_async_API.c:737-738`); contexts come from the pool afterwards |
| Shutdown functions, destructors | run while ACTIVE; destructors through the core's iterators on `gc_new_coroutine` and switch handlers (`zend_execute_API.c:261-292`, `zend_objects_API.c:90-182`) |
| Output handlers | `php_output_end_all` runs after DEACTIVATE; per-coroutine buffers are S10 (D22) |
| `exit()`, `graceful_shutdown()` | section 6 |
| RINIT, RSHUTDOWN | the core goes OFF at every request end (`main.c:1948`): RINIT calls `ZEND_ASYNC_INITIALIZE`; RSHUTDOWN aborts the waits of unfinished coroutines (U6), frees the queues, releases unrun microtasks, drops the exit exception, and sets `ZEND_ASYNC_CURRENT_COROUTINE` and `MAIN_COROUTINE` to NULL (the core does not at DEACTIVATE, and `ZEND_ASYNC_INTERNAL_CONTEXT_FIND(NULL, …)` in the next request's RINIT would read the freed coroutine) |

**GC.** The RFC core collects in a coroutine and runs deferred destructors through `defer`,
`await` and finish handlers (`zend_gc.c:2017-2235`). `zend_gc_collect_cycles` awaits the GC
coroutine whenever async is active (`zend_gc.c:2203-2235`), and automatic GC fires at any
allocation that crosses the root threshold: inside the scheduler's own work (releasing a finished
coroutine), inside a microtask, inside a tick function or a pcntl handler where switching is
blocked. The fork's core defers instead (`F` `zend_gc.c:677-681`). The rules:

- **Where switching is blocked**, the GC starts its coroutine (`new_gc_coroutine`,
  `zend_gc.c:2181-2197`; the enqueue needs no switch) and returns 0 without awaiting; the
  collection runs at the next tick. The root still lands in the buffer (`zend_gc.c:724-735`). A
  core change on `async-core` (D13); its side effect, `gc_adjust_threshold(0)` raising the
  threshold by a step (`:681-692`), is settled in S3.2.
- **In scheduler context** the RFC await slot returns false without throwing (D31); the GC treats
  false as "not collected" and its already enqueued coroutine collects at the next tick
  (`zend_gc.c:2217-2234`).
- **User waits where switching is blocked**: `Async\suspend()` and `Async\await()` throw `Error`,
  checked through `ZEND_API zend_fiber_switch_blocked()` (`zend_fibers.c:412`), as the Fiber methods
  do (`:1314, 1370, 1397, 1421, 1464`) (D14). No core change.
- **No rule for the `from_main` calls and no reset hook** (D15): the switch-block counter is reset
  per request only, in the RFC core as in the fork (`zend_fibers.c:1621`; `F` `zend_fibers.c:2022`),
  so a block leaked by a fatal error behaves as in plain PHP.

`gc/005` ran its GC inline in the reference and expects `GC collected cycles: 2` after the
destructors; `gc/011` ran inside an active scheduler and expects `0` at once. The RFC core starts
the scheduler eagerly, and no GC behaviour passes both as written: both are ported with `changed:`.

## 8. Fibers

Fibers are in S3 (D9). With a scheduler active, `Fiber::start()` asks `intercept_fiber` for a
coroutine (R:341-356); NULL would keep the legacy fiber, which switches stacks the scheduler does
not know about, so True Async always adopts. The core marks the coroutine `F_FIBER`
(`zend_fibers.c:1011`). A fiber's caller parks with zero records and the edge is
`fiber->caller_coroutine` (4.8); `Fiber::suspend()` parks through the suspend slot
(`zend_fibers.c:911`) and is refused inside the tick (4.6). The deadlock exemption reads
`context.status` (section 6, D6).

Core changes that touch fibers (S3.2, section 10): a Fiber dropped while its coroutine is not
FINISHED is cancelled (`zend_fibers.c:770`, D3), so a parked caller is woken through U1; the only
CREATED fiber coroutine, on the failed-enqueue branch (`zend_fibers.c:1038-1039`), is released
without a cancel; `zend_fibers.c:1375` keeps only `extended_data == NULL` (D5), so a
scheduler-cancelled fiber may call `Fiber::suspend()` from `finally`, a behaviour change accepted
with D5. `fiber/030` expects a `FiberError` "Cannot suspend in a force-closed fiber" at shutdown;
under that change the fiber parks again in `finally`, the exemption delivers the graceful exit once
more and unwinds it, and the error never appears (traced by reading, `s3-note-critic.md` 5). The
test is excluded with `rfc-rule:` D5; an own test covers the new behaviour.

Of the 30 `fiber` tests, 7 call `Fiber::getCoroutine()`, absent from the RFC core (S10): up to 23
candidates (section 9).

## 10. Core changes for S3.2

The minimal list, each a one-topic commit on `async-core` with a test, then a core update by

1. `ZEND_COROUTINE_F_STARTED` (bit 8); `ZEND_COROUTINE_IS_STARTED` reads it; the RFC contract: the
   scheduler sets it immediately before the body's first instruction (in-place run and main

   say "the body began executing" (`coroutine/005`). D3.

## 12. Measurements before final

D2: on B1-B5, at most 3 % more `instructions:u` per operation than the reference `1fdacf8`, and
allocations per operation not above it. Edmond's key criterion is speed; a departure from the
reference's code needs a measurement (D17).

**Reference** (performance review, release build `~/php-src/bld-rel-zts`, ZTS, `-O2`; its
`ext/async` objects predate `1fdacf8`, so the numbers are indicative until it is rebuilt):

| Operation | Reference | Note |
|---|---|---|
| `spawn` to finish | 2 allocations (object 544 B in the 640 B bin, fcall), a scope vector add, a hash insert and delete, three `zend_try`, about 7 indirect calls; 0 switches after the first (in-place run) | the 100 000-coroutine run is 88 % scope bookkeeping, quadratic (`scope.c:58-74`) |
| `suspend` and resume | 0 allocations, 1 switch, 76-84 ns: waker clean about 10 %, file and line capture about 5 %, `clock_gettime` about 3 %, the switch about 15 % | |
| `await` on a coroutine | 0 allocations per wait after the first (the events hash and the target's callback vector, once per coroutine); 2 hash lookups and 1 delete, about 6 indirect calls, the result copied twice | on a fiber-pool miss: about 7 mallocs, 4.85 syscalls and 4.9 page faults per link, about 75 % of the chain-of-awaits time |

**Benchmarks** (`bench/`):

| Name | What | Isolates |
|---|---|---|
| B0 | empty script | startup |
| B1 | `gc_disable()`, spawn and await in batches of 100, 1000 batches; a labelled unbatched 100 000 variant | spawn, first run, finish; scaling |
| B2 | ping-pong of two coroutines, 2 000 000 `suspend()` | suspend, enqueue, switch |
| B3 | one coroutine suspending alone | the tick without a switch (B2 − B3 = the switch) |
| B4 | recursive `await(spawn(f, k-1))`, depth 100 × 1000 and 10 000 × 10 | park and wake, fiber supply |
| B5 | 1000 waiters on one target × 100 | growth of the target's `callbacks`, removal under fan-in |

**Method**: release builds of both sides (the reference `bld-rel-zts` rebuilt at `1fdacf8`, fork
core `863f6dd`, `make` then `make sapi/cli/php`; the RFC core `834811f2d88` in a separate tree with
the WORKFLOW configure line minus `--enable-debug`, installed in `~/ta-prefix/pocs-rel`), ZTS, `-n`,
no opcache, pinned to one core (`taskset -c 3`). Primary metric: `perf stat -e instructions:u` per
operation as (I(2N) − I(N)) / N, stable to 0.001 % where wall time moves ±10 % on WSL2. Alongside:
allocations per operation (an LD_PRELOAD counter with `USE_ZEND_ALLOC=0`), page faults, `strace -c`.
Wall time: builds alternated, 30 runs each, median with a bootstrap 95 % interval.

**Known answer**, run first: a B1 variant with one extra `new stdClass` per spawn shows exactly one
more allocation per operation and a separable instruction count; a C variant with
`efree(emalloc(64))` in the spawn path behind `--enable-true-async-known-answer` does the same. A
benchmark that cannot separate them does not judge the allocation criterion.

**Thresholds.** "Faster", "regresses" and "shows" in the table below mean a difference above 0.5 %
in `instructions:u` per operation (five hundred times the spread of the metric), with allocations
per operation not above the other side's; the wall-time interval is reported, and a result where it
points the other way is named. O(N^2) means per-wake instructions grow more than threefold from
N = 1 000 to N = 10 000. D2's control: B2 and B4 with an empty scheduler (`ext/test_scheduler`) on
both cores, so the comparison carries no difference between the cores (section 10, item 14).

| Item | Run | Decides |

## 13. Reference and fork bugs to fix in php-async

Found by reading, not run, unless marked.

1. **Nested `protect()`** (`async.c:251, 276, 289-293`): `protect(fn() => protect(fn() =>
   suspend()))` cancelled while the inner runs: the inner's exit clears PROTECTED and throws the
   deferred cancellation inside the outer `protect` (D7). `protect/003` nests but never cancels.
2. **`isSuspended()` true while running** (`coroutine.c:1609-1619`): the cleaned waker reads as "not
   yet resulted" (D18).
3. **`asHiPriority()` is a no-op** (`coroutine.c:1434-1439`, a TODO) (D20).
4. **A woken coroutine takes a second event** (`coroutine.c:861-866`, `scheduler.c:426-436`): woken in
   scheduler context, its unlink is deferred; a second target firing in the same tick overwrites
   and leaks the first result (`F` `zend_async_API.c:1256-1260`; `scheduler.c:1450-1510`), and a
   channel value is lost (D26).
5. **The Traversable iterator links after the waiter returned** (`async_API.c:526-618`): after
   `await_any_or_fail(gen())` returns on item 0 (`:1130-1133`), a later `yield` adds an edge to the
   waiter's current waker (`:618`, read at `:540`) (D27).
6. **The waker's GC walk reads triggers as events** (`coroutine.c:310-318` against
   `F` `zend_async_API.c:1203-1204`): a coroutine parked in `await($future)` with the future
   reachable only through that wait: the trigger's `length` (1) is read as flags → `CLOSED`,
   nothing is reported, the object is invisible to the cycle collector (leak); a `length` in 16-31
   would be read as `ZEND_OBJ` and push a garbage pointer.
7. **The fork's callbacks-vector iterator** (`F` `zend_async_API.c:1654-1660`): callbacks A B C D on
   one target, B's handler removes A: the fork runs A B B C, never D (reproduced in a
   transcription, `opt/iter_sim.c`).
8. **Spawn failure after the registry insert** (`async_API.c:170-200`, `scheduler.c:1486-1495`): a
   throwing `SpawnStrategy::afterCoroutineEnqueue` leaves the coroutine IGNORED without CANCELLED;
   `coroutine.c:466-470` skips finalize, so `ASYNC_G(coroutines)` keeps the pointer after
   `OBJ_RELEASE`; `get_coroutines()` or the deadlock report reads freed memory.
9. **Bailout runs PHP finally handlers** (`scheduler.c:960-968`, `coroutine.c:547-552, 1329-1336`):
   OOM in coroutine A while B (started, queued, with `finally()`) waits: B is switched into with the
   BAILOUT transfer flag without `SET_BAILOUT`, and finalize calls B's handlers during the bailout
   (D24's fix).
10. **A user class implementing `Async\Completable` is awaited as an event** (`async.c:302`, no
    `interface_gets_implemented`): `await(new class implements Async\Completable { … })` reads the
    `zend_object` header as an event (`handlers->offset == 0`) and writes a callback into it.
11. **A bailout is lost in `TRY_HANDLE_SUSPEND_EXCEPTION_BOOL`** (`scheduler.c:79-88`): under graceful
    shutdown the macro discards the return of `switch_to_scheduler(transfer)`; a BAILOUT transfer
    from `bailout_all_coroutines` (`scheduler.c:968`) comes back as true, and the coroutine keeps
    executing PHP code during the bailout (`exit()` in A, a throwing microtask in B's tick, OOM in C).
12. **A second wait by the current coroutine cleans the first** (`coroutine.c:68, 84-86`): main awaits
    `$x`; the deadlock report prints through an `ob_start` handler that calls
    `Async\await(Async\spawn(fn() => 1))`; the inner wait removes main's edge on `$x` (scheduler
    context is already false at `scheduler.c:1572`). D31's flag refuses the inner wait.
13. **Dead call** `zend_fiber_switch_blocked()` at `scheduler.c:1243`: the result is discarded, the
    block is never honoured (D14 adds the check).
14. **Parks without `zend_try`**: `pool.c:472`, `async.c:1075`, `scope.c:370, 439`,
    `task_group.c:1467` park without the `zend_try` that `thread_pool.c:247-256` and
    `thread_channel.c:177-194` use, so a bailout leaves their heap waiters in event vectors (a
    debug-build leak).
15. **`Async\signal(…, $t)` leaves the Timeout armed** (`async.c:1484, 1336-1340`): the cancel
    callback is removed without a stop when the signal arrives; the timer and the reactor
    (`scheduler.c:2017-2018`) stay alive until it fires or `$t` is released.
16. **A closed Thread awaited directly sets no `EXCEPTION_HANDLED`** (`async.c:328-337`): the Thread's
    free rethrows an exception already caught (`libuv_reactor.c:2484-2491`).
17. **TaskGroup readiness is not CLOSED** (`task_group.c:367, 725`): a settled unsealed group with new
    tasks hands a waiter UNDEF.
18. **`start_graceful_shutdown` clears `EG(exception)` in the `shutdown` slot**: on the RFC core this
    crashes at `zend_fibers.c:872-873` (`GC_ADDREF(NULL)`) after `exit()` in a fiber coroutine; the

19. **Pointer queues cleaned as zval queues**: the scheduler ran `zval_c_buffer_cleanup` on pointer
    queues, where each pop leaves the zval UNDEF and releases nothing.
20. **Microtasks counted twice under the RFC rule**: the fork's `add_microtask` adds a reference the
    RFC caller already added.
21. **Exported `zend_std_*` names** from the extension's circular buffer.
22. **Dead `IS_PTR` branch** in `zval_to_event` (`async_API.c:312-313`; no producer).

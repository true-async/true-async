# S10 notes: TrueAsync features beyond the RFCs

Decision note of S10, 2026-10-08. TrueAsync changes the core for more than the two RFCs carry; S10
takes each such feature and proposes one outcome for it: a change to our scheduler RFC (`async-core`),
a request to bukka's IO RFC (php/php-src#23997), an upstream php-src fix, an extension-level design, or
"not in the first version". A private core patch is not among them (P1.1). Edmond answered section 11 on
2026-10-08: the proposals stand, except output buffers, which are not built (`DECISIONS.md` 2026-10-08).

Sources: the fork's core `true-async/php-src` `true-async` `829cde6d4b5` (below `F:`), its own changes
taken as the diff from its php-src base `a7b265ca611b`; TrueAsync's extension at `tests/lists/REFERENCE`
`1fdacf8` (below `R:`); the pinned core `async-core-io-2026-10-08-2` `d3681ac7d41` (below `P:`). All of
it was read, not run, unless a line says otherwise; counts of tests are counts of files.

## 2. Per-coroutine output buffers

**TrueAsync.** `main/output.c` replaces all 95 `OG()` uses with `ASYNC_OG()`, which looks the stack up in
the current coroutine's internal context under one key and falls back to `OG` when the coroutine has
none (`F:main/php_output.h:131-174`, `F:main/output.c:39`). A coroutine gets its context at its first
`ob_start()` (`F:main/output.c:613-618`); when main starts, a start handler moves the handlers already in
`OG` (those of `output_buffering` and `output_handler`) into main's context (`1663-1706`); a finished
coroutine's buffers are flushed by `php_output_end_all()` in its finish callback, which makes the
finished coroutine current for the call (`1708-1731`). Effects: a coroutine without its own
`ob_start()` writes past main's buffers straight to the SAPI (`output_buffer/001` expects this); main's
buffers are flushed when main finishes, before the shutdown functions; the output flags and the "output
started at" location are per coroutine. Size: about 380 lines in `output.c` and `php_output.h`. With the
extension loaded main and every Fiber are coroutines, so the lookup runs 6-9 times per `echo` of every
script (counted in the code, not measured); resolved once per entry point it would be 1-2.

**Pinned core.** It has the storage the RFC names for exactly this case: the internal context in
`zend_coroutine_t` (`P:Zend/zend_async_API.h:144`, `547-555`, `617-625`) and finish handlers
(`690-693`); `main/output.c` is unchanged. The RFC uses output buffering as the worked example of the
internal context and leaves the conversion of `ob_start()` to follow-up work (`scheduler_rfc.md:96`,
`514-517`, `696`). The INI handlers start in `php_request_startup()` (`P:main/main.c:1881-1888`), before
the scheduler is launched (`2609`). The engine never chooses the current coroutine
(`scheduler_rfc.md:226-228`), which TrueAsync's finish-time flush does.

**Two models.** In PHP without the extension one stack serves the request. TrueAsync's model is
*bypass*: a coroutine's levels are its own, and its output with no level of its own goes to the SAPI,
past main's levels. The alternative, *write-through* (a coroutine's output continues into its parent's
levels), is no port: `php_output_op()` ends at `sapi_module.ub_write` (`P:main/output.c:1124-1138`), so
it needs a chain of stacks through every PHPAPI entry point of `output.c`, rules for what
`ob_get_level()` and `ob_end_clean()` see in a coroutine with no levels, and a guard for main's user
handler that suspends while a child writes into it (the child's text is appended to the running
handler's buffer and dropped, `P:main/output.c:944-946`, `1078`). Write-through is not proposed.

**Fibers.** The RFC's goal 4, "existing Fiber-based code keeps running unchanged" (`scheduler_rfc.md:72-76`),
is an RFC rule (P2.1): `ob_start(); (new Fiber(fn() => print "x"))->start(); ob_get_clean()` returns `"x"`
without the extension, and a level a fiber opens before `Fiber::suspend()` is its caller's. So a Fiber's
coroutine never gets a stack of its own: it uses the stack of the coroutine waiting for it
(`fiber->caller_coroutine`, followed while that is a fiber too), main's when it has none (a graceful exit
of a dropped fiber, a fiber the deadlock closes). In coroutine mode `start()` and `resume()` only queue
the fiber (`P:Zend/zend_fibers.c:990-1016`, `1084`), so the stack is chosen when the fiber runs, not when
it is resumed. A level a fiber leaves open on X's stack stays there when Y resumes it later, as with one
stack. TrueAsync gives fibers their own stack; this is a departure by P2.1.

**Options.** P1.1 forbids a private core patch: a core change is an RFC change, an upstream fix, or waits.
- (C) The extension keeps a spawned coroutine's stack (`handlers`, `active`, `running`) in named fields of
  its coroutine. Invariant: `OG` holds the stack of the owner of the current coroutine, where main and the
  scheduler coroutine are owned by main, a spawned coroutine by itself, a fiber as above. One helper
  swaps the stack at every assignment of the current coroutine (`make_current()`,
  `make_scheduler_current()` in `src/scheduler.c:317-332` and the direct writes), with a debug assertion
  of the invariant. `output_globals` is `PHPAPI` (`P:main/php_output.h:140`, with a caution at `142`).
  The flags and the "output started at" location stay request-wide, so `headers_sent()` and zlib's check
  keep their meaning (TrueAsync makes them per coroutine: a departure). A coroutine's leftover levels are
  flushed at the end of its body, inside the coroutine; after a fatal error they are flushed too, as
  `php_request_shutdown()` flushes main's (`P:main/main.c:1954-1956`), so the message is not lost; main's
  levels are flushed at request shutdown, as without the extension. Cost: two copies of 40 bytes per
  switch between owners, nothing per write. A mechanism TrueAsync lacks, recorded with its reason
  (P1.4): TrueAsync's own is a core patch P1.1 forbids. The upstream follow-up the RFC promises
  (`scheduler_rfc.md:696`) can replace it with no visible change.
- (A) An RFC change on `async-core` with TrueAsync's mechanism, bypass and the fiber rule above: it moves
  an item out of the RFC's Future Scope (`scheduler_rfc.md:96`, `514-517`, `696`) of a public RFC under
  review, with the RFC text, core tests over `test_scheduler` and a push to php/php-src#22561 on
  Edmond's word; a lookup per write of every script.
- (D) Wait for the upstream follow-up: meanwhile a template rendered inside `ob_start()` that suspends
  takes another coroutine's output.

**Edmond's answer: not built** (2026-10-08, «можно не делать ваще»); `output_buffer/001`-`006` stay
excluded. The proposal was C (the Sage's ruling, 2026-10-08), with bypass for spawned coroutines and fibers on the
stack of the coroutine waiting for them. Bypass has a cost Edmond sees before choosing, as with
TrueAsync: a spawned coroutine's output skips the handlers started from the INI before the launch
(`P:main/main.c:1881-1888`), so under `zlib.output_compression` its text goes out uncompressed and under
`output_buffering=4096` its first `echo` sends the headers. Our tests by reading: `io_provider/006`
(`spawned` before `main`), `io_provider/011` (the fatal error before main's buffered lines) and
`scheduler/053` (the coroutines' lines before `main end`) change order; `scheduler/031` and `072` keep
theirs; each change goes to Edmond (rule 4) after a run. The reference `output_buffer/001`-`006`
keep their expectations. A design note of its own, reviewed before code, would settle: an exception
pending at the body's end set aside during the flush (`src/coroutine.c:367`, `418`); the lock error
deactivating output for the request (`P:main/output.c:766-769`) and the stacks it leaves to free; output
written by the scheduler while main is parked inside its own user handler (`944-946`); the handler zvals
of saved stacks reported to the GC. `output_buffer/007` and `008` need only S6 (proc_open, file IO): S10.2
lists them in `S6.txt`.

## 3. `Fiber::getCoroutine()`

**TrueAsync.** A core method (`F:Zend/zend_fibers.stub.php:29`, `F:Zend/zend_fibers.c:1963-1975`)
returning the fiber's coroutine object or null; the fork creates the coroutine with the Fiber object
(`F:Zend/zend_fibers.c:1291-1327`), so it returns one before `start()` too.

**Pinned core.** The link is there: `fiber->coroutine` (`P:Zend/zend_fibers.h:148`), set at `start()`
and kept after the fiber ends. The RFC defines no PHP-visible names (`scheduler_rfc.md:44-46`): the
provider does.

**Tests.** 019 and 026 read the coroutine after `start()` and after the end; 023, 024, 027, 028 cancel it
and resume the fiber; 025 cancels its parent before the parent runs, so its fiber code never runs, and
S10.4 adds an own test that cancels the coroutine of a suspended fiber, then its parent. None calls the
method before `start()`. The cancellation path is ours: `fiber/024` with the coroutine taken by
`Async\current_coroutine()` inside the fiber instead of `getCoroutine()` prints its expected output
(pocs-dbg, 2026-10-08); only the accessor is missing.

**Options.**
- (A) A function `Async\fiber_coroutine(Fiber $fiber): ?Coroutine`: about 20 lines; the 7 tests change.
- (B) The extension patches the core class: `getCoroutine()` added to `zend_ce_fiber`'s function table at
  MINIT with `zend_register_functions()` and hand-written arginfo (`gen_stub` cannot declare a method of
  another module's class), removed at MSHUTDOWN (module shutdown runs before the class table goes,
  `P:Zend/zend.c:1183`, `1190`). About 40 lines; the tests run unchanged. If PHP or another extension
  already defines the name, the extension leaves it and logs a notice instead of failing MINIT.
- (C) A core method: against the RFC's rule of no PHP names.
- (D) None: the tests capture `Async\current_coroutine()` inside the fiber body.

**Proposed: B**, TrueAsync's API (P2.2) with no core change; like option C of section 2 it writes core
state through an exported API (the Sage, 2026-10-08), with its reason recorded. Departure: null before `start()` (no reference test checks it).

## 4. The `zend_sigaction` hook and signals

**TrueAsync.** `zend_sigaction()` asks `zend_async_sigaction_fn(signo)` and, when the reactor owns the
number, skips the OS install (`F:Zend/zend_signal.c:248-256`). libuv replaces Zend's OS handler and
forwards each delivery into `SIGG(handlers)` (`R:libuv_reactor.c:1383-1403`, `1566-1614`); without the
hook a `pcntl_signal()` would reinstall Zend's handler over libuv's.

**Pinned core.** A `SignalHandle` owns a number by keeping it blocked; Zend's OS handler stays and must
stay, since `signal_forward()` calls `SIGG(handlers)` (`src/os_signal.c:227-250`). The only wrong step is
the unblock in `zend_sigaction()` (`P:Zend/zend_signal.c:260-263`). bukka's `bdfa5fa7a12` covers pcntl:
`pcntl_signal()` blocks a watched number again (`P:ext/pcntl/pcntl.c:700-715`, `913-918`),
`pcntl_sigprocmask()` filters it out (`1043-1057`). A hook in the scheduler API would be a second owner
beside the handle's own count and record (`P:ext/standard/io_poll.c:997-998`) and would not cover a
script's own `SignalHandle`.

**Left open** (RFC-CHANGES 5, "Still open"):
- (a) Unblocks bdfa5 does not cover: the instant between the unblock and pcntl's block again inside
  `pcntl_signal()`; pcntl's request shutdown (`P:ext/pcntl/pcntl.c:242-246`), harmless only while our
  RSHUTDOWN runs first (module order not checked); phpdbg and third-party callers. Our
  `async_signal_reblock()` covers them before the next poll.
- (b) pcntl swallows the script's unblock of a watched number without recording the block as the
  handle's, so after the watch the number stays blocked and a `pcntl_signal()` handler for it no longer
  runs; `signal/031` expected that (`changed:2026-10-08`). The S6.9 fix (`reblocked`) prevented it.
  Fixed in S10.3a: `signal/031` expects the unblock after the watch.
  Run in S10.3 on `async-core-io-2026-10-08-2`: confirmed (a later `SIGUSR1` killed the process, exit
  code 138), and a block during the watch is undone by the last removal too. The fix is S10.3a.
- (c) `signal_watch_free()` unblocks a number another `SignalHandle` of the thread still watches
  (`src/os_signal.c:298-306`). `php_io_poll_signal_watched_mask()` is a PHPAPI of the pinned core
  (`P:ext/standard/io_poll.h:55`), so the extension can ask before unblocking. Settled in S10.3a: the
  core's count decides the unblock (`signal/035`).
- (d) A watch needs an `Io\Poll\Context` never waited on: a poll backend per thread, nothing broken.

**Proposed.** No hook in the scheduler API (a departure from TrueAsync: in the pinned core a number is
owned by the handle's mask, not by the OS handler). Instead one request to bukka replacing what is left
of RFC-CHANGES 5: a hook in `Zend/zend_signal.c` that `ext/standard` fills, so `zend_sigaction()` (and
`pcntl_sigprocmask()`) leaves a number a live `SignalHandle` watches blocked; that makes pcntl's own
block and our `async_signal_reblock()` unnecessary. Whether the request also records such a block as
the handle's follows the question asked after S10.3's run (section 11). (d) goes into the same request as a second, optional
part; (c) is settled in S10.3a through the core's count (`signal/035`).

On (b): Edmond 2026-10-08 18:02, «если это баг... может поправить? дай мудрецу глянуть», 18:06
«ок сделай я потом рассмотрю». 19:22, «я бы шёл по малопу пути. пока вообще не трогать маску»: `$old`
stays the real mask, and bukka's filter is fixed only where it drops the script's request. S10.3a
(`signal-unblock-at-removal` on bukka's `566a6833eb5`): pcntl records the script's unblock of a number
it blocked before the watch (`php_io_poll_signal_unblock_at_removal()`), the last removal does it, and
a later block by the script takes it back (`php_io_poll_signal_keep_blocked_at_removal()`; Edmond
19:46, «ок сделай пока так»). The extension's `async_signal_reblock()` records a `zend_sigaction()`
unblock through `php_io_poll_signal_reblocked()`, which no script request takes back, as the
`reblocked` record did; that record is gone, which settles (c). Left to bukka as questions: an
unblock followed by a save-and-restore ends blocked, and a block during the watch of a number the
handle blocked itself is undone by the last removal, as before; both need the script's mask in
`$old`. The script-mask variant of 18:17 (patches in `/mnt/project-files/notes/s10/signal-fix/`) is
not used.

## 5. PDO pool

**TrueAsync.** `PDO::ATTR_POOL_ENABLED`, `_MIN`, `_MAX`, `_HEALTHCHECK_INTERVAL`, `_STMT_CACHE_SIZE` and
`PDO::getPool(): ?Async\Pool` (`F:ext/pdo/php_pdo_driver.h:131-136`, `F:ext/pdo/pdo_dbh.c:914-930`).
The user's PDO becomes a template; each coroutine is bound to a separate `pdo_dbh_t` from the pool for
one call, or longer while a statement, a transaction or session state holds it; a finished coroutine's
transaction is rolled back; a broken connection is replaced; mysqlnd resets a reused connection with
`COM_RESET_CONNECTION`. Size: `ext/pdo` about 1,600 lines (`pdo_pool.c` 985), the mysql, pgsql and
sqlite drivers about 800, dblib, firebird and odbc about 50, a pool type and 6 slots in the core API
(`F:Zend/zend_async_API.h:2129-2160`, `2713-2721`) over `R:pool.c` (1,678 lines); `PDO_DRIVER_API`
changes and `query_stmt` is renamed (ABI).

**Pinned core.** Vanilla `ext/pdo`; no pool type. The per-coroutine side it needs exists (current
coroutine, finish handlers, internal context). A pool without `ext/pdo` changes cannot work safely:
drivers read `dbh->driver_data` again after their IO (`P:ext/pdo_mysql/mysql_driver.c:42-62`), so
swapping it per coroutine hands a suspended coroutine's driver another connection.

**Options.** (A) Port as is, with a pool API in the scheduler RFC: about 2,900 lines in php-src, an ABI
break, against the RFC's scope (`scheduler_rfc.md:699`). (B) Hooks in `ext/pdo` by a PDO RFC (a
connection resolver, `stmt->pooled_conn`, per-binding error state, `conn_broken`, `H = S->H` in driver
error paths), the pool logic in our extension over S9's `Async\Pool`: about 1,000-1,200 lines in
php-src. (C) An extension pool with explicit acquire over `Async\Pool`: no php-src change, another user
API, every pool test rewritten. (D) Not in the first version. **Proposed: D**, with B recorded as the
path afterwards; S9's pool layer comes first either way.

## 6. pgsql and pdo_pgsql

**TrueAsync.** Both drivers send with `PQsend*` and `PQflush`, then wait on `PQsocket()` through a socket
event of the core (`ZEND_ASYNC_NEW_SOCKET_EVENT`); only `pg_query()` and `pg_query_params()` in
`ext/pgsql` (connect, prepare and COPY still block); no handling of cancellation or of one connection
used by two coroutines. Size: `ext/pgsql/pgsql.c` +207/-18, `ext/pdo_pgsql` about 225 lines of IO (the
rest is the pool). `pdo_sqlite` and `mysqlnd` change only for the pool.

**Pinned core.** libpq does its own socket calls, outside the IO hooks. The wait a driver could use
exists: `php_io_poll(NULL, fd, events, &deadline)` (`P:main/php_io_hooks.h:296`), which our provider
serves. CI builds no pgsql and starts no PostgreSQL server.

**Proposed: not in the first version**, and no PostgreSQL fixture in CI until then. Afterwards
`ext/pgsql` and `pdo_pgsql` wait through `php_io_poll()`: about 600-800 lines with cancellation and a
guard against two coroutines on one `PGconn` (mysqlnd's guard is stream-based,
`P:ext/mysqlnd/mysqlnd_connection.c:2342-2347`, and does not apply). Driver code is neither RFC's, so
the proposal is our own php-src PR once the IO hooks RFC is merged, not a widening of bukka's RFC.
`pdo_pgsql/001`-`004` need no pool; they stay excluded with this reason until then.

## 7. Threads

**TrueAsync.** `spawn_thread()`, `Thread`, `ThreadPool` (with `coroutine: true` and `reload()`),
`ThreadChannel`, a `FutureState` sent to another thread (`R:thread.stub.php`, `thread_pool.stub.php`,
`thread_channel.stub.php`, `R:future.c:752-832`, `1956-2424`). Each thread runs a full PHP request in a
new TSRM context; values are deep-copied, closures as copied op_arrays (`R:thread.c:43-723`,
`2295-2760`), mirroring the private `zend_closure` struct (`2277-2286`); an internal object without a
transfer handler arrives empty with no error (`1176-1181`). About 8,300 lines in the extension. The
core adds `transfer_obj` to `zend_object_handlers` (`F:Zend/zend_object_handlers.h:186-201`),
WeakReference and WeakMap transfer (`F:Zend/zend_weakrefs.c:815-985`), `sapi_module.thread_init`
(`F:main/SAPI.h:292`), a drain of child threads at module shutdown (`F:main/main.c:2474`), 64-bit and
pointer atomics, and thread slots in the API.

**Pinned core.** No thread API; the scheduler RFC introduces no parallelism (`scheduler_rfc.md:30-32`,
`104`). Our `async_trigger_fire()` already wakes a thread's loop from any thread (`src/reactor.h:47-70`).

**Proposed: not in the first version.** The follow-up is an extension-level design (as ext/parallel is
built) with three small core needs: a drain point at module shutdown, `thread_init` for Windows, and
WeakReference transfer; `transfer_obj` for other extensions' objects only if Edmond wants them
transferable. `signal/008`, `009`, `012` also need a process-wide signal owner, a request to bukka's IO
RFC (masks and counts are per thread, `P:ext/standard/io_poll.c:987-998`); until then `Async\signal()`
outside the main thread of a threaded CLI (ext/parallel) is not refused, since the core refuses a
`SignalHandle` by SAPI name only (`1255-1263`): a known gap until threads come, with no test path
before a thread API exists.

## 9. Found by the inventory

The inventory sorted every other core change of the fork (`F:` diff): most are in the pinned core
(GC and shutdown destructors in coroutines, sleep, DNS, curl, sockets, TLS IO, `stream_select()`,
`proc_open()`, fibers in coroutine mode), dropped by a decision (`\Cancellation` D8, the acting
coroutine and `zend_alloc_pop_is_oom`, `dev/plans/S3.md:1205-1206`), or debug tooling (libbacktrace,
`zend_mm_dump_live_allocations()`). Not named by any stage:

- **HTTP wrapper headers leak.** `php_stream_url_wrap_http()` releases `BG(last_http_headers)` before
  the request and copies the new headers over it after (`P:ext/standard/http_fopen_wrapper.c:1280-1288`);
  a request that runs while another waits overwrites the first one's array without releasing it. The
  IO hooks' suspend is one way; a `notification` callback that calls `file_get_contents()` is another,
  with no extension loaded (the wrapper notifies during the header parse, `335`). So the bug is
  php-src's: a test without the extension, the fix on `php-src-fixes` with its own PR branch (the fork's
  `829cde6d4` fix is one line), after checking that `PHP-8.4` has `BG(last_http_headers)`. Merging it is
  a core update. S10.3: fixed on `php-src-fixes`, PR branch `http-last-response-headers-leak`; the
  reproducer is a notification callback, red on `PHP-8.4` debug without the fix.
- **FileSystemWatcher** (`R:fs_watcher.stub.php`, 13 tests; a filesystem event slot in the fork's core).
  On Linux and macOS an inotify or kqueue descriptor can be waited on with `php_io_poll()` from the
  extension (not checked); Windows needs a directory-change op in the IO hooks and ior. Proposed: a
  new S9 layer, with Windows as a request to bukka.

# S7 notes: the collector of coroutines that can never wake

Design note of S7.1, 2026-10-06. The collector finds the coroutines of a request that nothing can
wake any more while other coroutines still run or wait for timers and IO (a partial deadlock), and
resolves them by a policy: a warning (the default), the cancellation the global deadlock delivers,
or nothing. It is a pass over the references of the parked coroutines, PHP's trial deletion
(`zend_gc.c`) without the freeing, extended with Go's rule that a parked stack counts only once one
of its wait targets is reachable. TrueAsync has no counterpart: it detects only the global deadlock
(`scheduler.c:749-889`) and, for channels, closes soft-timer channels when the loop has nothing else
to wait for (`docs/channel-deadlock-protection.md`, layer 2); section 9 lists what S7 adds against it.

Sources: the pinned core `async-core-io-2026-10-05-4` `9531d5b0b1f` by path (`Zend/zend_gc.c`,
`Zend/zend_execute.c`, `Zend/zend_fibers.c`, `Zend/zend_types.h`, `Zend/zend_vm_def.h`); the
reference `ext/async` `1fdacf8` by file name; `dev/plans/S3.md`, `S4.md`, `S5.md`, `S6.md` below
`S3.md` and so on; the prior-art review `dev/reviews/s3-structures/prior-art.md` below `prior-art`

## 2. What can wake a parked coroutine

A coroutine parked on a wait ends its park in one of three ways: the target completes (a coroutine
finishes, a `FutureState` completes, a channel gets a value), somebody cancels it or its target
(`Coroutine::cancel()`, `Future::cancel()`, a scope's cancel in S9), or an outside source fires (a
timer, IO, a signal, another thread's trigger). The first two need code that holds the target, the
token or the coroutine: a `FutureState`, a `Future`, a `Coroutine` object, a channel, a scope. So a
parked coroutine can never wake when no outside source is armed for it and no code that can still run
reaches any of its targets or the coroutine itself.

Four ways to reach a coroutine through the registry are left out by design: `Async\get_coroutines()`,
`Async\graceful_shutdown()`, `exit()` with D16's deadline, and the global deadlock. Each of them
cancels every coroutine at once and needs no reference to it; counting them would make every coroutine
reachable, as Go's leak profile would never fire if it counted `allgs`.

The plan's edge "waiter → awaitable → completers" cannot be walked toward the completers: a
`FutureState` does not know who holds it, and a channel does not know its senders (the Critic in
S3.1, `frame-records-critic.md` section 10). Reachability answers the same question from the other
side: whoever can complete or cancel a target holds a reference to it, so a target that no running
code reaches has no completer. That is Go's answer too: the leak profile marks from the roots and
scans a blocked goroutine's stack only once something it waits on is marked (prior-art 13.6).

PHP has no list of roots: an extension may keep a value in its own globals, a resource may hold a
callable, a static property or a constant may hold an object. Trial deletion needs none. PHP's
collector subtracts the references a candidate subgraph holds to itself and keeps whatever still has a
reference left, since that reference comes from outside the subgraph (`gc_mark_grey`,
`zend_gc.c:1073`; `gc_scan`, `:1311`). The collector does the same over the subgraph the parked
coroutines reach: every holder it does not walk counts as live, so an unknown root makes the collector
miss a finding, never invent one.

## 3. The walk

### 3.1 Candidates

The walk starts from the registry (`ASYNC_G(coroutines)`) and takes as candidates the coroutines that
are SUSPENDED with at least one linked record (the waker's two and its block's, `async_wait_walk`),
every one of whose kinds has `collector_target` set (section 4). Everything else is not a candidate,
and the walk treats it as live:

- QUEUED and RUNNING coroutines: they run.
- CREATED coroutines (a core coroutine whose enqueue was refused, S3.md 7 "As built"): they wait for
  nothing.
- A wait with any record of an outside source: TIMER, TIMEOUT, the S6 IO kind, TRIGGER, and every
  kind without `collector_target` (a kind written before it learns S7 is conservative by default).
- A park with no record: `Fiber::suspend()`, a Fiber's caller in `start()`/`resume()`, the GC
  coroutine waiting for destructors (S3.md 4.8). Their edges live on the target side (the fiber's
  caller, a finish handler's waiter), which the walk does not read; Go treats unknown wait reasons the
  same way.
- A Fiber's coroutine (`ZEND_COROUTINE_F_FIBER`), parked on any wait: the `zend_fiber` holds it
  through a pointer the walk cannot count, and while its caller is parked the frame chain of its stack
  continues into the caller's (`zend_fibers.c:1006-1007`).

With no candidate the run ends after the registry scan.

### 3.2 Nodes and their references

A node is anything with a reference count whose holders can reach other nodes: a PHP object, a
refcounted array (immutable ones skipped), a `zend_reference`, and a refcounted event of the extension
(S4.md 2.1, `ref_count`; an event inside its object, `ASYNC_EVENT_F_ZEND_OBJ`, is that object).
Strings and resources hold no node and are never visited. A node's references are what its holder
owns:

| Node | References the walk reports |
|---|---|
| A PHP object of another class | its `get_gc` handler: the table, the count and the returned hash, as `zend_gc.c` reads them |
| An array, a reference | their values |
| A candidate coroutine | its `get_gc` (`src/coroutine.c:208-277`) and its parked stack, frame by frame from the suspended `execute_data` to the coroutine's own bottom frame (below) |
| `Future`, `FutureState` | the `FutureState` object a `Future` holds, the mapper, and the future event as its own node where the object owns a reference to it (section 10) |
| A future event | its result, its exception, the child objects of its `chain` |
| A record of a kind that owns a reference to its target (AWAIT_ITER, S5.md 5) | its target |
| A coroutine that is not a candidate | nothing: it is live, and what it holds counts as held from outside |

The frames of a candidate's stack:

- A user function's frame goes through `zend_unfinished_execution_gc_ex` (`zend_execute.c:5028`),
  which gives its live CVs, temporaries, unfinished calls, extra arguments and `$this`.
- An internal function's frame is read by the collector itself and not passed to that function, which
  asserts that an internal frame has no extra named parameters (`:5043`) while a variadic internal
  function such as `call_user_func()` gets them (`:5566-5569`). It gives `$this` when the call owns
  it, the closure, the arguments and the extra named parameters, all owned by the call until it
  returns; so `await(spawn(...))` counts the coroutine its argument holds.
- A generator's frame is skipped: `zend_generator_frame_gc` is not exported. A frame with no
  function (a generator's `execute_fake`, `zend_generators.c:811`) is skipped before anything reads
  `func`, as `zend_unfinished_execution_gc_ex` returns on it (`zend_execute.c:5030`).
- A symbol table: `EG(symbol_table)` is not reported (below); any other table gives its values once
  per walk, by its address, each `IS_INDIRECT` value read through its CV slot. `include` and `eval` inside a function hand the function's own table to
  the included frame (`zend_vm_def.h:6653-6662`), so two frames return the same table; reporting it
  twice would subtract a reference that a static property or a running coroutine holds.

The core declines to scan a stack parked inside an `await()` for PHP's own collector
(`zend_fibers.c:1267-1270`): that collector frees what it judges garbage, so a slot misread there is a
use after free. This collector frees nothing. A slot it leaves out hides a finding; a slot it reports
must own its reference, which holds for every slot above between the park and the wake, since the
frame changes nothing while it is parked.

Records own no reference to their targets (S3.md 4, invariant F): the waiter's frame does, and the
frame is walked. A record gives the walk a wake edge instead, target → waiter, which section 3.3
reads. The registry's own reference to each candidate is subtracted as one held inside the subgraph
(section 2).

**The global scope is a root.** Main's top frame keeps its variables in `EG(symbol_table)`, which
every coroutine reaches through `global` and `$GLOBALS`; the walk does not report that table, so what
a global variable holds stays live. Static variables, static properties, constants, resources, pending
microtasks and the stacks of running coroutines are never walked, so their references count from
outside.

**Weak references.** An object with `IS_OBJ_WEAKLY_REFERENCED` (`zend_types.h:936`) is live: a
`WeakReference::get()` or a `WeakMap` in running code can still reach it, which its reference count
does not show.

### 3.3 Counting and liveness

1. **The wait graph first.** A candidate with a record whose target is a coroutine that is not a
   candidate is live: that coroutine runs or waits for an outside source, and it can finish. Its
   waiters are then live too, to the fixed point over the wait edges alone. Only the candidates left
   go to the heap walk; a server whose coroutines wait for running workers walks nothing. A candidate
   made live here is a live node when the heap walk meets it: its registry reference is still
   subtracted, and its references are live.
2. **Count.** A depth-first walk from the candidates left, on an explicit stack, visits each node once
   and counts, in a side table keyed by the node's address, the references that nodes of the subgraph
   hold to it. It collects the wake edges of every candidate's records into a second table, target →
   waiters. `get_gc` answers in one buffer per thread (`zend_get_gc_buffer_create`,
   `zend_gc.c:2543-2549`), so each answer is copied onto the walk's stack before the next call.
3. **Seed.** A node is live when its reference count exceeds the references counted inside, when it is
   weakly referenced, when it is a coroutine that is not a candidate, or when an outside source holds
   it (3.4).
4. **Spread.** From each live node, its references are live (the walk calls the same reporters again,
   as `gc_scan_black` walks again, `zend_gc.c:872`), and a live wake-edge target makes its waiters
   live; a live candidate's object and stack are live. A worklist runs it to the fixed point.
5. **Result.** The candidates left are the coroutines that can never wake, each with the targets it
   waits for. The objects only they hold are the rest of the subgraph; they stay until their holders
   unwind (section 6).

The walk changes no reference count and writes no `GC_INFO` colour, so it never disturbs a root
buffered for PHP's own collector; its colours and counts are in its own tables. It is not free of
side effects: `zend_std_get_gc` may separate a shared properties table (`zend_array_dup`), as it does
inside PHP's collector.

A live candidate means that some running code may reach it or its target. A coroutine whose
`Coroutine` object a running coroutine or a global keeps can be cancelled, so it is never reported,
even when the holder never cancels it; a stuck coroutine handed to a supervisor stays unreported until
the supervisor drops it.

### 3.4 Soundness

A reported coroutine has no armed outside source and no reference path from code that can run to it or
its targets. A wrong report needs a reference the walk counted that its holder does not own, or a
completer that holds no counted reference. The rules that exclude both:

- A reporter gives only slots that own a reference (3.2). A slot that cannot be shown to own one is
  left out; its target then counts as held from outside, which hides a finding but reports none.
- **Outside sources are seeded from the reactor's lists.** Every event on the reactor's `waits` and
  `triggers` lists (S4.md 3.4) is live, and so is the node it belongs to: the event itself, or the
  object it is embedded in (a Timeout's timer, S5.4), so a Timeout is live wherever it is linked, as a
  target, an `await_*` item or a token. A source whose completion lands on another awaitable (the
  reactor's `SignalHandle` and the Futures of `Async\signal()` waiting on it, S6.5; S10's remote
  Future) reports the awaitables it will complete, a set it keeps anyway in order to complete them.
  These are the lists that decide the global deadlock, so a source left off them already fails the
  existing deadlock tests; a flag or a reference kept only for the collector could be forgotten with
  nothing failing but the collector. A Timeout item whose timer S5 never arms is stuck in fact, and
  S7.3's test shows it. A scope, a task group and anything else that may cancel coroutines it does
  not hold through PHP values (S9) holds a counted reference to each of them or reports them as live.
  S5, S6 and S9 keep these rules; the Critic checks them per stage.
- No PHP code runs between the count and the result, so no reference changes under the walk; `get_gc`
  handlers run no PHP code (`zend_gc.c` calls them inside the collection).

### 3.5 Cost

The registry scan is one pass over the registry, and the wait-graph pass is linear in the candidates'
records. The heap walk is linear in the nodes and references the remaining candidates reach, twice
(count, spread), with one side-table entry per node, as PHP's collector is linear in the subgraph of
its roots and allocates its own stack for it. A candidate whose stack reaches a large shared structure
(a `$this` that holds the application's container) walks all of it; so does PHP's collector. Section 5
bounds how often the walk runs, and section 11 measures it on 10 000 parked coroutines and on a graph
of one million nodes.

## 4. The kind's slot

S3.md 3.5 reserved a fourth slot, `completers(record, walker)`, for this walk. Section 2 shows that
completers cannot be enumerated, so the slot reports the record's target instead and gets the name of
what it does:

```c
struct _async_wait_kind_s {
	zend_string *(*info)(const async_coroutine_event_callback_t *record);
	void (*unlink)(async_coroutine_event_callback_t *record);
	void (*abort)(async_coroutine_event_callback_t *record);
	/* Reports the record's target to the collector as a node, and whether the record owns a
	 * reference to it: whoever reaches the target can end the wait. NULL: an outside source may end
	 * the wait, and the waiter is not a candidate. */
	void (*collector_target)(const async_coroutine_event_callback_t *record, async_collector_t *collector);
};
```

The kind table stays one const table per kind in `.rodata`; nothing on a wait's path reads the slot.

| Kind | Stage | `collector_target` |
|---|---|---|
| COROUTINE | S3 | the target coroutine's object |
| TIMER, TRIGGER, the test kinds | S4 | NULL |
| FUTURE | S5 | the future event, owned: the wait holds one reference from `await()`'s C frame (`src/future.c:703`, S5.2) |
| CANCELLATION | S5 | the token: a coroutine's object or the future event |
| AWAIT_ITEM | S5 | the item; owned when S5 keeps one per item (section 10) |
| AWAIT_ITER | S5 | the item, owned |
| TIMEOUT | S5 | NULL |
| IO | S6 | NULL |
| CHANNEL | S9 | the channel's object; a channel with no holder but its receivers is the plan's "channel without senders" |

A block's records come through its `walk` op (`src/true_async_API.h:322-326`), which S4.2 added for
this walk.

## 5. When it runs

- **At the idle point.** `scheduler_loop` (`src/scheduler.c:845`) reaches the reactor's idle wait when
  nothing is runnable and some wait has an outside source (`src/scheduler.c:862`). Before it blocks,
  the collector runs when its interval passed since its last run, on the coarse clock of the tick's
  throttle (`src/reactor.c:305`). The interval starts at `true_async.partial_deadlock_interval`
  milliseconds, doubles after each run that found no coroutine without `ASYNC_COROUTINE_F_DEADLOCK_REPORTED` up to
  64 times that value, and returns to it after a run that found one: under `report` the stuck
  coroutines stay candidates, so a run finds the old ones again, and only new ones count. PHP's collector raises its own threshold when a run collects
  little (`gc_adjust_threshold`). The time of the last run and the current interval are two fields of
  `ASYNC_G`, read only at the idle point. A run that cancelled anything enqueued its coroutines, and
  the loop goes on instead of blocking. A program that never idles runs it only on demand.
- **On demand.** `Async\get_deadlocked_coroutines()` runs the walk in the calling coroutine and returns
  the stuck coroutines. It refuses in scheduler context and with async off, as `spawn()` and
  `get_coroutines()` do (`THROW_IF_UNAVAILABLE`, `src/true_async.c:197`): an error or output handler
  run during a tick has a SUSPENDED current coroutine with records linked. It applies no policy and
  works with the setting `off`.
- **The global deadlock stays as it is.** With nothing runnable and no outside source the scheduler
  resolves a deadlock as TrueAsync does (S3.md 6); every parked coroutine is stuck then, and the walk
  would add nothing.

Rejected:

- **With PHP's collector** (replacing `gc_collect_cycles`, `zend_gc.c:254`): it runs on the root
  buffer's fill (10 000 possible roots), which says nothing about waits, so a server idle on IO with
  one stuck coroutine might never run it; the pointer is process-wide and profilers replace it too.
- **At every park.** A park is the hot path (B1, B4); the walk is linear in the parked subgraph.
- **At every idle without a bound.** A server reaches the idle point after every IO completion that
  leaves nothing runnable.
- **A cap on the walk's nodes.** A capped run would report nothing on exactly the large graphs where a
  stuck coroutine is hardest to find by hand; the back-off bounds the cost instead, and the side table
  grows with the graph as PHP's collector's buffer does.

## 6. Policy

`true_async.partial_deadlock` (`PHP_INI_ALL`) decides what an automatic run does with each stuck
coroutine:

- `report` (default): one `E_WARNING` per stuck coroutine, "Partial deadlock: coroutine #%u spawned
  at %s:%u can never wake (%s)", the last field its first awaiting-info line (S4.md 2.4). Once per
  coroutine: bit 22 of the flags word, `ASYNC_COROUTINE_F_DEADLOCK_REPORTED`, is set by the warning and
  never cleared, since a stuck coroutine stays stuck. The bit gates the warning only. The coroutines stay parked, so when the rest of
  the request finishes the global deadlock resolves them as in TrueAsync, with its `DeadlockError`.
- `cancel`: the warning (once), then every stuck coroutine is cancelled with
  `AsyncCancellation("Deadlock detected")`, protection cleared, as the global deadlock cancels each
  waiter (`scheduler_resolve_deadlock`, TrueAsync's `scheduler.c:860-879`); no exit exception, since
  the rest of the request goes on. Each run that finds a coroutine cancels it, so one that catches the
  cancellation and parks on another dead target is cancelled again.
- `off`: no automatic run.

The warning is raised in scheduler context, where the global deadlock report is written too, and
only when `error_reporting` read from INI includes `E_WARNING`, as the deadlock report reads it
(`ini_error_reporting()`, `src/scheduler.c:750-751`): the scheduler's stack has its own copy of the
setting. An exception an error handler throws (a framework turning warnings into `ErrorException`) is
released: no PHP code called what warned, so nothing could catch it, and joining it to the exit
exception would end a long-running request on its first finding. An error handler that waits gets the
scheduler-context `Error`, released the same way.

**Why `report` is the default.** TrueAsync never resolves a partial deadlock: its stuck coroutines
wait until the global deadlock, and a long-running server keeps serving (P2.2). A warning changes no
outcome and is what the leak profile Go ships gives (prior-art 13.6). `cancel` is opt-in.

**Why a cancellation, not `DeadlockError`.** The plan named `DeadlockError` thrown into the waiters.
A stuck coroutine is by definition one nobody holds, so a `DeadlockError` it does not catch meets the
unobserved-exception rule of its finalize (`src/coroutine.c:454-461`), becomes the exit exception and
cancels every other coroutine: a server would stop on its first finding. The global deadlock already
splits the two the same way, `DeadlockError` for the request and `AsyncCancellation` for each waiter;
`cancel` takes the second half.

Every stuck coroutine is cancelled in the same run, as the global deadlock cancels every waiter. One of
them may hold, in a `finally` block, what would have woken another (a `FutureState` completed while it
unwinds); the other is cancelled even so, as in the global deadlock. Cancelling only the coroutines
whose targets no other stuck coroutine holds was rejected: it needs a reachability pass per stuck
coroutine, and two coroutines each holding the other's target would be skipped forever.

What the stuck coroutines alone hold (a `Future` whose `FutureState` is gone, a channel with no sender)
is released by reference counting as `cancel` unwinds their stacks; under `report` and `off` it stays
until the global deadlock or the request's end, as today.

## 7. PHP's collector

PHP's collector never frees a parked coroutine: the registry holds a reference it cannot explain, and
the coroutine's `get_gc` leaves the parked stack out (`src/coroutine.c:272-273`), so two coroutines
awaiting each other, and everything their frames hold, stay until the request ends. The core walks a
Fiber's stack only when it is parked in `Fiber::suspend()` (`zend_fibers.c:1267-1305`), and not inside
an `await()`. The collector finds exactly those cycles and frees nothing itself: `cancel` unwinds the
frames, and reference counting and PHP's collector then free what they held. The two never run at
once: the collector runs at the idle point or in a PHP function, PHP's collector in its own coroutine,
and neither runs PHP code while it walks.

## 8. PHP API

```php
namespace Async;

/** The coroutines nothing can wake any more (dev/plans/S7.md); the walk runs now. */
function get_deadlocked_coroutines(): array {}
```

It returns a list of `Coroutine` objects in registry order; holding the list makes them reachable, so
the next run does not report them again until the caller drops it, and the caller may cancel them. INI,
both `PHP_INI_ALL`:

| Setting | Default | Meaning |
|---|---|---|
| `true_async.partial_deadlock` | `report` | section 6 |
| `true_async.partial_deadlock_interval` | `1000` | milliseconds before the first automatic run and between runs, before the back-off; `0` runs at every idle point, without back-off (tests, fuzz) |

The names follow `get_coroutines()` and `true_async.debug_deadlock`; TrueAsync has none of them.

## 9. Against TrueAsync

| What | TrueAsync | S7 | Why |
|---|---|---|---|
| Partial deadlock | not detected: a stuck coroutine waits until the global deadlock or the request's end | found by the walk; a warning by default, a cancellation by setting | the plan's S7 goal; global detection sees nothing while one timer or socket is armed |
| Channels | soft per-channel timers (5 s) and a closing pass when the loop has nothing else to wait for (layer 2) | S9 ports layers 1 and 3 with channels; a receiver with no possible sender is S7's finding | the walk needs no timer and works while other waits are armed; S9 decides layer 2 against it |
| Global deadlock | `DeadlockError` exit, every waiter cancelled | unchanged | |

S7 is a mechanism TrueAsync lacks (P1.4): it adds a kind slot, two `ASYNC_G` fields read at the idle
point, two INI settings, a flag bit and a function, and no counter, `zend_try` or work on the wait
path. Its correctness is checked by the tests of section 11 and by the fuzz oracle there.

| S9 | CHANNEL's `collector_target`; a Scope and a task group hold a counted reference to each coroutine they may cancel, or report them as live (TrueAsync's scope keeps a bare pointer, `scope.c:47`) | with each layer |

**Which references to the future event exist** is fixed against S5's code in S7.3, before its
reporters are written, since the notes read two ways: S5.md 2 says a waiter and a drain hold references
to the event, while S3.md 4 invariant F says the waiter's frame keeps the target alive; S3.md 4 says
one `Z_ADDREF` per `await_*` item, while S5.md 5 says the input array keeps the items. S5.2's code
settles the first: `await()` on a Future holds one reference to the event in its C frame for the whole
wait (`src/future.c:701-703`), which the FUTURE record reports as owned. The rule for
each: a reference that S5 holds from C is reported exactly once, by the holder the walk reaches (the
FUTURE record as owned, a `FutureState` object for its event); a reference nobody holds is not
reported. `new Future($state)` holds the `FutureState` object and no reference to the event (S5.md 2);
a child of `map()` and the Future of `completed()` hold the event themselves. S7.3 writes the table of
these holders into this section.

# S6 notes: the IO hooks provider

Design note of S6.2, 2026-10-06. S6 installs the extension as the core's IO hooks provider: the
core's blocking wrappers (`php_io_recv`, `php_io_read`, `php_io_poll`, `php_io_sleep`,
`php_io_waitpid`, `php_io_sigwait`, `php_io_getaddrinfo` and the others) hand their op to the
provider's `run()`, which submits it to the reactor's queue of `dev/plans/S4.md` and parks the
current coroutine until the completion. S6 also adds `Async\signal()`. Names and behaviour come
from TrueAsync (`ext/async` at `tests/lists/REFERENCE`, `1fdacf8`, file names alone below; the fork
core `true-async/php-src` `863f6dd90cf` below `F` with its path); a departure is listed in section
11.

Sources: the pinned core `async-core-io-2026-10-05-4` `9531d5b0b1f`: `main/php_io_hooks.h` below
`H:`, `main/io/php_io_hooks.c` below `Hk:`, `main/io/php_io_queue_poll.c` below `P:`,
`main/io/php_io_ring.c` below `Rg:`, `ext/standard/io_poll.c` below `Ip:`, `ext/standard/io_hooks.c`
(the userland bridge provider) below `Br:`, other files by path. `dev/plans/S4.md` below `S4.md`, the
IO hooks review `dev/reviews/io-hooks-design-review.md` by item (B1, B3, M1, M2, M10-M13). The test
counts of section 12 were measured; nothing else in this note was built.

The Critic's round and the Sage's rulings changed section 2 (two install triggers instead of the
launch, flags set where the queue is created), 3 (the `in_flight` copy-back, a completed op returns
its result under a pending exception), 6 (files stay synchronous), 9 (overlapped pipes on both
paths), added section 13 and split the steps into S6.3-S6.9.

## 1. What S6 implements

| Kind | In S6 | Later |
|---|---|---|
| Provider | `php_io_hooks` installed per request and thread at the first coroutine other than main or at the reactor queue's creation; `run()`, `add()`, `remove()`, `dtor()` | |
| Ops | every `php_io_op_type` the reactor's queue accepts: POLL, TIMER, READ, WRITE, RECV, SEND, ACCEPT, CONNECT, GETADDRINFO, GETNAMEINFO, FSYNC, WAITPID, SIGWAIT, ANY | Flock: no op in the core (M10) |
| Waits | the IO kind: one record per parked `run()`, its target an IO event of S4.md 3.2 holding a copy of the op | |
| Functions | `Async\signal(Signal $signal, ?Completable $cancellation = null): Future` and the `Async\Signal` enum (`async.stub.php:290-316`) | |
| Core | Windows pipes as overlapped named pipes (section 9), one commit on the next `async-core-io` branch | the RFC changes of section 14 |

## 2. Install point

The provider is one struct per thread in `ASYNC_G(io_provider)`, the core's `php_io_hooks`
embedded first, found by `ZEND_CONTAINER_OF` (`H:225-229`). It is installed with
`php_io_hooks_register()` at the first of two events of a request, and removed with
`php_io_hooks_register(NULL)` in the extension's RSHUTDOWN, before the reactor's queue is destroyed
(S4.md 3.7):

- **the first coroutine other than main**: `Async\spawn()` (`src/true_async.c`), the core's
  `new_coroutine` slot for other extensions (`scheduler_new_coroutine()` in `src/scheduler.c`) and
  `scheduler_intercept_fiber()` (a `Fiber`), not their common `async_coroutine_new()`, which the
  launch also calls to adopt main (`main_coroutine_adopt()`), nor the engine's coroutines for a GC
  run and the shutdown destructors, which take the `gc_new_coroutine` slot (S6.8; before it the core
  fell back to `new_coroutine` and a script's first `gc_collect_cycles()` installed the provider,
  `io_provider/019`). The interrupt coroutine of S4.3 (`scheduler_interrupt_start()`) starts only
  while the reactor waits, so the queue and the provider exist by then;
- **the creation of the reactor's queue** in `reactor_queue()` (`src/reactor.c`, S4.md 3.1) at the
  first submit: the first timer, signal or IO wait, so `delay()`, `timeout()` or `Async\signal()` in
  a script that never spawns.

TrueAsync turns its IO on at the same moments: its scheduler launches lazily from
`SCHEDULER_LAUNCH` in `spawn`, the `await*` functions, `delay`, `timeout`, `signal` and `iterate`
(`async.c:172-1384`), and its stream code takes the async path only after that
(`ZEND_ASYNC_IS_OFF`, F `main/streams/plain_wrapper.c:237, 547`). Our core launches the scheduler
before every script (`main/main.c:2606`, `Zend/zend_async_API.c:733-756`), so the launch itself is
too early: a provider installed there would make every blocking wait of a plain script go through
`run()` and create a registration record per stream pair (`Hk:272-329`). Spawn alone is too late:
`Async\signal(...); fgets(STDIN);` in main would not park, where TrueAsync parks it. Both triggers
are cold: one flag test per coroutine creation and one per queue creation.

- **Per request.** `PHP_RINIT(basic)` clears `FG(io_hooks)` (`ext/standard/basic_functions.c:432-442`),
  so a provider installed in MINIT does not survive into a request. The core removes the provider
  itself in `php_io_hooks_request_shutdown()`, basic's RSHUTDOWN (`Hk:451-502`); ours runs before it,
  since modules shut down in the reverse order of registration (`Zend/zend_API.c:2598`).
- **Per thread.** `FG()` and `ASYNC_G()` are thread globals under ZTS (`ext/standard/file.h:123-125`),
  so each thread's request has its own provider and queue.
- **Refused install.** `php_io_hooks_register()` fails while a userland provider from
  `Io\Hooks\set_hooks()` is installed (`Hk:396-428`). The request goes on and its IO stays the user's
  provider's: one provider per request is the core's rule. The refusal is retried at the next
  trigger, so the provider takes over at the first trigger after the user's one is removed. With the
  two triggers this case is real: a script may call `Io\Hooks\set_hooks()` before its first spawn.
  `Io\Hooks\set_hooks()` after our install throws
  "IO hooks are owned by an internal provider" (`Br:1493-1562`).

**Flags.** `hooks.flags` is read by each wrapper call (`php_io_hook_flags()`, `Hk:1060-1063`), so it
follows the queue. It is set at two cold points, never on a `run()`: the reactor's creation of the
queue sets `hooks.flags = q->ops->hook_flags(q)` when the provider is installed, and the install
reads the flags when the queue exists. A forked child's rebuild drops the queue and sets the flags
to 0 until the next submit creates one (S4.md 3.1); before that rebuild `add()` and `remove()` skip
the parent's queue, and a registration skipped there stays one-shot in the child, since the core
re-adds a registration only for a new generation (`Hk:315`). Until then it is 0: every wait is a
readiness wait after the syscall, which both queues serve, and no pair is registered. The Poll queue
gives `PHP_IO_HOOKS_F_EDGE_REGISTRATIONS | PHP_IO_HOOKS_F_LEVEL_REGISTRATIONS` (`P:712-715`), the Ring
`php_io_ring_hook_flags()`: Edge registrations and direct accept (`Rg:266-275`).
`PHP_IO_HOOKS_F_FILES` stays off (section 6). `PHP_IO_HOOKS_F_DIRECT_DATA` stays off: data ops go
syscall first, then a readiness wait, the order TrueAsync uses for sockets (F
`main/network_async.c:568-629`) and the Ring's default for the reason it gives (data is usually
ready). `PHP_IO_HOOKS_F_DIRECT_ACCEPT` stays off too, and the copy of an ACCEPT op waits for
readiness (section 4): an accept is `accept()` first, then a readiness wait, as in TrueAsync (S6.4).

**Registrations.** `add()` and `remove()` call the queue's `add()` and `remove()` (`H:392-393`); the
queue keeps its record in `reg->queue_data`. A provider that forwards nothing gets one-shot waits only:
the Poll queue serves Edge from `reg->edge`, which only its `add()` sets (`P:336-337`), and the Ring
arms its multishot poll and accept the same way (`Rg:1211-1267`). `dtor()` does nothing: the struct
lives in `ASYNC_G`, and the core ends the registrations without `remove()` when the provider goes
(`H:222`).

## 3. `run()`

### 3.1 The suspend predicate (M2, M13)

`run()` is never called with an exception pending: `php_io_run_ex()` answers Cancelled with
`ECANCELED` itself then (the pinned core since 2026-10-06, `Hk:964-975`), which covers the greedy
`_php_stream_read()` that calls `php_io_read()` again after a read that returned under a pending
exception (3.3, step 5). The plain and socket wrappers report that `ECANCELED` neither as a notice nor
as eof (`io-hooks-fixes`, sent to bukka). So IO in a destructor that unwinding runs fails with
`ECANCELED`, the same -1 TrueAsync's wrappers give under a pending exception (F
`main/streams/plain_wrapper.c:549-551, 699-701`). A process wait with `WNOHANG` (proc_open's resource
destructor) goes to `waitpid(2)` directly and never reaches `run()` (`Hk:1869`).

`run()` answers `PHP_IO_UNSUPPORTED` without touching the op, and the core then runs it
synchronously (`Hk:953-988`), when any of these holds:

- async is off (`!ZEND_ASYNC_IS_ACTIVE`): after `ZEND_ASYNC_DEACTIVATE` (`main/main.c:1948`), in the
  output handlers and module RSHUTDOWNs that follow it, the window M13 names;
- there is no current coroutine, or it is finished (after the scheduler's deactivation, as `delay()`
  in S4.md 1);
- the scheduler context flag is set (`ZEND_ASYNC_IN_SCHEDULER_CONTEXT`): a tick, a notify, a
  microtask or a destructor run there may not park (S3.md 4.6);
- the deadline is non-blocking (`dl.hrtime == 0`, `main/php_deadline.h:22-39`): the wrapper asks for
  one readiness check (`Hk:1169-1224`), which the core's own path answers without a switch; so is a
  POLL whose deadline has passed, `feof()`'s zero timeval the common case: on ior's IOCP backend its due
  link timeout can complete before the poller thread sees the readiness (DECISIONS 2026-10-08);
- the reactor's queue cannot be created (section 13: the submit returns the error instead of
  throwing).

`zend_fiber_switch_blocked()` is not part of the predicate (P1.4, the gate of `tools/check-gates.py`):
the core blocks switches around a provider's `add()`, `remove()` and `dtor()` (`Hk:212-222`), which
never call `run()`, and around pcntl's dispatch of PHP signal handlers (`ext/pcntl/pcntl.c:1434`). A
handler that does IO therefore parks its coroutine, as in TrueAsync, whose scheduler does not read the
block either (the fork's pcntl blocks the same way, F `ext/pcntl/pcntl.c:1383`). Whether such a wait
should be refused is the open question S4.3 put to Edmond (`dev/PLAN.md`, "A pcntl handler that
waits"); provider IO follows his answer with no change to this predicate unless he picks the refusal.
The window it also leaves for S6 (pcntl restores its signal mask after the handlers, `pcntl.c:1527`,
and so unblocks a signal a `SignalHandle` blocked meanwhile) closes with that question's core option,
pcntl blocking signals only around its queue: an S8 request (section 14). The same predicate answers
M2's "one may-suspend-here test": it is the one place the provider decides.

### 3.2 The op on the heap (M12)

The core's op lives on the wrapper's frame (`php_io_op op;` in every wrapper, `php_io_poll_ex` at
`Hk:1092-1110`). A queue keeps a pointer to the op it was given and writes through it at delivery
(`P:263, 505, 722`; `Rg:1882-1889`). `run()` therefore never submits the caller's op: it allocates an
IO event of S4.md 3.2, copies the op into `event->op`, and submits the copy. For ANY it also copies
the members and their pointer array into the same allocation (section 3.4). The frame then holds
nothing a queue points to.

Why the copy and not M12's `zend_try` around the park:

- **TrueAsync's path.** TrueAsync keeps everything its reactor touches in heap events: a poll wait
  allocates one socket event and one callback per descriptor (F `main/network_async.c:590-615`), and
  the coroutine destroys its waker, which removes the callbacks before anything can fire again, in the
  bailout's catch and in the finalize (`coroutine.c:549, 685`). Only the callback holds a pointer into
  the frame (`ufd`, read in its resolve at F `main/network_async.c:407`), and it is gone before the
  frame could be read. No `zend_try` is involved. S4.md 3.2 already put the Timer on the heap for the
  same reason.
- **The window.** A bailout reaches a parked `run()` in two ways. From `scheduler_bailout_all()`,
  through the BAILOUT transfer: `scheduler_suspend()` aborts the wait (U4, `async_wait_abort()`,
  the BAILOUT branches of `scheduler_suspend()`) on the parked stack before its `zend_bailout()`, while `run()`'s
  frame is alive. From a bailout raised on the parked coroutine's own stack, in its switch handlers
  or its tick inside `scheduler_suspend()`: the longjmp leaves through
  `run()` to the body's `zend_try` (`src/coroutine.c:347-373`), and only the finalize aborts the wait
  (`src/coroutine.c:397-398`), after its own calls have reused that stack. With the op on the frame,
  the unlink's `orphan()` would read `op->queue_data` from reused memory; with the copy it reads the
  heap. The event holds no pointer back to the frame (3.3), so neither path writes into the frame
  either; the kind's `abort`, which `async_wait_abort()` calls before the unlink
  (`src/true_async_API.c:226-238`), drops the reference `run()` would have released.
- **Cost.** One `emalloc` per parked op (the event is about 260 B with the op), where TrueAsync makes
  two per descriptor. An op completed at submit frees its event before `run()` returns (3.3).
  `zend_try` costs a `setjmp` per parked op and is a hot-path `zend_try`, which needs Edmond's word;
  the copy needs none. S8 measures the allocation; a per-coroutine reused event is the lever if it
  shows.

What the queue writes through the copy's pointers (`buf`, `addr`, `addrlen`, `res`, `status`, `info`,
the ANY results) still goes to the caller's memory, at delivery only. No delivery runs between a
bailout's longjmp and the finalize's unlink (no poll on that path; for main, the three catches of
3.3 step 1 re-enter the scheduler at once), and an orphaned op produces no
delivery on either queue (`P:502-530`, `Rg:1437-1467`). The Ring bounces a caller's buffer and copies
it back at delivery (`Rg:478-484, 536-537`), so its backend never writes into a frame; a stream's own
buffer stays valid while the stream is frozen (`Rg:1469-1486`).

### 3.3 Submit, park, wake

1. The predicate (3.1), which answers Unsupported in scheduler context and for a coroutine that is
   not running: a main a caught bailout left behind, or a call from a switch handler inside a
   suspend. `run()` never touches a wait it did not link: a running coroutine has none. A bailout a
   shutdown function, the script or the destructors catch re-enters the scheduler at once, which
   finishes that main and aborts its wait before any PHP code runs on it
   (`ext/standard/basic_functions.c:1703-1712`, `main/main.c:2618-2621, 1931-1945`).
2. The event is allocated and the op copied into it. The event is submitted with
   `async_io_event_try_submit()`,
   which puts it on the reactor's `waits` list (S4.md 3.4). A queue that completed the op at submit
   (`take_inline`, `H:387-389`) leaves the event `CLOSED`: `run()` copies the result and `in_flight`,
   releases the event and returns without parking, as the core's own path does (`Hk:830-882`) and as
   the S4.3 test hook does (`src/test_hooks.c:1625-1647`). Otherwise the record of kind IO is linked
   (phase 3) with a reference of its own; `run()` keeps its reference across the park, as TrueAsync's
   process wait reads its event after the suspend (F `ext/standard/proc_open.c:1643-1646`).
3. A failed submit: in a forked child the reactor has already rebuilt the queue (it compares the pid
   before each submit, S4.md 3.1), so no other rebuild is needed; `ENOTSUP`, `EOPNOTSUPP` and `ENOSYS`
   answer Unsupported, and the core runs the op itself; any other `errno` answers Done with
   `res = -1` and that error, which the wrapper reports as the syscall would (`Hk:1124-1152`). A
   failed fork rebuild leaves its Error pending and `run()` returns FAILURE.
4. The park: `ZEND_ASYNC_SUSPEND()`. The dispatch (S4.md 3.2) writes `event->result`, takes the event
   off the `waits` list and calls the record's `wake`, which only wakes the coroutine; the enqueue
   unlinks the record, which drops its reference. After the suspend `run()` copies from the event:
   the result (for ANY also `n_results` and `results[]`) and `in_flight` when the event fired, only
   `in_flight` otherwise; then it releases the event.
5. Woken without an exception: `run()` returns SUCCESS with what it copied. Woken with an
   exception after the event fired with a Done without an error (a cancellation that arrived after the
   completion; `run()` sees `result->status == PHP_IO_DONE`, which `php_io_run_ex()` set to
   Unsupported before the call): `run()` still returns SUCCESS with the result and leaves the
   exception pending. After delivery the result (an accepted descriptor, an address list, a reaped
   status, a taken signal) belongs to the provider, and the core frees nothing on FAILURE
   (`php_io_getaddrinfo` returns `EAI_SYSTEM` and the list leaks, `Hk:1708-1710`). The callers are
   safe with it: the VM frees the result of an opcode that threw (`Zend/zend_vm_def.h:8289-8305`);
   `main/network.c:829-862` and `ext/sockets/sockets.c:856-878` build their stream or object,
   `ext/standard/dns.c:273-293` frees the list, `ext/standard/proc_open.c:260-333` and
   `ext/pcntl/pcntl.c:407-424` return the status; a Send or a Write that returns SUCCESS is not
   retried (M1). A Done of a POLL or an ANY is a readiness, which belongs to nobody: it answers
   FAILURE, as step 6 does (S6.8), since with SUCCESS a pipe or `ext/sockets` caller would run its
   syscall under the cancellation (section 16, `io_provider/020`, `RFC-CHANGES.md` 14).
6. Woken with an exception otherwise (a Done with an error, which holds nothing to free; a Ready; a
   Timeout; no completion yet: a cancellation, a graceful shutdown): if the op had not completed, the
   enqueue's unlink ran the IO kind's `unlink`, which orphans the copy (`op->queue->ops->orphan`);
   `run()` copies the copy's `in_flight` back. `run()` returns FAILURE with the exception thrown by
   the suspend; the core turns that into Cancelled and `ECANCELED` (`Hk:972-977`), and the
   exception reaches PHP code, as TrueAsync's blocking functions throw the cancellation. A Ready under
   an exception is FAILURE because SUCCESS would send the readiness ladders (`php_io_descriptor_op`,
   `Hk:1188-1221`; `php_io_waitpid`, `Hk:1881-1914`) to park again (M1). A wake that is neither the completion nor
   a cancellation answers Interrupted, `EINTR` at the wrapper, so the core does not run the op again
   beside one the queue may keep. A bailout that reaches a woken `run()` before it resumes leaks
   `run()`'s reference to the event: the event is off the queue, and the request heap frees it, as
   TrueAsync's process wait leaks its event (F `ext/standard/proc_open.c:1643-1646`). A result the Ring holds
   undelivered is freed by the Ring itself (`php_io_ring_req_discard`, `Rg:546-609`). The wrappers add
   no notice and no eof for that `ECANCELED` (3.1).

`in_flight` travels back after every park and every completion at submit. The Ring sets it on the
copy when it keeps an op on a stream buffer after an early Timeout or an orphan (`Rg:1876-1880`,
unfrozen in `php_io_ring_req_free`, `Rg:705-707`); the wrapper's `php_io_frame_end()` then keeps the
stream frozen (`Hk:1048-1058`) while the backend writes into its read buffer. After a park (S6.8)
`run()` waits for such a copy with the queue's `drain()`, as `php_stream_free()` does, and reports
it settled: otherwise the next read, of a coroutine that caught the cancellation or after a
timeout, threw "Concurrent access to a stream" until a later poll settled the op (the Critic,
`io_provider/023`; the Sage for the early Timeout). The drain blocks the thread without a switch
until the queue completes the cancel, as `php_stream_free()` does; TrueAsync stops its read at the
cancel instead (`uv_read_stop()`). A completion at submit is not drained; on the Ring no listed
test reaches one (section 17).

The core's `php_io_op_finish()` after `run()` orphans the frame op only when `op->queue` is set
(`Hk:704-722`); the copy leaves it NULL, so the provider alone owns the orphan.

**The IO kind.** `info` gives `await: io <op type>` for `getAwaitingInfo()` and the deadlock report
(S4.md 2.4); `wake` wakes the coroutine (step 4); `unlink` is the reactor's
`async_io_record_unlink()`: it removes the record, orphans the op when the event has not fired and
drops the record's reference; `abort` drops `run()`'s reference for a `run()` a bailout unwound (3.2),
before the unlink. `run()` reads `in_flight` after the park, so after the orphan: the Ring sets it at
submit, clears it on cancel and sets it again only when the orphan keeps the op
(`php_io_ring_req_cancel()`, `php_io_ring_orphan()`), and a value read before the orphan would keep a
stream frozen for good.

### 3.4 ANY

An ANY op carries caller-owned member ops and a caller-owned results array (`H:112-117`). The IO event
for it is one allocation: the event, `n` member copies, the pointer array the copy's `u.any.ops` points
to, and `n` results the copy's `u.any.results` points to. Members are submitted by the queue as part of
the ANY (`P:476-494`, `Rg:1323-1336`); the provider submits only the ANY. The callers are
`stream_select()` (`ext/standard/streamsfuncs.c:860-917`), `socket_select()`
(`ext/sockets/sockets.c:1437-1477`) and curl (section 7).

## 4. Readiness and data ops

With the flags of section 2, the wrappers reach `run()` with:

| Wrapper | Op that reaches `run()` | Queue's answer |
|---|---|---|
| `php_io_recv`, `send`, `accept`, `recvfrom`, `sendto` | after `EAGAIN`, the data op with `F_AFTER_DRAIN` (`Hk:1169-1224`), or a POLL op for `sendto`/`recvfrom` (`Hk:1293-1359`); for `accept` the ACCEPT op, whose copy the provider submits as a POLL READ | Poll queue: Ready, then the wrapper's syscall (`P:311-372`); Ring: Done with the bytes, and for an accept the POLL's Done, which `run()` answers as Ready |
| `php_io_connect` | CONNECT after `EINPROGRESS` | Ready, then `SO_ERROR` (`Hk:1402-1502`) |
| `php_io_read`, `write` on a pipe | POLL first, then the syscall (`Hk:1510-1597`); the plain wrapper sets `O_NONBLOCK` once hooks are active (`main/streams/plain_wrapper.c:510-537`) | Ready |
| `php_io_read`, `write` on a regular file | no op: `F_FILES` is off (section 6) | the core's synchronous path |
| `php_io_poll` | POLL | Done with revents |
| `php_io_sleep` | TIMER (`sleep`, `usleep`, `time_nanosleep`, `time_sleep_until`, `ext/standard/basic_functions.c:1140-1297`) | Done at the deadline |

`php_io_sleep` answers Interrupted under the provider only for a wake that is neither the Timer's
completion nor a cancellation (3.3, step 6), which nothing sends today: the coroutine sleeps on while
a signal's PHP handler runs in another coroutine (S4.md 3.3), so `sleep()` returns 0 where the synchronous path
returns the seconds left. TrueAsync's `sleep()` is a timer wait too and is not interrupted either.

**Accept waits for readiness (S6.4).** With `PHP_IO_HOOKS_F_DIRECT_ACCEPT`, the core submits an
ACCEPT first, and the Ring arms a multishot accept on a registered listener
(`php_io_ring_accept_wait()`) that takes every later connection into its own buffer. `stream_select()`
and `socket_select()` ask the kernel and the queue for readiness, which neither shows for a buffered
connection: a select loop waited its whole timeout with a connection pending (`io_provider/015`), and
the Ring closes a connection it handed to a wait that was cancelled meanwhile. The provider masks the
flag, so `php_io_accept()` runs `accept()` first, and submits the copy of the ACCEPT op that follows
an `EAGAIN` as a POLL READ on the listener; its Done goes back to the core as Ready, and the core
accepts. That is TrueAsync's order (a libuv poll, then `accept()`), and the Poll queue's answer to an
ACCEPT. A registered listener keeps the Ring's multishot poll armed for its life, one completion per
connection whether anyone waits or not. The Ring's behaviour is a bug in bukka's code for any provider
that keeps the flag (`dev/WORKFLOW.md`, "Ownership").

## 5. Deadlines and deadlock

The op's deadline is absolute on `zend_hrtime()` (`main/php_deadline.h:22-39`); the copy carries it
to the queue unchanged. The Poll queue keeps it in its timer heap, the Ring links a timeout to the op
(`Rg:999-1005`); either answers Timeout, which the wrapper turns into `ETIMEDOUT`, 0 from
`php_io_poll`, `EAI_AGAIN` or `EAGAIN` (`Hk:45-75, 1702-1744, 1949-1987`). Stream timeouts reach the
deadline through the wrappers (`default_socket_timeout`, `stream_set_timeout()`,
`main/streams/xp_socket.c:75-147`); pipes wait without one (`plain_wrapper.c:514-537`). An infinite
deadline arms no timer.

A parked provider op is on the reactor's `waits` list from its submit to its completion or orphan, so
a coroutine waiting on IO with nothing else runnable is not a deadlock (S4.md 3.4), as TrueAsync
counts an active IO event (`scheduler.c:1849`). The Poll queue's `EDEADLK` (an op without a
descriptor and without a finite deadline, `P:639-643`) goes to the deadlock resolution as S4.md 3.3
says.

## 6. DNS and files

**DNS.** GETADDRINFO and GETNAMEINFO reach `run()` whenever a provider is installed (`Hk:1680-1744`).
The Ring runs them on ior's worker pool (`Rg:763-787, 955-963`) and returns the `EAI_*` code. The Poll
queue has no form for them and answers Unsupported (`P:328-331`), so the core calls `getaddrinfo()`
on the thread: the `dns` tests count only on the Ring (`dev/PLAN.md`, S6 Done when), which every
lane builds (`tools/ci/build-core.sh`). A lookup the provider's coroutine was cancelled in is orphaned;
the Ring drops a list the worker returned late (`Rg:590-605`).

**Files stay synchronous.** The provider leaves `PHP_IO_HOOKS_F_FILES` off, the core's default
(`php_io_ring_hook_flags()` does not give it, `Rg:266-275`): regular-file READ, WRITE and FSYNC run
on the thread. With it on, a cancelled read on the Ring loses the bytes the backend read (B3), which
is worse than a coroutine holding the thread for a disk read. TrueAsync runs file IO in libuv's pool
(F `plain_wrapper.c:237-288`), so this is a departure (section 11); it ends with the core's
commit-on-settle (B3, section 14), and S8 measures a slow-disk read against the others. `io/100`
(a cancelled read keeps the position) is then expected to pass, an inference to be confirmed by
S6.3's run.

## 7. Children, exec and curl

**WaitPid.** `proc_close()`, `pcntl_waitpid()` and `pcntl_wait()` call `php_io_waitpid()`, which
reads the core's reaped-status table first and submits WAITPID with a pidfd (`Hk:1850-1922`). The
table is `FG(io_reaped)`, per request and thread (`Hk:534-612`); the core fills it from a
`ProcessHandle` and from a Ring WaitPid nobody claimed (`Rg:590-598`), and reads it in `proc_close`,
`proc_get_status` and pcntl (`ext/standard/proc_open.c:251-330`, `ext/pcntl/pcntl.c:397-411`). The
provider adds nothing to it: a cancelled WaitPid on the Ring is recorded by the Ring, and on the Poll
queue the op is readiness only and reaps nothing. `php_io_child_reaped()` stays the core's. Without a
pidfd (`pid <= 0`, a kernel before 5.3) the Poll queue answers Unsupported and the core's blocking
`waitpid()` holds the thread (section 14).

**exec().** `exec()`, `shell_exec()`, `system()` and `passthru()` read the child's output through
`php_io_read` on a pipe, so the reads park; the close is libc's `pclose()` (the stream has no
`child_pid`, `plain_wrapper.c:748-762`) and blocks the thread in `waitpid()` once the output is read
(review 11.2.7). An RFC change makes it the WaitPid op (section 14).

**curl.** `curl_exec()` with a provider runs the multi socket API: each pass registers the wanted
directions as Level pairs and runs one ANY of POLL members and a Timer (`ext/curl/interface.c:2577-2838`).
On the Poll queue the pairs register; on the Ring, which takes Edge only, `php_io_register()` returns
NULL and the waits are one-shot (`Hk:280-285`). `curl_multi_select()` runs an ANY of POLL ops with no
handle (`ext/curl/multi.c:300-385`). `curl_multi_exec()` is not routed.

**mysqlnd** reads and writes through the socket stream, so `php_io_recv`/`send` with the stream's
timeout (`ext/mysqlnd/mysqlnd_vio.c:85-108`); `mysqli_poll()` calls `select()` and bypasses the hooks.

## 8. Signals

**SigWait.** `pcntl_sigwaitinfo()` and `pcntl_sigtimedwait()` call `php_io_sigwait()`, which opens a
signalfd for the set and submits SIGWAIT (`Hk:1924-2026`); the caller has blocked the signals. Both
queues serve it: the Ring with `ior_prep_sigwait`, the Poll queue as readiness on the signalfd
(`P:322-326`). Nothing provider-specific.

**`Async\signal()`** returns a `Future` (S5) that completes with the `Async\Signal` case when the signal
arrives, or fails with the `$cancellation`'s error (TrueAsync's `async.c:1373-1470`). The reactor keeps
one `Io\Poll\SignalHandle` per signal number in the thread (`ASYNC_G`, created by class name as S4.md
3.6 creates the `NotifyHandle`), with one SIGWAIT op in flight while any Future waits for that
number; a delivery completes every such Future, as libuv delivers a signal to each handle of a loop.
On the Ring the op's `info` carries the signal; on the Poll queue the op answers Ready and the
reactor takes the signal with `php_poll_signal_source_take()`, as `php_io_sigwait()` does
(`Hk:1950-1959`). Neither queue blocks the signal: `ior_prep_sigwait` and the signalfd see only
blocked signals, and a `SignalHandle` blocks its set only while an `Io\Poll\Context` watches it
(`Ip:1031-1105`, called from `Context::add()`, `Ip:2247`). The reactor therefore keeps one
`Io\Poll\Context` for the thread while any number is watched, made by class name and never waited
on, and adds each signal number's handle to it with `Event::Signal` while a Future waits for that
number (`src/os_signal.c`; the file is not `signal.h`, which `<signal.h>` would find).
The add is how the core blocks a signal and records it as blocked by a handle, so `proc_open()`,
`exec()`, `mail()` and `pcntl_exec()` children start with it unblocked (`Ip:1000-1008`).

- **The watch** of one number: the handle, its SIGWAIT event, and the waiting Futures as callbacks
  in an `async_callbacks_vector_t`, notified with `async_callbacks_notify()`, which is safe against
  removals during the walk. A Done with EAGAIN (the Ring) or a Ready whose take finds nothing (the
  Poll queue), the loss of a race with a `pcntl_sigwaitinfo()`, submits the op again. A delivery
  clears the op first, completes every Future in the vector, Futures made during the notify
  included, and submits again only when the vector is not empty after it.
- **The Future**: a pending one from S5's event (`async_future_new_pending()`), completed with
  `async_future_event_resolve()` once (the caller checks CLOSED). The Future's own callback on its
  event has a `dispose` that leaves the watch when the Future is freed or completed, so a dropped
  Future stops the wait (`signal/005`-`007`); a waiter holds its own reference to the event.
- **`$cancellation`**, a Coroutine, Future or Timeout as for `await()`. A Timeout is first checked
  with `async_timeout_fire_if_due()`. Completed already: the Future is rejected at once with the
  token's exception (a Timeout's `async_timeout_exception()`, TimeoutException), or with
  AsyncCancellation("Signal wait cancelled") when it has none, as TrueAsync (`signal/003`, `004`).
  Otherwise a callback on the token (a Timeout subscribed, unsubscribed when the Future leaves)
  rejects it the same way.
- **The last Future goes**: the op is withdrawn and the handle removed from the context, which
  unblocks the number and takes what arrived meanwhile into the handle. That signal came when
  nothing waited for it, so it is raised again with `raise()` and gets the process's own action: the
  Zend handler's, the default one, or none when ignored. On the Ring a SIGWAIT completion reaped after
  the withdrawal is re-raised by the Ring itself (`Rg:592-596`), to the same effect. The context goes
  with the last watch.
- **`pcntl_signal()` unblocks**: `zend_sigaction()` unblocks the number it installs a handler for
  (`Zend/zend_signal.c:258-263`), as do pcntl's RSHUTDOWN and `pcntl_sigprocmask()`. Before each
  poll and idle wait, while a watch exists, the reactor blocks the watched numbers again with
  `pthread_sigmask()`; the core's records still say blocked, so nothing else changes. A signal that
  comes between the unblock and that poll goes to the handler only. An RFC request asks that
  `zend_sigaction()` leave a handle's signals blocked (`RFC-CHANGES.md`).
- **Fork**: the child's reactor rebuild submits each watch's op again on the child's queue, makes a
  new context, adds the handles to it, then frees the parent's context, whose `add()` and `remove()`
  refuse a foreign process (`main/poll/poll_core.c:449-462`); the order keeps the numbers blocked.
- **No ZEND_SIGNALS**: the forward to the Zend handler below is compiled out, so a `pcntl_signal()`
  handler does not see a signal a Future took.
- A Future for a signal the handle refuses (SIGKILL, SIGSEGV and the others that cannot be blocked,
  the execution timeout's) is not made: `signal()` throws the handle's ValueError.
- **Numbers**: the enum carries Linux numbers; `signal()` maps each case to the platform's constant.
  `SIGBREAK` (21) and `SIGABRT2` (22) exist only on Windows and throw a ValueError elsewhere, where
  TrueAsync passes 21 and 22 through and so watches `SIGTTIN` and `SIGTTOU` on Linux
  (`async.c:1203-1217`).
- **A completed token** fails the Future at once, before any platform check, so `signal/003` and
  `004` pass on Windows too, where `signal()` otherwise throws (section 9).

A delivery taken from the handle is also passed to the handler the
Zend signal table holds for it (`SIGG(handlers)`, pcntl's), as TrueAsync's
`libuv_global_signal_callback` does (`libuv_reactor.c:1383-1403`), so `pcntl_signal()` keeps working
with either order of registration (`signal/013`, `014`). The core is built with `ZEND_SIGNALS`. A
`pcntl_sigwaitinfo()` for a signal the reactor's handle also waits for competes with it as two
`sigwaitinfo()` callers do: one of them takes it. The SIGWAIT event is on the reactor's `waits` list
while a Future waits on it, so a coroutine awaiting a signal is no deadlock; a Future nobody awaits
keeps nothing alive once it is released (`signal/005`-`007`). A held one keeps a script that ends
by itself waiting for its signal (`signal/030`), but not a graceful shutdown: with no coroutine left
the scheduler stops and the request's shutdown closes the watch (S6.8, `signal/027`-`029`).

**Ownership with threads, decided.** A `SignalHandle` blocks its signals in its own thread only
(`pthread_sigmask` under ZTS), and the core refuses it outside the CLI under ZTS: "The mask is per
thread: in a multi-threaded SAPI another thread would take the signal with its default action and the
handle would never see it" (`Ip:1301-1310`). The first version follows that rule: a signal belongs to
the one PHP thread of the process, where `Async\signal()` works; in a multi-threaded SAPI it throws the
core's error. ior's worker threads block every signal (`ior_worker_pool.c:23-33`), so they never take
one. Delivery to several PHP threads (TrueAsync's `signal/008`, `009`, `012`, a thread pool's
workers each awaiting one signal) belongs to the thread pool (the Fog's ZTS line, S10) and needs a
process-wide owner the core does not have; those three tests are excluded with that reason.

## 9. Windows

With ior the queue is the IOCP Ring (S4.md 3.8). Sockets, DNS, timers and WaitPid
(`ior_prep_waitpid`, `Hk:1746-1848`) go through `run()`; files stay synchronous as on Linux (section
6). Pipes do not reach `php_io` today: `proc_open()` creates them with `CreatePipe()`, synchronous
anonymous pipes (`ext/standard/proc_open.c:495`), the plain wrapper reads them with a `PeekNamedPipe`
and `usleep()` loop (`main/streams/plain_wrapper.c:634-639`), and IOCP posts completions only for
overlapped handles (`ior_iocp.c:1347-1400`, `plain_wrapper.c:1499-1500`).

S6.10 brings one commit on `io-hooks-fixes`, merged into the next `async-core-io` branch, with an
`RFC-CHANGES.md` entry (`dev/WORKFLOW.md`, "Ownership"; one topic per commit): `proc_open()` creates the parent's end
of each pipe as an overlapped named pipe, as libuv does, the child's end stays synchronous (the core
keeps a socket pair's child end non-overlapped the same way, `proc_open.c:967`), and the plain
wrapper reads and writes such a pipe through `php_io_read()` and `php_io_write()` (`plain_wrapper.c:577, 670`). The same commit serves the path
without a provider: `php_io_run_sync()` goes to the core's Poll queue (`Hk:839`), which cannot poll a
Windows pipe, so the synchronous path does an overlapped `ReadFile()` or `WriteFile()` and waits for
it, as it already does for overlapped files. Without that a plain `proc_open()` on Windows would
break. `exec()` output (`_popen()` pipes) and STDIN stay synchronous (section 11). No signals on
Windows: `Async\signal()` throws there, as `SignalHandle` is unsupported
(`main/poll/poll_core.c:191-207`).

### 9.1 S6.10 as built (2026-10-08)

Line references are to bukka's `io_hooks_poc` head `566a6833eb5` (php) and ior `2bfd231` unless a
file says otherwise; "finding vN-M" are the Critic's reviews of the design's drafts.

What the Windows lane shows on the pinned core (S1.5): `stream_select()` on a `proc_open()` pipe
returns 0 (`stream/033`, `035`, `036`); a `fread()` on a pipe in a coroutine blocks the thread
(`io/044`). `proc_open()` makes synchronous anonymous pipes (`CreatePipe()`, `proc_open.c:489-495`),
which IOCP cannot complete and WSAPoll cannot poll, so the plain wrapper never hands a pipe to
`php_io` (`plain_wrapper.c:562-573, 621-669`).

Section 9 decided overlapped named pipes (DECISIONS 2026-10-06). Versions 7-12 of this text replaced
them with a 16 ms polling loop after a Critic round, without Edmond's word; Edmond's question
(2026-10-08) brought the plan back. Measured on his machine (2026-10-08,
`notes/s6-10/overlapped-pipe-measurements-2026-10-08.md`): through IOCP 100 MB from a child takes
0.07-0.08 s, 100 MB into a child 0.03-0.04 s, a request and response 9-15 us per turn (vanilla
`blocking_pipes`: 0.58 s, 0.03 s, 8.8 us; the polling loop: 1.6 s, 1.6 s, 13 ms). CRT `_read()` and
`_write()` on an overlapped end move 100 MB each way intact while one operation at a time runs on the
handle; an overlapped end handed to a second child works (`findstr` and a C child); `ReOpenFile()`
cannot give a synchronous handle of the pipe, so every path keeps the overlapped handle. A zero-byte
overlapped `ReadFile()` stays pending until data arrives, completes with 0 bytes 21 us after the
child's write and leaves the data, and completes with `ERROR_BROKEN_PIPE` at the child's exit; a
cancelled pending read completes with `ERROR_OPERATION_ABORTED` and loses no bytes.

TrueAsync wraps the `CreatePipe()` handle in libuv, which waits for data with a zero-byte blocking
`ReadFile()` on a worker thread (from memory, not checked). libuv's own `uv_spawn()` makes the
parent's end an overlapped named pipe (libuv `src/win/pipe.c:276-345, 447-500`), which is what this
section does. TrueAsync's order for data, the syscall first and then a readiness wait, is kept for
reads; TrueAsync's provider runs with no data flags (true-async `src/io_provider.c:403-407`, S6.md
section 2), so nothing here relies on `PHP_IO_HOOKS_F_DIRECT_DATA` (finding 1).

**ior is required** (finding 11). Without it the provider falls back to the Poll queue (true-async
`src/reactor.c:368-397`), which cannot wait for a pipe: a pipe wait there is Unsupported and the
core does it synchronously, blocking the thread. The lanes build with ior
(`tools/windows/build-ior.ps1`); a build without it keeps the S6.10 tests' `xfail-on` tag.

**Four ior changes come first** (finding v16-1; by the bukka bug rule: our ior branch
`release-handle` in true-async/ior, `IOR_REF` moved to it, a PR to libior/ior that Edmond opens;
Edmond chose fixing ior, 2026-10-08 09:05, and taking the handle off the port with the filter kept,
2026-10-08 14:31):
- **A packet that is not one of ior's ops is dropped.** ior takes any `OVERLAPPED` from the port
  for one of its ops: the dequeue (`ior_iocp.c:4378`), the pump thread, which writes into it before
  anything else (`:4154-4157`), and the teardown drain, which frees it (`:3876-3880`). A pipe handed
  to a second child stays associated with the parent's port, and the child's own overlapped I/O
  posts there with the child's `OVERLAPPED` address and the parent's key (measured, third round),
  so ior writes through an address of another process. The fix is one predicate, called at all
  three sites before the address is touched (finding v17-1, v17-2, v17-3):
  - key 0: ior's own packet, taken as today. ior posts every synthetic completion with key 0
    (`:1046, 1066, 2964`) and associates every handle with key = the handle (`:1207, 1265, 1281`),
    which is never NULL (`:1258`); a child's packet carries the parent's association key, never 0;
  - any other key: the address must be an op slot of one of the context's chunks (in range and on
    an op boundary, `iocp_op_chunk`, `:256-261`), the op's `state` must be `IOCP_OP_IO` or
    `IOCP_OP_IO_CANCEL` (atomic, a kernel request of ior's in flight, `:81-82`; read first, with
    acquire), and the op must not be taken yet: `atomic_exchange(&op->packet_taken, true)` returns
    false, and `iocp_op_start_io()` clears the flag before each of the six kernel calls (ior Critic,
    third pass: an LSP's `WPUCompleteOverlappedRequest()` queues the packet before it writes
    `Internal`, so a `STATUS_PENDING` gate is unsafe, and the pump could stage one op twice). A
    child's packet that lands exactly on a slot with a request in flight is taken for it: nothing in
    the packet tells the two apart. Anything else is dropped and not counted in
    `active_count`. A drop at the dequeue dequeues again with the time left, as the pump does
    (`:4151`), at most 64 times per call, so foreign packets neither end a batch reap early
    (`peek_batch_cqe()` stops at the first negative answer, `:4710-4714`) nor hold a 0 ms peek
    forever (finding v18-1).
  The parent issues no op on a handed-out pipe (item 6), so no in-flight op matches a child's
  packet. `op->live` is not used: it is also true for ops that never entered the kernel
  (finding v18-3). The chunk list is published with release and read with acquire (the poller thread grows
  the pool, `:692-705`, 2351; finding v17-5), so the walk takes no lock; it covers a few chunks, since each new one
  doubles the pool (`:724`), and synthetic packets skip it. The key is not compared (ior Critic,
  second pass): an op on a duplicate handle takes the file object over under its own key
  (`:1281-1290`), and ops on the first handle then complete under it; with a key check they
  would be dropped and hang. Duplicates keep working as on the base, and a test pins it. The
  child's overlapped I/O completes for the child at once, whether or not the parent's ring
  dequeues its packet (the ior README says so).
- **`ior_release_handle()` takes a handle off the port.** `NtSetInformationFile()` with
  `FileReplaceCompletionInformation` and no port (Windows 8.1 and later), so the child's packets
  reach no port at all; the filter above stays for the cases the release does not cover. Windows 11
  unties a handle even with a request pending on it, and that request's packet then reaches no port
  (measured), so ior answers `-EBUSY` while a read, write, send, recv, accept or connect of the
  context on the handle is queued or its completion not yet dequeued; `-ENOTSUP` where ntdll lacks
  the call or rejects the class (Wine); 0 for a handle the context does not own. The context's next
  op on the handle associates it again.
- **A read of part of a message or datagram completes with the bytes read.** Its packet says
  `ERROR_MORE_DATA`, and ior completed it with `-EIO` and 0 bytes; Windows 11 reports such a read
  as pending even with the data there (measured), Wine fails it at once and still queues the packet,
  so a synchronous `ERROR_MORE_DATA` or `WSAEMSGSIZE` counts as started when the `OVERLAPPED` holds
  `STATUS_BUFFER_OVERFLOW`.
- **`ERROR_NO_DATA` (232) completes a write with `-EPIPE` and a read with `-EAGAIN`.**
  `win_error_to_errno()` (`:464-549`) lacks it and answers `-EIO`; 232 is a write to a pipe whose
  reader closed (measured) or a read of an empty `PIPE_NOWAIT` pipe; ior maps it per op.

One commit on `io-hooks-fixes`, `RFC-CHANGES.md` 18, all of it under `PHP_WIN32`:

1. **Who gets named pipes.** A process-wide setting, `PHPAPI bool php_io_overlapped_pipes`
   (`main/php_io_hooks.h`, beside `php_io_signal_pending`, `php_io_hooks.c:36`), false by default;
   TrueAsync sets it in MINIT (Edmond, 2026-10-08: PHP without the extension keeps today's pipes).
   It is a setting rather than a hook flag because TrueAsync installs the hooks only at the first
   coroutine (true-async `src/io_provider.h:42-48`) and a `proc_open()` before it must get the same
   pipe.
2. **Creation** (finding 10). With the setting on, `proc_open()` makes each pipe as libuv does
   (`pipe.c:236-360`): the parent's end `CreateNamedPipeW(\\.\pipe\php-<pid>-<random>,
   PIPE_ACCESS_INBOUND or OUTBOUND | FILE_FLAG_OVERLAPPED | FILE_FLAG_FIRST_PIPE_INSTANCE |
   WRITE_DAC, PIPE_TYPE_BYTE | PIPE_READMODE_BYTE | PIPE_WAIT | PIPE_REJECT_REMOTE_CLIENTS, 1, 64 KB,
   64 KB, 0, NULL)`, not inheritable (libuv makes the stdin end duplex for a write-buffer probe,
   `pipe.c:465-470`, which this design does not do); the child's end `CreateFileW()` of the name,
   synchronous and inheritable, with libuv's access (`GENERIC_READ` or `GENERIC_WRITE`, the other
   direction's attributes right, `WRITE_DAC`); then `ConnectNamedPipe()` with an `OVERLAPPED`,
   which answers `ERROR_PIPE_CONNECTED` at once. These are the measured flags. `<random>` is 64 bits
   of `php_random_bytes_silent()` per pipe (`ext/random/php_random_csprng.h:21`), so a name cannot
   be guessed from an earlier one; a name taken at `CreateNamedPipeW()` (`ERROR_ACCESS_DENIED`,
   `ERROR_PIPE_BUSY`) is retried with new bytes, at most 16 times; a failure at `CreateFileW()`
   fails the `proc_open()`, as libuv fails it (`:333-336`): with one instance, another client got
   there first. 64 KB is libuv's size and Linux's default; the buffer no longer bounds the speed
   (measured: 1 MB adds nothing). The parent's end goes through the shared
   `make_descriptor_cloexec()` as an anonymous pipe's does (`proc_open.c:904-914`): one extra
   `DuplicateHandle()`, harmless.
   **The stream** (finding 6) comes from a new plain-wrapper call,
   `php_stream_fopen_from_overlapped_pipe(fd, mode)`, which makes it as `proc_open.c:1556-1559`
   does today and sets a new field, `is_overlapped_pipe`. `is_overlapped` keeps its meaning (a disk
   file with a position): none of its paths (`make_sync` in casts, `sync`, `seek`, the copy's
   position, `plain_wrapper.c:210, 835, 868-881, 907, 969`) sees a pipe.
3. **Reads.** The plain wrapper reads an overlapped pipe through a new `php_io_pipe_read(stream, fd,
   buf, len, dl, no_provider)` (`php_io_hooks.c`, beside `php_io_read()`), the syscall first as TrueAsync does:
   - `PeekNamedPipe()`; with bytes available it reads at most that many with
     `php_win32_ioutil_pread()` at offset 0, which a pipe ignores, so the call never waits;
   - with none: a stream in non-blocking mode (item 9) answers `EAGAIN`; otherwise, under hooks, a
     READ op of `len` at offset -1 with `PHP_IO_OP_F_PIPE`, which the provider performs whatever its
     data flags (the Ring: an overlapped `ReadFile()` at `IOR_OFF_NONE`, which ior reads at 0,
     `ior_iocp.c:1376-1379`; done as soon as any bytes arrive), so the thread never blocks; offset -1
     keeps the op one that advances the stream (`php_io_op_read_advances()`, `php_io_hooks.h:132-136`),
     so bytes a cancelled read already took are kept in the stream (`php_io_run_cancelled()`,
     `php_io_hooks.c:1162`; the Ring's orphan, `php_io_ring.c:1554-1558`), and the call starts with
     `php_io_stream_read_lost()`, sets `php_io_stream_buf_flag()` on the op and ends with
     `php_io_run_cancelled()` as `php_io_read_at()` does (`php_io_hooks.c:1342-1352, 1669, 1762`,
     finding v15-1); the op's deadline is infinite (a stream in non-blocking mode never gets
     here); a provider answering Ready is taken as Unsupported, since a Ready that does not
     suspend would loop the peek (finding v16-4, v17-6); the provider
     answering Unsupported (no current coroutine) or no hooks: a blocking `pread()` of `len`, which
     waits for data as a blocking pipe does today;
   - `PeekNamedPipe()` failing with `ERROR_BROKEN_PIPE` is EOF (0 bytes), and so is a read that
     ends with it (`pread()` returns 0 for it, `ioutil.c:1431`; under hooks the op completes with
     error `EPIPE`, `php_io_ring.c:1723-1728`, which `php_io_pipe_read()` turns into 0 bytes, so
     the plain wrapper's read notice, `plain_wrapper.c:684-690`, never sees it, finding v16-2);
     failing with `ERROR_ACCESS_DENIED` (the write end) is `EBADF`. No 0-length
     read is ever issued (a wake with nothing to read cannot read as EOF, finding v14-3).
   The vanilla peek loop (`plain_wrapper.c:628-651`, `usleep(10)` rounds) is skipped for an
   overlapped pipe, with or without hooks (code, 2026-10-08: the loop is timer polling where the OS
   can wake): `php_io_pipe_read()` peeks once and, with nothing there, waits for data or EOF
   through the provider or a blocking `pread()`; a non-blocking one peeks once and answers `EAGAIN`
   at 0 (finding v15-4). An anonymous pipe keeps its whole path as today (finding 7). The visible
   change: where the loop ran out after 3 200 000 rounds and `read(fd, buf, 0)` returned 0 (a false
   EOF), the read now waits.
4. **Writes.** A pipe has no write readiness (an overlapped end's signaled state means nothing,
   measured), so a write is performed, not waited for: a new `php_io_pipe_write(stream, fd, buf, len,
   dl)` builds a WRITE op with `PHP_IO_OP_F_PIPE` of at most 64 KB with an infinite deadline
   whatever the stream's mode (item 9; TrueAsync answers Unsupported for a zero deadline,
   true-async `src/io_provider.c:268-270`, finding v16-3), which a provider performs
   whatever its data flags (the Ring: an overlapped `WriteFile()`, done when all of it is in the
   pipe); the wrapper returns the short count and the stream's write loop issues the next
   (`streams.c:1138-1153`), so the Ring's bounce buffer stays bounded (`php_io_ring.c:505-508`) and
   a cancelled write loses at most one chunk, of which the child's stdin then holds an unknown part
   (section 11; finding v14-2). Ready: the chunk is written with `php_win32_ioutil_pwrite()`, as
   `php_io_descriptor_op()` treats Ready (`php_io_hooks.c:1281-1282`, finding v16-4). Unsupported
   or no hooks: `php_win32_ioutil_pwrite()` of the whole
   count, which blocks as `_write()` does today. A write to a child that closed its end fails with
   `EPIPE`: measured, one started after the close fails at once with `ERROR_NO_DATA` (232), one
   pending at the close completes with `ERROR_BROKEN_PIPE` (109); `php_win32_ioutil_overlapped_io()`
   turns both into `EPIPE` for a write (today it returns 0 for 109, which a caller retries forever,
   and 232 is missing from `winutil.c`'s table, so the CRT's EINVAL comes out; a disk file never
   gets either). Under hooks ior gives `-EPIPE` for both once its 232 mapping is fixed (above).
   `PHP_IO_OP_F_PIPE` is documented in `php_io_hooks.h`: on a READ, WRITE or POLL op, `fd` is the
   CRT descriptor of an overlapped pipe; a provider performs such a READ or WRITE, or answers
   Unsupported.
5. **Readiness on the Ring.** `stream_select()` alone waits for a pipe's readiness (item 7). The
   Ring takes a POLL with `PHP_IO_OP_F_PIPE` on the handle (`php_io_ring_file_fd()`,
   `php_io_ring.c:846-856`): READ is a zero-byte overlapped `ReadFile()` into a non-NULL one-byte buffer of the Ring's (libuv
   reads into `&uv_zero_`, `pipe.c:39, 1633-1638`),
   done at data (`READ`) or at the child's exit (`READ | HUP`); WRITE is done at once (item 4); a
   zero-byte read that fails otherwise (`ERROR_ACCESS_DENIED` on a write end) completes with
   `PHP_POLL_ERROR`, which `stream_select()` reports as it reports an error on a socket. Without
   the flag the Ring would hand the CRT descriptor to ior's WSAPoll thread, where one non-socket
   fails every poll of the context (`ior_iocp.c:2336-2341, 2451-2460`). The group probe
   (`php_io_ring.c:1799-1822`) checks such members with `PeekNamedPipe()` and keeps them out of
   `php_poll2()` (finding 4). A parked op on a stream that is closed goes the way of a socket's:
   the stream is orphaned and its free drains the op (`php_io_hooks.c:643-689`, `streams.c:309,
   367`).
6. **Casts** (finding 3, v14-1). An overlapped pipe hands out its descriptor as it is (no
   `ReOpenFile()`): the CRT and a second child work on it while one operation at a time runs
   (measured). `AS_FD` and `AS_STDIO` with `ret` given (`plain_wrapper.c:904-950`) check the stream
   first, since a synchronous call on the handle may complete falsely while an overlapped one is
   pending (`ReadFile()` documentation): an op of another frame holding it (`IN_USE` without an
   orphan) fails the cast with "Concurrent access to a stream"; an orphaned op is drained first (the
   queue's drain, then `php_io_stream_unfreeze()`, `php_io_hooks.c:656-694`; the drain waits for the
   op the orphaning already cancelled). After `AS_STDIO` the stream reads and writes through its
   `FILE*` (`plain_wrapper.c:606, 708, 924`), which blocks the thread under hooks (section 11). `AS_FD_FOR_SELECT` and `FOR_POLL`, which
   `stream_select()` takes on its own frozen members (`streamsfuncs.c:709`), are not checked.
   `set_proc_descriptor_from_resource()` (`proc_open.c:1123-1143`) casts `AS_FD`, so a pass-on
   gets the check. **A pass-on of a pipe the Ring has used** (finding v14-4, v16-1): the port
   association belongs to the file object, which the second child shares, so the child's own
   overlapped I/O posts to the parent's port (measured, third round). Right before
   `CreateProcessW()`, after the descriptor loop that may run user code, a pass over the
   descriptors sets `PHP_STREAM_OVERLAPPED_PIPE_RELEASE` on each overlapped pipe: a pipe with an op
   in flight or backlogged in the Ring throws "Concurrent access to a stream" and `proc_open()`
   fails, as the cast does; otherwise `php_io_queues_release()` calls the new queue op `release()`
   on every queue of the thread, and the Ring calls `ior_release_handle()` (above) and ignores its
   answer: where ior cannot release, its filter drops the child's packets. `proc_open()` then marks each such stream through a new
   plain-wrapper option, `PHP_STREAM_OPTION_OVERLAPPED_PIPE` with `PHP_STREAM_OVERLAPPED_PIPE_HAND_OUT`
   (OK for an overlapped pipe, NOTIMPL for anything else), only after `CreateProcess()` succeeds
   (finding v16-6). It sets `is_handed_out`: from then on the stream's reads and writes skip the provider and take the
   synchronous path of items 3 and 4, and `stream_select()` takes it to `php_select()` (item 7).
   Without the mark the parent's next Ring op would take the file object over
   (`iocp_take_over_handle()`, `ior_iocp.c:1288-1291`) from a libuv child, which binds an inherited
   handle to its own port (libuv `pipe.c:427-429`), and the child's completions would come to the
   parent. The core does not call `NtSetInformationFile()` itself: only ior knows whether it bound
   the handle and which of its ops are still in the kernel (`ior_iocp.c:1196-1214, 1256-1276`,
   finding v15-3), so the release goes through the queue to ior. Using a passed-on pipe from both sides at once stays the script's race (section 11). `AS_FD_FOR_COPY` reports a pipe without a position (`plain_wrapper.c:952-974`),
   so a copy without hooks uses the CRT calls on it; under hooks a pipe copy takes the fallback
   already (`streams.c:1730-1733`).
7. **`stream_select()` under hooks** (finding 4). A new plain-wrapper option,
   `PHP_STREAM_OPTION_OVERLAPPED_PIPE` with `PHP_STREAM_OVERLAPPED_PIPE_QUERY`, answers OK for an
   overlapped pipe and stores whether it is handed out in the `bool` given; anything else answers
   NOTIMPL, and only OK counts (`php_streams.h:531-533`, finding v16-6); `stream_select_any()` asks it
   for each member (`streamsfuncs.c:870-890`) and sets `PHP_IO_OP_F_PIPE` on that POLL op, and a
   handed-out member sends the whole call to `php_select()` (finding v15-2). A pipe in the except
   set is reported there at once, as `php_select()` does (third pipes Critic).
   Its pre-check (`:811-863`) checks such members with `PeekNamedPipe()` (a pipe in the write set
   is writable) and passes only the others to `php_poll2()`, which on Windows is Winsock `select()`
   and fails as a whole on a pipe. When the Any comes back with an `F_PIPE` member Unsupported, the
   call rebuilds its sets from the members and does it through `php_select()` with the time left
   (the sets were cleared for the provider, `:1145-1147`). Unsupported is what the core's queue
   answers for a pipe: its WSAPoll backend refuses a non-socket at add (`poll_backend_wsapoll.c:123-127`,
   `php_io_queue_poll.c:360-361`), which every fallback here rests on.
8. **`stream_select()` without hooks** (finding 5, v14-6). With `php_io_overlapped_pipes` on,
   `php_select()` (`win32/select.c:32-185`) judges a pipe in the read set by `PeekNamedPipe()`
   whatever else is in the sets, counts a pipe in the write set as writable, and leaves pipes out
   of the `WaitForMultipleObjects()` wait (`:129`), so they have no 64-handle limit (second pipes
   Critic, finding 1). The loop is reshaped for it: each round peeks
   the pipes first and returns when one is ready; a round with no handles left to wait on skips the
   wait (a count of 0 fails it today, `:137-140`); with pipes in the sets the Winsock slice and the
   handle wait ask for 1 ms instead of 100 ms (`:120-129`), which the timer tick rounds up (15.6 ms
   by default, finding v15-5), and a round with neither sockets nor other
   handles sleeps `usleep(100)` as it does for read pipes now (`:169-171`). With the setting off
   `php_select()` is unchanged.
9. **`stream_set_blocking()`** (finding 8, v14-5) on an overlapped pipe succeeds and sets
   `is_nonblocking`: a read with nothing available answers `EAGAIN` (the wrapper returns 0,
   not EOF), as on Linux, which is what `io/044` checks. A write stays one that is performed:
   under hooks it parks the coroutine until it is in the pipe, without them it blocks, since an
   overlapped pipe has no partial-write mode and its write quota misleads while the child has a
   read pending (measured 2026-10-07). On other pipes `stream_set_blocking()` keeps failing
   (`plain_wrapper.c:1008-1029`).

## 11. Departures from TrueAsync

| What | TrueAsync | S6 | Why |

## 13. What S6 needs from S4

S4.3 (`b46918a`, `src/reactor.c`, `src/reactor.h`) built the reactor: heap IO events on the `waits`
list, `async_io_event_submit()`, `async_io_event_orphan()`, `async_io_record_unlink()` for a kind's
unlink, the queue created at the first submit and rebuilt in a forked child. As built in S6.3, the
provider uses it with these additions (agreed with the S4 thread):

- **A submit that returns the error**, `async_io_event_try_submit()`: `run()` needs the `errno`
  where `async_io_event_submit()` throws (3.3, step 3).
- **The install at the queue's creation** in `reactor_queue()`, which also sets `hooks.flags` from
  the new queue, and `async_io_provider_queue_destroyed()` in a forked child's rebuild, which clears
  them (section 2).
- **An IO event with trailing room** for ANY's members and results (3.4):
  `async_io_event_new_ex()`. The IO kind uses `async_io_record_unlink()` as it stands.
- **The queue without a rebuild**, `async_reactor_live_queue()`, for `add()` and `remove()`, which
  run inside stream close and free paths that cannot take a rebuild's Error (section 2).

The signal handles of section 8 come with S6.5. S4.5 created no `NotifyHandle`: the reactor keeps
its own descriptor pair per thread (S4.md 3.6), so the signal handles get their own creation.

## 16. IO chaos (S6.8)

Sections 16 and 17 cite the core S6.7 pinned, `8f89755d2b1`, under the prefixes of the header.

IO chaos is the S2 test layer "provider fault points, seeded" (`dev/plans/S2.md` section 4): in the
fuzz build (`--enable-true-async-fuzz`) `run()` sometimes answers an op the way a queue legally could
but rarely does on a loopback test machine, and the lists run once per seed. The layer is armed by
its own token, `TRUE_ASYNC_SCHED=random:<seed>:io`, which `tools/test.py --seeds N --io-chaos` passes;
a plain `random:<seed>` run is the scheduler fuzz alone, so the seed runs S3-S7 recorded keep their
meaning. The fault points draw from the scheduler's own SplitMix state (`ASYNC_G(fuzz)`): one stream
per seed, so a seed replays the same faults and picks, and a second state would only add code (the
Sage). TrueAsync arms its one IO fault hook by a variable of its own too
(`ASYNC_FUZZ_CANCELLED_WRITE`, `libuv_reactor.c`). The verdict is the seed rule: a crash, an
assertion, a sanitizer or leak report or a timeout fails a seed, a new diagnostic is listed for
reading. A normal build compiles none of it.

Each fault point keeps the op's outcome, so a listed test's expected output stays valid:

| Point | When | What `run()` does | Real case it stands for | Path it reaches |
|---|---|---|---|---|
| C1 yield before submit | any op, 1 in 4 | enqueues the coroutine and suspends before `io_wait_new()`, as the DNS lookup does; a cancellation there returns FAILURE with nothing submitted | the submit happens on a later pass | a cancellation before any submit; another coroutine changing the stream first |
| C2 late resume | a park that resumed with the event fired, 1 in 2 | delivers the result and releases the event, then enqueues and suspends once more; a cancellation in that yield gets the answers of 3.3 steps 5 and 6 | the wake was queued and a cancellation landed before the coroutine ran | steps 5 and 6 for every op type that parks, ANY included, not only the Ring batch case of `io_provider/009` |
| C3 spurious readiness | RECV, SEND, ACCEPT, or POLL, each with `PHP_IO_OP_F_AFTER_DRAIN`; 1 in 4 | answers without a submit: Ready, for a POLL Done with `res` the requested events (the queues' form, `P:390`) | a Poll queue readiness another reader consumed first | the core's ladders (`php_io_descriptor_op`, `php_io_readiness_op`, `socket_*`) retry the syscall, get `EAGAIN` and submit again |

C2 fires only after a suspend that returned true: after a cancellation a second suspend would run
with the exception pending, which the core forbids (`Hk:968-969`). The completion at submit is not a
point: on the Ring no listed test reaches it (`io_provider.c` `io_wait_submit()`'s delivery branch is
not covered by the lists, section 17). C3 needs the flag because a caller sets it after draining the
descriptor and runs the syscall again on Ready (`Hk:1226-1279, 1359-1388`, `ext/sockets/sockets.c:677`);
CONNECT also carries it (`Hk:1507-1509, 1535`) but reads `SO_ERROR` after Ready, which a false Ready
turns into a success, so the point names its op types. C3 consumes no cached readiness, since it
skips the submit (`P:338-341`, `Rg:1282-1286`). A coin of 1 in 4 ends a C3 ladder after a few rounds.

Not taken, with the reason:

- A short read or write (TrueAsync's "split a delivered chunk"): legal on TCP, but tests print what
  one `fread()` returned and protocol helpers wait for whole lines, so a seed would list output
  changes and timeouts that are no defect.
- A cancellation injected at the park: it changes every affected test's output, so the seed rule's
  list of new diagnostics turns into noise; the cancellation windows have own tests
  (`io_provider/005`, `009`, `012`, `013`, `017`) and C2 reaches the late ones.
- An Unsupported answer: the core then runs the op on the thread, and a pipe between two coroutines
  of one thread blocks for good.
- Holding a completion back in `reactor_poll()`: C2 reaches the same window inside `run()`, and the
  scheduler hook already reorders the wakes.
- A resubmit (orphan a POLL or TIMER copy and submit a fresh one in the same call), drafted as C4:
  the orphan and cancel paths it would reach already run under every cancellation test, and data
  ops are out of it anyway, since a Ring RECV kept after an orphan still writes into the stream
  buffer (`Rg:1533-1542`); the Sage dropped it as cost without a new path.

**Known answer.** A seed fails only by a crash, an assertion, a sanitizer or leak report or a
timeout, so each point is checked on a planted leak inside its own branch (for C2, the branch where
the extra yield returned a cancellation): armed with `:io`, some seed over the S6 list must fail, and
the first such seed is recorded; the same seeds without `:io` must pass. No bound on that seed is
promised in advance (the Sage): a point that never fires within the 100 seeds of the stage run, or
a C2 yield that never meets a cancellation, fails its check. Results: section 17.

**A change to 3.3 step 5 the review found (the Critic, S6.8).** Step 5 returns SUCCESS for any Done
without an error under a cancellation. For a POLL or an ANY the caller then runs its syscall anyway:
`php_io_run_cancelled()` lets a POLL through (`Hk:1102`), so a pipe `fwrite()` sends its bytes while
it throws (`Hk:1642-1660`), and `ext/sockets` retries `send()` (`sockets.c:677-682`); a SEND parked
on Ready answers FAILURE under the same cancellation and sends nothing. A readiness belongs to nobody,
so a POLL or ANY Done under a cancellation answers FAILURE as a Ready does; every other op keeps
SUCCESS, since its Done carries what the caller owns (bytes moved, an accepted descriptor, an
address list, a child's exit status, a taken signal) or no syscall follows it (a TIMER).

# S5 notes: Futures, `await()` with a cancellation, the `await_*` family

Design note of S5.1, 2026-10-05. S5 adds `Future` and `FutureState` within one thread, their
`map`/`catch`/`finally` chains, `await()` on any `Completable` with a `$cancellation`, the six
`await_*` functions over arrays and Traversables, `OperationCanceledException`, and in S5.4
`timeout()` with `TimeoutException`. Names, signatures, messages and behaviour come from TrueAsync
(`ext/async` at `tests/lists/REFERENCE`, `1fdacf8`, file names alone below) and its core API (the
fork `true-async/php-src` `863f6dd90cf`, below `F:` for `Zend/zend_async_API.h` and `F` `file:line`
for its other files); a departure is listed in section 8 with its reason. The wait-record layer
(records, their storage, unlink, the event header) is S4's (`dev/PLAN.md`, "Parallel tracks");
section 7 states what S5 needs from it, and S5 code starts once that layer is on `main`. Nothing in
this note was built or measured.

## 1. What S5 implements

| Kind | In S5 | Later |
|---|---|---|
| Classes | `FutureState` (final, no interface), `Future` (final, `Completable`), `Timeout` (final, `Completable`, private constructor; S5.4) | `RemoteFuture` and the cross-thread state: S10 |
| `FutureState` | `__construct`, `complete`, `error`, `isCompleted`, `ignore`, `getAwaitingInfo`, `getCreatedFileAndLine`, `getCreatedLocation`, `getCompletedFileAndLine`, `getCompletedLocation` (`future.stub.php:16-68`) | transfer to a thread: S10 |
| `Future` | `completed`, `failed`, `__construct(FutureState)`, `isCompleted`, `isCancelled`, `cancel`, `ignore`, `map`, `catch`, `finally`, `await(?Completable $cancellation)`, the five diagnostics (`future.stub.php:73-185`) | |
| Functions | `await($awaitable, ?Completable $cancellation)` on every `Completable`; `await_any_or_fail`, `await_first_success`, `await_all_or_fail`, `await_all`, `await_any_of_or_fail`, `await_any_of` (`async.stub.php:50-62`); `timeout()` (S5.4) | `delay()`: S4. `iterate()`: S9 (section 8) |
| Exceptions | `OperationCanceledException extends AsyncCancellation` (`exceptions.stub.php:17`); `TimeoutException extends \Exception` (`:38`; S5.4) | |

`AsyncCancellation` extends `\Error` here (D8), so `OperationCanceledException` is an `\Error` too;
in TrueAsync both descend from the fork's `\Cancellation`.

## 2. `Future` and `FutureState`

A `FutureState` is the writing end and a `Future` the reading end of one completion. Both point at
one refcounted future event, as in TrueAsync (`future.h:47-71`, F:1919-1933): three allocations for
`new Future(new FutureState)`, as TrueAsync. The event holds the outcome; a waiter, a mapper's drain
(section 3) and the objects that own it hold references to it. `new Future($state)` holds the
`FutureState` object and reads the event through it, so a user-made event has one object holder,
the `FutureState`, which the GC rule below needs; a child `Future` of a chain and the `Future` of
`completed()`/`failed()` hold their event themselves.

```c
typedef struct {                          /* 96 B (arithmetic), bin 96; the fork's zend_future_t is 184 B
                                             (optimization.md, measured) */
	async_event_t event;                  /*  0 32  S4's header: flags (bit 31), ref_count, callbacks */
	zval result;                          /* 32 16 */
	zend_object *exception;               /* 48  8  NULL: no error */
	uint32_t created_lineno;              /* 56  4 */
	uint32_t completed_lineno;            /* 60  4 */
	zend_string *created_filename;        /* 64  8 */
	zend_string *completed_filename;      /* 72  8 */
	async_future_chain_t chain;           /* 80 16  the child Future objects of map/catch/finally, in order */
} async_future_event_t;
```

The objects carry S4's reference prefix (S3.md 3.2, 3.7: `async_awaitable_from_object()` decodes
it) and the event pointer; `Future` adds the `FutureState` object it holds, or NULL, and the mapper
of a child (`zval mapper`, its kind). `chain` is an array of child objects, one reference each,
which the drain reads directly; TrueAsync keeps them in the source object's `child_futures` table
plus one subscriber (`future.c:1748-1770`), and S5 keeps them in the event, so a temporary source
still completes its chain (test `future/038`, TrueAsync issue #193). A child made by
`map`/`catch`/`finally` has no `FutureState`, as in TrueAsync (`future.c:1898-1953`).

Completion (`FutureState::complete`, `error`) follows `zend_future_resolve` (`future.c:481-512`):
refuse a second completion with `AsyncException` "FutureState is already completed at %s:%d"
(`future.c:948-958`, test `future/034`); store the result or the exception; record the completion
location; set `CLOSED`; notify `callbacks` (the waiters' records); hand a non-empty `chain` to a
drain (section 3). `Future::cancel()` does nothing on a completed future (`future.c:1276-1278`, test
`future/032`) and rejects a pending one with the given cancellation or
`AsyncCancellation("Future has been cancelled")` (`future.c:1258-1288`); `isCancelled()` is
"completed with an `AsyncCancellation`" (`:1242-1256`). `Future::completed()` and
`failed()` build a state, complete it and release it (`:1160-1225`).

**Observation flags** keep the fork's event bits (S3.md 3.7) and TrueAsync's points of setting
them. `await()` and `await_*` set `RESULT_USED` and `EXC_CAUGHT` on entry, before they wait
(`async.c:319-320`, `async_API.c:1007-1008`), and so does a Future used as a token
(`async_API.c:1257-1260`); `Future::await()` sets `RESULT_USED` (`future.c:1329`); a waiter's record
woken with an exception sets `EXCEPTION_HANDLED` (F `zend_async_API.c:1266`), which the completion
turns into `EXC_CAUGHT` (`future.c:507-509`); `map`/`catch`/`finally` set `RESULT_USED` (`:1710`),
`catch` sets `EXC_CAUGHT` when it runs, and a mapper copies its child's `EXC_CAUGHT` to the source
when it ends (`:1522-1525`); `IGNORED` comes from either `ignore()`. A Future is marked on entry,
as in TrueAsync; S3's rule for a coroutine, marked when its waiter reads the outcome, stays. The
event's last release reports what nobody observed, with TrueAsync's texts and level
(`future.c:581-654`, `async_warning`): "Future was never used; call await(), map(), catch(), finally() or ignore() to
suppress this warning. Created at %s:%d" and "Unhandled exception in Future: %s; use catch() or
ignore() to handle. Created at %s:%d, completed at %s:%d" (tests `future/022`, `024`).

**PHP GC.** An object reports the event's result, exception and every child object in `chain` only
when it holds the event's only reference; a `Future` also reports its mapper and the `FutureState`
it holds. PHP's collector subtracts one reference per reported edge and frees what reaches zero
(`zend_gc.c` `gc_mark_grey`, `gc_scan`), so an edge may be reported only by a holder that dies with
it; a waiter or a drain raises the event's count and suppresses the report while it runs, which is
safe. The core's own shared structures follow the same pattern: an SPL list iterator holds the list
object and only the list reports (`spl_dllist.c:436-447, 1173, 1189`). TrueAsync's `Future` reports
the event's contents from every `Future` (`future.c:853-880`), so two `Future` objects on one state
report one edge twice and the collector may free a result a live holder still has (found by
reading, not run; section 8, item 4). The cycle `$h->s = new FutureState; $h->f = new
Future($h->s); $h->s->complete($h); unset($h);` is collected: the `FutureState` is the event's only
holder and reports `$h`. S5.2 tests it, and two `Future` objects on one state with a cycle through
the result.

## 3. Chains without recursion

`map`, `catch` and `finally` create a child `Future` holding the callable, append it to the source
event's `chain` and mark the source `RESULT_USED` (`future.c:1678-1778`). Mappers run in a drain
coroutine, TrueAsync's chain iterator (`future.c:205-323, 1561-1615`) on S5's own queue instead of
S9's `async_iterator_t`:

- A source that completes with a non-empty `chain` starts one drain coroutine (an internal entry,
  `zend_coroutine_t.internal_entry`, R:122) over a FIFO of items, one per child: a reference to
  the completed parent's event and one to the child. The completion moves its children out of
  `chain` into the FIFO in registration order, so a completed event holds no children; the drain
  takes the next item before it calls the mapper. A source already completed when `map()` is
  called starts a drain of one item, as `future.c:1711-1736` spawns a coroutine.
- A child completed inside a drain joins that drain's FIFO instead of starting a drain
  (`future.c:1565-1582`), so the order is breadth-first, as TrueAsync's: for `$a = $f->map(A);
  $b = $a->map(B)` with a waiter on `$a`, B runs before the waiter resumes.
- On entry the drain, and every helper, arms one microtask embedded in the drain's state; at the
  next tick it spawns one helper coroutine on the same FIFO if items remain, and does nothing
  otherwise (`iterator.c:137-157, 559`); the FIFO's exhaustion cancels it (`:405-409`). Mappers that
  return without suspending therefore run in one coroutine for any fan-out, and a mapper that
  waits does not hold back its siblings: `$m1 = $f->map(function () use (&$m2) { return
  await($m2); }); $m2 = $f->map(fn($v) => $v);` completes. The last coroutine out frees the drain
  (`iterator.c:80-96`).

As built in S5.2 (`src/future.c`), after the Critic: the microtask is armed before each mapper call
that leaves items behind it, when it is not queued already, instead of once per coroutine entry. A
resumed mapper's completion may queue items after the tick found the FIFO empty; armed only at
entry, they ran in one coroutine, and `$a = $first->map(fn() => await($b))` with `$b` behind it
deadlocked (test `future/111`). An `exit()` in a mapper stops the drain: no coroutine of it takes
another item, the microtask spawns nothing, and the items left go with the drain (`future/107`);
TrueAsync's mapper turns the exit into the child's rejection (`future.c:1481-1489`). The drain holds
a reference to the child's event for the call, since the mapper may `__construct()` its child again
(`future/110`), and a second `__construct()` puts the new state in place before it lets go of the
old one, whose release may run a destructor that suspends while the child's item is queued
(`future/113`). A pending source that dies releases its chain in a loop: a child that dies with it
hands its own children over first, so a chain of any depth is released without nested frees
(`future/112`).

A notify never calls a mapper (S3.md 3.6: N chained futures must not nest N notifies): completing
a child notifies its waiters and appends it to the FIFO.

Each mapper call is TrueAsync's `process_future_mapper` (`future.c:1404-1526`): `map` is skipped
on an error and passes it on; `catch` runs only on an error, sets `EXC_CAUGHT` and
`EXCEPTION_HANDLED` on the source and completes the child with its return value; `finally` always
runs, receives the exception or the result, passes the source's outcome on unchanged and never counts
as catching (`:1446-1453`, test `future/024`); a callable that throws rejects the child, with the
source's exception chained as `previous` for `finally` (test `future/035`). The child's rejection is
the only place the error goes, and the drain goes on (section 8, item 1). A rejected child with a
non-empty `chain` counts as observed (`EXC_CAUGHT`, as TrueAsync's append sets `EXCEPTION_HANDLED`,
`future.c:1575-1582`, and the completion turns it into `EXC_CAUGHT`, `:507-509`): passing an error on
is observation, and the warning falls on the last unobserved link.

## 4. `await()` with a cancellation

`Async\await($awaitable, ?Completable $cancellation = null)` and `Future::await(?Completable
$cancellation = null)` take any `Completable` (`Coroutine`, `Future`, `Timeout`), as
`async.c:296-380` and `future.c:1304-1390`:

1. Phase 0 of the wait (S3.md 4.1, `async_wait_begin`): the refusals S3 has.
2. Mark the awaitable `RESULT_USED`; `$awaitable === $cancellation` drops the token
   (`async.c:323-325`).
3. A completed awaitable returns its result or throws its exception in place (S3's coroutine path;
   a Future from its event), before the token is looked at (`async.c:328-340`).
4. A Future token is marked `RESULT_USED` and `EXC_CAUGHT` whether or not it completed. A token
   already completed throws `OperationCanceledException("Operation has been cancelled")` with the
   token's exception, if any, as `previous` (`async_resolve_cancel_token`, `async_API.c:1253-1281`;
   tests `await/073`, `075`, `077`; a token completed during the wait: `074`, `076`, `078`).
5. Link a record on the awaitable (kind FUTURE or COROUTINE) and, with a token, a CANCELLATION
   record on it; park.
6. Woken by the awaitable: read its outcome in place, as S3's `await()` reads a coroutine's
   (`src/true_async.c` `Async_await`); mark `EXC_CAUGHT` when it delivers an exception. Woken by
   the token: the record's wake enqueues the waiter with the `OperationCanceledException` above,
   built as `zend_async_waker_callback_cancel` builds it (F `zend_async_API.c:1272-1285`).

The token's wake applies the error by S3's rule (section 6 of S3.md), so a coroutine woken by the
awaitable and the token in one tick takes one wake and one error, never two results (D26).

## 5. The `await_*` family

All six run TrueAsync's `async_await_futures` (`async_API.c:900-1170`) with these arguments
(`async.c:382-670`):

| Function | count | errors | null fill | key order | waits for the rest | returns |
|---|---|---|---|---|---|---|
| `await_any_or_fail` | 1 | throw | no | no | no | the first value, or NULL on empty input |
| `await_first_success` | 1 | collect | no | no | yes | `[result\|null, errors]` |
| `await_all_or_fail` | all | throw | yes | (ignored) | yes | results |
| `await_all` | all | collect | param | param | yes | `[results, errors]` |
| `await_any_of_or_fail` | `$count` | throw | no | param | no | results; `$count == 0` gives `[]` |
| `await_any_of` | `$count` (0 or negative: all) | collect | param | param | yes | `[results, errors]` |

Results and errors are keyed by the input's keys; "key order" keeps the input's order and drops
missing items, "null fill" keeps the input's order with NULL for them, neither gives completion
order (`async_API.c:968-973, 1143-1168`). "Waits for the rest" is TrueAsync's `cancel_on_exit`
(`async_cancel_awaited_futures`, `:800-873`): after the wait is satisfied, the waiter waits until
every still-running `Coroutine` item finishes, and their errors join the errors table; it cancels
nothing, despite its name. S5 keeps that behaviour.

**The token wins.** A token is checked before the items (section 4, step 4), and a token that
completes while the waiter is parked wins over an item completing in the same notify: an item's
wake that would satisfy the wait first tests whether the token has completed and, if so, enqueues
the waiter with the cancellation instead (test `await/071`: `await_all([$c1, $c2], $c2)` throws).
TrueAsync gets the same result from link order (the token's callback is linked before the items,
`async_API.c:945`); S5 does not rely on the order of a vector, which removal changes (S3.md 3.6).

**Arrays.** One pass before any side effect checks each element (an `Awaitable` of this extension,
or NULL, which is skipped; else "Expected item to be an Async\\Awaitable object",
`async_API.c:304-319`), marks it `RESULT_USED` and `EXC_CAUGHT` (`:1007-1008`), and takes the
outcome of every completed item in place. When that satisfies the wait, nothing is linked and no
coroutine parks (TrueAsync's fix #103, `:1122-1132`). Otherwise one heap block holds the context
(counters, flags, the two tables, the token) and one AWAIT_ITEM record per pending item, plus the
CANCELLATION record; the records are linked and the waiter parks. The input array is held for the
call, so its items outlive their records. An item's wake updates the context and self-removes; it
enqueues the waiter only when the wait is satisfied, or with the item's error when errors throw
(`async_waiting_callback`, `:370-459`). The waiter takes the block with `async_wait_take_block()`
as its suspend() returns and drops its reference through the block's `ops->release` (S4.2, N4). NULL items still count in `total`, as TrueAsync counts them (`:957, 998-1000`);
whether `await_all([$future, null])` then never finishes, S5.3 checks against the tests before
keeping it.

**Traversables.** TrueAsync iterates in a separate coroutine, so a Traversable whose own code
suspends does not hold back items already linked (`async_API.c:1067-1110, 526-631`). S5 keeps the
separate iterator coroutine and drops its scope and worker coroutines (S9's iterator): the iterator
coroutine is spawned with an internal entry and links one AWAIT_ITER record per pending item into
the waiter's wait; a completed item is taken in place, as in the array pass. Each AWAIT_ITER
record holds a reference to its item, released when the wait's block is freed, as the fork's
`resume_when` holds one per trigger (F `zend_async_API.c:1240-1242`): nothing else keeps an item a
generator has yielded alive. The records are stored in fixed chunks, never moved, since a vector
holds their addresses.

The waiter also links a COROUTINE record on the iterator coroutine, as TrueAsync does
(`async_API.c:1103`). The iterator's end, normal or with an exception, fires it: `total` becomes the
number of items seen, as `await_iterator_dispose` sets it (`:654-664`), and the waiter is enqueued
when the wait is satisfied, or with the Traversable's exception (`:644-648`); until the end,
"satisfied" is decided only by `count`, never by `total`. So `await_all(gen())` whose generator
suspends between yields waits for its end, and `await_all(new ArrayIterator([Future::completed(1)]))`
returns at the iterator's end with nothing linked.

The context and its chunks are refcounted by the waiter and the iterator coroutine (D27). `finished`
is set by whoever enqueues the waiter (an item's, the token's or the iterator's wake, or a cancel
of the waiter through the wait's unlink), not by the waiter's later exit: an iterator coroutine
that runs between the waiter's enqueue and its switch-in links nothing more. The waiter's exit
cancels the iterator coroutine and releases its reference; the iterator tests `finished` before
every link and every write and releases its reference when it ends, so a cancelled iterator still
in the run queue reads a live block.

**Cancellation** links a CANCELLATION record as in `await()`, and runs step 4 of section 4 before the
item pass. TrueAsync reaches the same outcome for a Future token completed before the call: its
`resume_when` fires the token's callback inline (`future.c:527-531`) and the error is rethrown after
the item pass (`async_API.c:1116-1120`); a finished Coroutine token is not detected there
(`coroutine.c:1021-1024`), which S5 changes (section 8, item 3).

**As built in S5.3** (`src/await.c`). `await()` and `Future::await()` check the token before every
link of their loop, so a token that completed while a foreign enqueue woke the waiter still throws;
a token's exception delivered as the previous is marked observed. `await_*` checks it once, after
the Traversable's `getIterator()`, which may complete it (`await/111`); nothing runs PHP code between
that check and the first link. Every wait holds a reference to its token's awaitable, and every
record to its trigger's (the coroutine, or the Future's event), so a Future constructed again during
the wait leaves the wait on the event it had (`await/112`). The array pass runs twice: the first
checks every trigger and counts the ones that are not null into `total`, the second marks each,
reserves its result's place and takes completed outcomes in place, and stops at the trigger that
satisfies the wait, as TrueAsync's loop does (`async_API.c:1043-1045`, `await/114`); after a trigger
that throws it goes on marking the rest, and a later trigger that has failed is thrown instead with
the error before as its previous, as TrueAsync's waker chains them (`coroutine.c:810-816`,
`await/094`, `115`). TrueAsync counts null
triggers in `total` (`:957`), so `await_all([$future, null])` never ended there; S5 does not
(`await/103`). The block holds a record per pending trigger with its key; every slot is reserved
before the first link, one per record, so a trigger that repeats or is the token too gets one per
record (`await/109`). A trigger that is the waiter is refused as `await()` refuses it (S3.md 4.1,
phase 0; `await/104`). The wait for the rest runs only after a wait that did not throw and counts the
coroutines it links: TrueAsync resumes when `resolved_count` reaches `total` (`async_API.c:511`),
which a pending Future never lets it reach (`await/106`). After a wait that parked it goes over the
triggers the wait did not take, so a coroutine that finished between the wake and the wait for the
rest gives its error to the table (`await/113`); after one that ended in place it goes over the
array, as TrueAsync's does. The token does not end it, as in TrueAsync. The iterator coroutine goes
on walking the Traversable after the wait is over, without linking or writing, until the waiter's
exit cancels it, as TrueAsync's iterator does (`await/049`); coroutines the Traversable spawned are
not cancelled with it, which needs S9's scope (`await/062` waits for S9). A Traversable's trigger that
repeats is linked again, as in an array; TrueAsync skips one already in the waker
(`async_API.c:540`). A Traversable's trigger that has completed is taken in place and may wake the
waiter while the iteration goes on; TrueAsync takes it without a wake and wakes the waiter at the
iterator's end (`async_API.c:550-558`). An enqueue that is not the wait's own (none in the extension today) ends
the family's wait with the results so far, as in TrueAsync, where `await()` waits again. The
family's errors are `AsyncException`, as TrueAsync's
`async_throw_error`; the refusal of the waiter itself stays an `Error`, as in `await()`.

## 6. `timeout()` (S5.4)

`timeout(int $ms): Awaitable` returns a `Timeout`; `$ms <= 0` throws `ValueError("Timeout value
must be greater than 0")` (`async.c:777-797`). Semantics are D32 (`timeout-semantics.md` option B):
the absolute deadline is fixed when `timeout()` returns, S4's Timer op is armed only while someone
waits, for the remaining time, and a fired `Timeout` stays fired. As a token it completes with
`TimeoutException("Timeout occurred after %lu milliseconds")` (`async.c:1622-1636`), which becomes
the `previous` of the waiter's `OperationCanceledException` (test `thread_channel/046:63`). The
armed Timer op sits on the `waits` list of `ASYNC_G(reactor)`, whose emptiness the deadlock check reads (`async_reactor_has_waits()`), so a
pending timer is no deadlock (S4.md 2.5, N7). `Timeout::cancel()` disarms; `isCompleted()` and `isCancelled()` as `async.c:1521-1564`.

**Design for S5.4** (`src/timeout.c`; after the Critic and the Sage). Every use of `timeout()` in
TrueAsync's tests is a token (`await()`, `await_*`, `signal()`, `Scope::awaitCompletion()`,
`Channel::recv()`); none awaits a `Timeout` itself or puts one among `await_*` triggers. The rules are
`timeout-semantics.md` section 5 (D32).

1. *Event.* `Timeout` is an object with S5.2's reference prefix (as `FutureState`) to a heap
   `async_timeout_event_t`: `base` (refcounted), the absolute `deadline` taken by `timeout()`
   (`php_io_deadline_from_ms`, an infinite one clamped as `async_reactor_delay` clamps it), `ms` for
   the message, `subscriber_count`, the armed `timer` (an S4 IO event with a TIMER op, NULL while
   disarmed), `timer_callback` (an `async_event_callback_t` inside the event, a plain subscriber of
   `timer`'s vector) and `exception` (the argument of `cancel()`). `ASYNC_TIMEOUT_F_TIMEOUT` is
   bit 30, set on every Timeout event and never on a future event, so `src/await.c`, which reads only
   those two, tells them apart: `await_outcome`, `async_awaitable_release`, `async_await_token_check`
   and the token record's info branch on it.
2. *Check.* `async_await_token_check()` on a Timeout fires it in place when its deadline is not later
   than the clock (D32 rule 4), then throws as for any completed token. It arms nothing.
3. *Subscribe.* `async_timeout_subscribe()` counts a subscriber and arms at 0 to 1: it makes the IO
   event, pushes `timer_callback` into its reserved slot and submits, holding a reference to the IO
   event across the submit, which may complete it at once; after it the Timeout's own `CLOSED` decides,
   and a fired Timeout throws as the check does. It allocates and may throw, so a wait calls it after
   its reservations and right before its first link (`await()`, `Future::await()`, `await_array`,
   `await_traversable`), never for a wait that ends in place: a bailout in a reservation leaves no
   armed timer that nothing unsubscribes (`await/127`). A subscription holds a reference to the event.
   `async_timeout_unsubscribe()` counts down, disarms at 1 to 0 and drops it. The
   TIMEOUT token kind's unlink is the generic removal plus the unsubscribe; any other holder (S6.5's
   `signal()`, which waits with a callback and no coroutine) uses the pair itself.
4. *Fire.* One `timeout_fire(event, exception)` for every path (the timer's callback, a passed
   deadline found by the check or by `isCompleted()`, `cancel()`): under a reference of its own it
   disarms an armed timer (orphan, remove `timer_callback`, release), keeps `exception`, sets `CLOSED`
   and notifies its records. Every waiter, then or later, gets `OperationCanceledException` whose
   `previous` is a `TimeoutException("Timeout occurred after %d milliseconds")` made for that wait
   (D32 rule 5; TrueAsync makes one per fire and loses it for a later use, `timeout-semantics.md`
   section 1). One kept exception would be shared: the engine's chaining onto a thrown exception
   (a `finally` with another one in flight) writes into its tail, and every later use would carry it
   (`await/117`).
5. *Cancel.* `cancel(?AsyncCancellation $cancellation = null)` fires with `$cancellation`, or with no
   exception, and sets `ASYNC_TIMEOUT_F_CANCELLED`: later uses throw at once and linked waiters wake
   with `OperationCanceledException` (D32 rule 7). `isCompleted()` is true once fired, cancelled or
   past the deadline (firing it then), `isCancelled()` only after `cancel()`. TrueAsync ignores the
   argument and reads a NULL event at a later use. The argument itself is shared by every wait, so
   what the engine chains onto one reaches the next and the user's object (point 4): kept, as a
   Future token shares its exception (section 4), since a copy would break `getPrevious() ===
   $cancellation`.
6. *Awaited itself.* `await($timeout)` and a `Timeout` among `await_*` triggers throw
   `Error("Async\Timeout can only be used as a cancellation token")` until a test needs them:
   TrueAsync accepts both, untested.
7. *Lifetime.* The object holds one reference to the event, each wait's hold one, each subscription
   one, and the event holds `timer`. Freeing the object does not cancel: a wait that outlives it still
   times out. An armed timer always has a subscription, so the last release never meets one.
   `exception` is reported to the GC by the object while it is the event's sole holder, as S5.2's
   events are.
8. *Order and fork.* `await()` reads a finished awaitable before its token (D32 rule 4); `await_*`
   checks its token first, as TrueAsync and S5.3 do. A Timeout armed before `fork()` keeps a `timer`
   whose op the child's rebuild drops. The rebuild runs lazily, so a subscribe that finds a `timer`
   runs the reactor's fork check first (`async_reactor_check_fork()`) and re-arms a `timer` that is
   off the reactor's lists (`await/124`). A parent's wait parked across the fork on the Timeout then
   ends at the deadline in the child too, being linked to the Timeout, not to the op; with no wait
   in the child to re-arm it, it ends as S4's parent waits do (S4.md 3.1).

## 7. S5's kinds and what S5 needs from S4's layer

S5's kinds, with their wake functions in S5's files (`future.c`, `await.c`):

| Kind | Target | Wake | Self-removes |
|---|---|---|---|
| FUTURE | a future event's `callbacks` | enqueue the waiter | yes (one-shot) |
| CANCELLATION | the token's vector (coroutine or event) | enqueue the waiter with `OperationCanceledException` | yes |
| AWAIT_ITEM | an item's vector | update the context; enqueue at the end or on a thrown error | yes |
| AWAIT_ITER | as AWAIT_ITEM, linked by the iterator coroutine into chunks; holds a reference to its item | as AWAIT_ITEM | yes |
| COROUTINE on the iterator | the iterator coroutine's vector | fix `total`; enqueue when satisfied or with the iterator's exception | yes |
| TIMEOUT (S5.4) | the `Timeout` event | enqueue with the cancellation; disarm at 1 to 0 subscribers | yes; on the reactor's `waits` while armed |

A chain (section 3) is an array of child objects in the future event, not a set of records; the
drain's helper is a microtask, as the scheduler runs them today (`src/scheduler.c`).

Needs, numbered for S4.1's answers:

- **N1. Event header and future event.** S4's `async_event_t` with bit 31, a `ref_count` (the
  future event is shared by its holders and lives on through waiters and drains), the callbacks
  vector, and the bits `CLOSED`, `RESULT_USED`, `EXC_CAUGHT`, `EXCEPTION_HANDLED` at the fork's
  positions (S3.md 3.7), plus one free subtype bit for `IGNORED` (the mapper kind stays on the
  child `Future` object). The object prefix and `async_awaitable_from_object()` (S3.md 3.2).
- **N2. Unlink of a record on an event.** Today's `async_wait_unlink` removes a record from a
  coroutine's vector only (`src/true_async_API.c:172-188`); S5's records sit on events too, so the
  unlink picks the vector by the target's bit 31.
- **N3. A wait of two records with no allocation**: `await($x, $token)` and `Future::await($token)`
  link the target and the token. The reference keeps two inline callback slots in its waker
  (`ZEND_ASYNC_WAKER_INLINE_SLOTS 2`, F:1704; F `zend_async_API.c:1134-1146`), so D2 allows no
  allocation here.
- **N4. A wait of N records in a heap block** the waiting coroutine points at: unlinked by every
  unlink site (U1, U2, U4, finalize's U6), then released, not freed: the waiter's reference goes
  after its exit, or in finalize after a bailout, and an AWAIT_ITER block keeps the iterator
  coroutine's reference too. The block also holds S5's context; S4 decides whether the waker
  points at it or the coroutine does. As built by S4.2: `waker.block` points at a head with const
  `ops {unlink, release, walk}`, which S5 embeds in its `await_*` block; the waiter takes it with
  `async_wait_take_block()`, and `async_wait_end()` releases one a bailout left.
- **N5. Records added to a live wait by another coroutine** (AWAIT_ITER): the iterator coroutine
  links into the waiter's block while the waiter is parked; the unlink walks the chunks. The unlink
  of such a wait calls S5's hook, which sets `finished`, so a cancel of the waiter by any path ends
  the linking, and nothing is linked after the waiter is enqueued. As built by S4.2: S5 sets
  `finished` in its `ops->unlink`; records link with `async_wait_link(record, coroutine, target,
  kind, wake)`.
- **N6. Gathering waits keep their records** until satisfied (D26): an AWAIT_ITEM wake that does
  not enqueue leaves the other records linked; an enqueue of the waiter, by any record or a cancel,
  unlinks them all.
- **N7. Counted records** (`F_COUNTED`) for TIMEOUT, and the arm at 0 to 1 and disarm at 1 to 0
  subscribers of a `Timeout` (S3.md 4.8 `ARM_ON_WAIT`), for S5.4. S4.1's answer: no `F_COUNTED`; an
  armed Timer op sits on the `waits` list of `ASYNC_G(reactor)`, TIMEOUT submits at 0 to 1 subscribers, and its
  kind's unlink cancels the op at 1 to 0 if it has not fired.
- **N8. Awaiting info per record**: `getAwaitingInfo()` of a coroutine parked on a future reads
  `await: future` beside S3's `await: coroutine #<id>`; `Future::getAwaitingInfo()` keeps
  TrueAsync's `FutureState(completed|pending)` (`future.c:574-579`).
- **N9. Teardown of a future event's vector with a record left** (a throwing callback ended the
  notify) wakes the waiter, which reads the completed future, as S3 does for a coroutine (S3.md
  4.4 "As built").

## 8. Departures from TrueAsync

1. **The mapper's error goes only into the child** (section 3), and the child's release reports it
   when nobody observed it. TrueAsync has two paths, both different. A pending source: it sets
   `EG(exception)` in the iterator when no waiter handled the child's error (`future.c:1497-1499`),
   which stops the iterator (`iterator.c:510-513`) and cancels the scope captured at `map()` time
   with "Cancellation of the iterator due to an exception" (`iterator.c:605-613`); the error itself
   is then released silently (`iterator.c:118-122, 199-203`), and the child's release still warns. A
   completed source: the error stays in the mapper coroutine and ends it as an uncaught exception
   (`future.c:1662-1666`), while a later `await($child)` delivers it again. No ported test covers
   either path (the Sage read `future/004`, `005`, `009`, `010`, `012`-`014`, `024`, `035`, `036`);
   Edmond may veto this one.
2. **No `async_iterator_t` or Scope for chains and Traversables** (sections 3, 5): S9 owns Scope,
   the iterator and `iterate()`; the chain drain and its helper microtask copy what the iterator
   does for chains. `iterate()` moves to S9 with them: it cancels pending coroutines
   spawned by its callable (`$cancelPending`, `async.c:1086-1092`), which needs a Scope, and runs
   `$concurrency` workers (`iterate/012`, `013`, `016`-`018`).
3. **`await_*` detects a finished Coroutine token before the call** (section 5): TrueAsync detects a
   completed Future token but not a Coroutine one (`coroutine.c:1021-1024` only pushes the
   callback). S5 checks both, before the item pass.
4. **GC reports the shared event only from its sole holder, and `new Future($state)` holds the
   `FutureState` object** (section 2): TrueAsync's `Future::get_gc` over-reports when two `Future`
   objects share one state. The `FutureState` object now lives while a `Future` on it lives;
   TrueAsync frees it on the user's `unset()` (`future.c:1154-1157`). No destructor or test observes
   the difference.
5. **The Traversable path cannot link a departed waiter** (D27, S3.md section 13, bug 5): the
   context is refcounted and `finished` is tested before every link (`async_API.c:540, 618, 662`
   wrote into a cleaned or reused waker; `:1170` freed a context the iterator still read).
6. **Awaiting info names the target**: `await: future` (N8); TrueAsync's `get_awaiting_info` is a
   TODO (`async_API.c:248-250`).
7. **`await_any_of` builds its tables after the scheduler launch** (`async.c:637-640` allocated
   them before and leaked them when the launch threw).
8. **`Future` and `FutureState` refuse `clone`, and a second `Future::__construct()` lets go of what
   the first gave** (S5.2): TrueAsync's standard clone gives a `Future` with no event and a
   `FutureState` with a new one, and its second `__construct()` keeps a reference it never drops
   (`future.c:1138-1158`).
9. **The drain's arming, stop on `exit()` and chain release** (section 3, "As built in S5.2").
10. **`await_*` skips null triggers in `total`, refuses the waiter among its triggers, checks the
    token after `getIterator()`, and its wait for the rest counts the coroutines it links and keeps
    the errors of those that finished since the wake; a Traversable's repeated trigger is linked
    again and its completed trigger may wake the waiter mid-iteration** (section 5, "As built in
    S5.3").
11. **A `Timeout` follows D32** (section 6, "Design for S5.4"): one deadline from `timeout()` for every
    use, armed only while a wait is parked on it, fired for good with a `TimeoutException` of its own
    for every later use, `cancel()` terminal and waking its waiters with its argument as the
    `previous`; awaiting a `Timeout` itself is refused. TrueAsync restarts the timer per wait, loses
    the exception after the fire, ignores `cancel()`'s argument and accepts an awaited `Timeout`,
    untested.

Kept as TrueAsync, worth a later look by Edmond, not changed here: `cancel_on_exit` waits for the
remaining coroutines instead of cancelling them (section 5), and that wait does not link the token,
so `await_first_success([$fast, $slow], timeout(100))` returns when `$slow` ends, past the deadline
(D32 rule 3 reads "every use"; the Critic on S5.4); `Future::isCompleted()` is false on a
`Future` with no event (`future.c:1227-1240`), an `unserialize()`d one in S5.2, where a `FutureState`
always has its event.

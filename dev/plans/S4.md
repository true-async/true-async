# S4 notes: the reactor on `php_io_queue`

The reactor is one `php_io_queue` per thread and request (the Ring when the core is built with ior,
the Poll queue otherwise) that the scheduler parks in when nothing is runnable and polls without
blocking while coroutines run; its completions wake coroutines through the wait-record layer, which
this note also designs for S5 (section 2.5 answers S5's needs N1-N9). S4 adds `Async\delay()`, the
idle wait, deadlock decided from the reactor's own list of waits that something outside the run
queue will end, timers, cross-thread wakeup, and the queue rebuilt after `fork()`. The S6 provider
submits its ops to the same queue, so section 3.2 designs completion dispatch for both.

Sources: the pinned core `async-core-io-2026-10-05-4` `9531d5b0b1f`: `main/php_io_hooks.h` below
`H:`, `main/io/php_io_queue_poll.c` below `P:`, `main/io/php_io_ring.c` below `Rg:`,
`main/io/php_io_hooks.c` below `Hk:`, `main/poll/poll_core.c` below `Pc:`, `ext/standard/io_poll.c`
below `Ip:`; ior `2fb12e8ce01` (`src/ior_iocp.c`); the fork core `true-async/php-src` `863f6dd90cf`:
`Zend/zend_async_API.h` below `F:`, `Zend/zend_async_API.c` below `Fc:`; the reference `ext/async`

## 1. What S4 implements

| Kind | In S4 | Later |
|---|---|---|
| Functions | `Async\delay(int $ms)` | `timeout()`: S5.4, on the Timer event of 3.5 |
| Waits | TIMER (a Timer op), TRIGGER (cross-thread wakeup) | FUTURE, CANCELLATION, AWAIT_ITEM, AWAIT_ITER, TIMEOUT (S5); provider ops (S6); CHANNEL (S9) |
| Reactor | the per-thread queue, the idle wait, the tick's poll, dispatch, the external-wait lists, fork, `EINTR`, the D16 deadline | signals and child processes through `SigWait`/`WaitPid` (S6) |
| Test functions | `TrueAsync\Test\wake_from_thread()` (S4.5); a test wait of N records (S4.2) | |

`delay($ms)` parks the current coroutine for `$ms` milliseconds. `$ms === 0` is a yield, as TrueAsync
(`async.c:688-690`): an enqueue of the current coroutine and a park. `$ms < 0` throws `ValueError`
("must be greater than or equal to 0"), a departure: TrueAsync casts it to `zend_ulong`
(`Fc:1303-1318`) and arms a timer of about 49 days (`libuv_reactor.c:1161-1178` saturates at
`UINT_MAX` ms); no reference test passes a negative value. With no current coroutine (after the
scheduler's deactivation) it returns at once, as TrueAsync (`async.c:684-686`). Otherwise it runs
phase 0 of S3.md 4.1 (`async_wait_begin`), so it refuses in scheduler context with the reference's
text.

## 2. The wait-record layer

S4 owns the layer (`DECISIONS.md` 2026-10-05): the event header, the record and its kind, the
storage of a wait of several records, link and unlink. S5 writes its own events (Future, Timeout)
and kinds on top of it.

### 2.1 Events and kinds (D25 decided as D28)

An event is any awaitable that is not a coroutine (bit 31 of `flags`, S3.md 3.2), with S3.md 3.7's
header and no methods (D28):

```c
struct _async_event_s {                                  /* 32 B */
	uint32_t flags;                                      /*  0 4  bit 31 = 1; S3.md 3.7 positions */
	union { uint32_t ref_count; uint32_t object_offset; }; /* 4 4  ZEND_OBJ selects */
	async_callbacks_vector_t callbacks;                  /*  8 24  S3.md 3.6 */
};
```

S4.2 defines the flags at the fork's positions that S4 and S5 use: 0 `CLOSED`, 1 `RESULT_USED`, 2
`EXC_CAUGHT`, 4 `ZEND_OBJ`, 6 `EXCEPTION_HANDLED`, and 13-30 for a type's own bits (S5's `IGNORED`
takes 13). The fork's 8 `ARM_ON_WAIT` and 10 `HIDDEN` stay unassigned: arming is the kind's (below),
and a hidden event is one the reactor keeps out of its lists of waits (3.4).

The per-type behaviour of a wait sits on its record's kind, S3.md 3.5 with the names D30 accepted:

```c
typedef struct _async_wait_kind_s {                      /* one const table per kind, .rodata */
	zend_string *(*info)(async_coroutine_event_callback_t *record);  /* one getAwaitingInfo() line */
	void (*unlink)(async_coroutine_event_callback_t *record);        /* F_TYPED; NULL = vector removal */
	void (*abort)(async_coroutine_event_callback_t *record);         /* D29, S9; NULL = nothing */
	/* S7 adds `completers`, the walk of the wait graph */
} async_wait_kind_t;

struct _async_event_callback_s {                         /* 24 B */
	uint32_t flags;                                      /* F_RECORD, F_TYPED */
	async_event_callback_fn callback;                    /* the wake function */
	union {
		async_event_callback_dispose_fn dispose;         /* a heap subscriber */
		const async_wait_kind_t *kind;                   /* a record (F_RECORD): never disposed */
	};
};
```

A record's `dispose` is NULL today and never called (`async_callbacks_free` skips `F_RECORD`), so the
kind costs no byte. `ASYNC_CALLBACK_F_TYPED` says `kind->unlink` is set, which spares the generic
unlink two loads; `F_COUNTED` does not come back (3.4 replaces the count with a list). Why kinds and
not TrueAsync's event methods: Edmond's D28 ("no event methods"), the wake function already sits on
each subscriber, and what a wait does with its target is decided by the code that links it, which
knows the target's type. S3's coroutine wait gets the COROUTINE kind (info only).

### 2.2 The waker: two records inline, a block past two

```c
typedef struct _async_wait_block_s async_wait_block_t;

typedef struct {
	void (*unlink)(async_wait_block_t *block);   /* unlinks every record the block holds; idempotent */
	void (*release)(async_wait_block_t *block);  /* drops the waiter's reference */
} async_wait_block_ops_t;

struct _async_wait_block_s {                     /* the head of a stage's own block */
	const async_wait_block_ops_t *ops;
};

typedef struct {                                         /* 112 B */
	zend_object *error;                                  /*   0  8 */
	zval result;                                         /*   8 16 */
	async_coroutine_event_callback_t records[2];         /*  24 80  linked while `event` is set */
	async_wait_block_t *block;                           /* 104  8  records past two; NULL when none */
} async_waker_t;
```

A wait of one or two targets (`delay()`, `await($x)`, `await($x, $token)`) uses `records[]` and
allocates nothing, as TrueAsync's `inline_callbacks[2]` (`F:1704, 1730`; S5's N3). A wait of more
uses a block that its stage allocates and embeds the head in: S5's `await_*` block holds its context,
its AWAIT_ITEM records or AWAIT_ITER chunks and its own reference count (N4, N5). The layer never
walks a block itself; it calls `ops->unlink`, which removes every record the block holds and is where
S5 sets `finished`. TrueAsync allocates one record per target past the second (`Fc:1136-1147`); one
block per wait saves N − 1 allocations. The coroutine grows from 424 B (allocation 408, bin 448) to
472 B (allocation 456, bin 512), still below the reference's 640 bin; S4.2 measures B1 again against
D2.

### 2.3 Phases

The phases of S3.md 4.1 hold; S4 fills phases 2-4 and the unlink of 4.4:

- Phase 2, `async_wait_reserve(coroutine)`: releases a block a previous wait left, then each linker
  reserves one slot in its target's `callbacks` (`async_callbacks_reserve`) before the first link. May
  bail out: nothing is linked yet.
- Phase 3, `async_wait_link(record, coroutine, target, kind, callback)`: the stores of S3.md 4.1 into
  a record in `records[]` or a block, and a push into the reserved slot. The record is passed in, so
  S5's iterator coroutine links into a parked waiter's block (N5).
- Phase 4 arms, after every record of the wait is linked: a kind whose target needs a submitted op
  (TIMER, TIMEOUT, an S6 op) submits it, so a submitted op always has a linked record to wake. An op
  the queue completed at submit (`take_inline`, `H:387-389`, which takes it out of the completions a
  wait delivers) is completed by the waiter after its last submit, before the park, so its wake and
  the enqueue's unlink find the whole wait linked (the Sage: a completion inside the arm of the first
  target would end the wait while later targets were still unlinked). A TIMEOUT is armed when its
  `callbacks` length goes from 0 to 1, so `await_any([$t, $t])` arms it once (N7). A failed submit
  unlinks the wait and throws `Error` with the system message.
- `async_wait_unlink(coroutine)`: for each of `records[]` with `event` set, `kind->unlink` when
  `F_TYPED`, else removal from the target's vector picked by bit 31 (N2) and `event = NULL`; then
  `block->ops->unlink` when there is a block. Idempotent; allocates nothing and runs no PHP code. The
  block stays: the waiter takes it with `async_wait_take_block(coroutine)` as its `suspend()` returns,
  reads S5's results from it and releases it; finalize (U6) and the next wait's phase 2 release one a
  bailout left with `async_wait_end(coroutine)` (N4). Every hand-over and release sets `block =
  NULL`, and `ops->release` reads nothing from the waker: S5's iterator coroutine may still hold the
  block's own reference.
- `async_wait_abort(coroutine)` at U4, finalize and U6, where the frame never runs again: `kind->abort` for
  each record that has one, then the unlink. No kind has an abort before S9's CHANNEL (D29).
- A record's wake only enqueues or records: a wake that enqueues leaves the unlink to the enqueue,
  which unlinks the whole wait at once (D26, U1, U2), as the as-built `await_record_wake` does; a
  gathering record that does not satisfy its wait may unlink itself and leaves the others linked
  (N6). A TIMER kind's
  `unlink` orphans the op when it has not fired, takes the event off the `waits` list and drops
  the record's reference; the notify holds its own reference, so the event outlives its last record
  inside the notify.

**As built** (S4.2, 2026-10-05): `src/true_async_API.h` and `.c`, `src/coroutine.h`. Phase 2 starts
with `async_wait_end(coroutine)`, which unlinks a wait a bailout left and releases a block left in
the waker, and each linker then reserves on its targets' vectors itself (a target twice in one wait
reserves twice); there is no `async_wait_reserve`. The waiter takes its block with
`async_wait_take_block()` as its `suspend()` returns and releases it when it has read its outcome, so
a wait it starts meanwhile (a destructor's `await()`) finds no block to end (the Critic); no PHP code
runs in the waiter between its first link and its `suspend()`. The waker's two records and a block
may serve one wait together (S5's cancellation record beside its items). The block's ops also have
`walk`, which visits its linked records for the awaiting info (and S7's walk later); its `unlink`
returns at once once it ran, and its `release` may run PHP code, its `unlink` may not.
`async_wait_record_unlink()` unlinks one record by its kind, `async_wait_record_remove()` is the
generic removal a kind's unlink calls first, and a target's teardown unlinks a record left there by
its kind too, so a TIMEOUT disarms (the Critic). `async_wait_abort()` runs at U4, at the finish of a
coroutine with a record still linked (its frame is gone) and for every coroutine at the request's
end, and aborts the waker's two records only: no kind S5 links into a block needs an abort, and no
kind has one before S9; a channel wait in a block (S9) would need an `abort` in the block's ops.
A wake run by a target's teardown finds its record unlinked already (`event` NULL), and nothing may
run PHP code in the waiter between its wake and `async_wait_take_block()`: `suspend()`'s error exit
drops `waker.result`, which nothing sets yet, so whoever sets it moves that drop past the call (the
Sage). `async_wait_unlink()` and the finish test inline that nothing is linked
before they call out (`async_wait_is_empty()`). `completers` is not in the kind table: S7 adds it with
its walk. `ASYNC_CALLBACK_F_TYPED` is bit 1. The event header, its flags, the reference prefix and
`async_awaitable_from_object()` are in the header; no event type of the extension uses them before
S4.4 and S5.2, so `TrueAsync\Test\Event` (the test hooks) drives the layer's tests,
`tests/internal/052`-`061`. B1: 7.5 instructions more per spawn, no allocation more
(`dev/BENCHMARKS.md`).

## 3. The reactor

### 3.1 The queue

`async_reactor_queue()` returns the thread's queue and creates it on first use, so a request with no
timer and no IO never creates one, as TrueAsync starts libuv lazily (`libuv_reactor.c:343-349,
387-409`). With `HAVE_IOR` it calls `php_io_queue_create_ring(0)` (256 entries,
`PHP_IO_RING_DEFAULT_ENTRIES`, `main/php_io_ring.h:28`) and falls back to `php_io_queue_create_poll(PHP_POLL_BACKEND_AUTO)`
(`H:408`) when the ring cannot be created; without ior it creates the Poll queue. Both allocate with
`ecalloc`, so the queue lives in `ASYNC_G(reactor_queue)` for one request and is destroyed at
RSHUTDOWN (3.7); the ior library chooses its backend itself (io_uring, IOCP or threads, `Rg:214`).

**Fork.** The core has no fork hook for the scheduler (`Zend/zend_async_API.h` has no fork entry;
TrueAsync registers `zend_async_fork_register`, `async.c:1807`, refuses `fork()` while other
coroutines exist, `async.c:1754-1776`, and rebuilds libuv in the child with
`libuv_after_fork_child`, `libuv_reactor.c:438`). `pcntl_fork()` itself refuses while a `php_io_run` frame is
in flight and makes the child forget the parent's rings (`php_io_child_forget(0)`); in the child the
Ring answers `EPERM` for a ring of the parent (submit `Rg:1305`, wait `Rg:1922-1925`) and a Poll context
`PHP_POLL_ERR_PERMISSION` (`Pc:450-465`). The reactor keeps no pid of its own: a submit or a wait that
gets that answer rebuilds. It destroys the old queue (an op of a forgotten ring is cleared of its
`queue` and `queue_data` first, so nothing reaches the parent's ring), creates a new one, replaces the
wakeup `NotifyHandle` (3.6), whose descriptor the parent shares, and empties both lists of 3.4
without resubmitting anything: a wait the parent started does not run twice. A child's
own `delay()` works; a coroutine the parent left waiting on a timer or a trigger ends in the child's
deadlock resolution, which names its wait. TrueAsync never reaches that state (it refuses the fork),
and the core's own answer for a child is that nothing of the parent completes there (`Rg:1469`,
`Hk:726-744`). Provider ops are never pending at a fork: `pcntl_fork()` refuses while one is in
flight. A fork hook in the scheduler
RFC is an S8 change-request candidate.

### 3.2 IO events: one dispatch for scheduler ops and provider ops

Every op the reactor submits belongs to an IO event, and the event is the `data` of the submit:

```c
typedef struct _async_io_event_s {
	async_event_t base;                                  /* ref_count: the records, the dispatch */
	php_io_op op;                                        /* a Timer or POLL op of the reactor */
	php_io_op_result result;                             /* written by the dispatch before the notify */
	void (*complete)(struct _async_io_event_s *event);   /* NULL: the default below */
	struct _async_io_event_s *prev, *next;               /* the reactor's list of waits (3.4) */
} async_io_event_t;
```

The events are on the heap, as TrueAsync's timer event (`Fc:1318`): the TIMER record owns one
reference, so an event outlives a bailout that unwinds the frame of `delay()` until U4 or U6 unlinks
the record. `async_io_event_submit(event)` calls `queue->ops->submit(queue, &event->op, event)`; an op
completed at submit (`take_inline`) completes the event before the park. A failed submit throws
`Error` with `strerror()`. Orphaning an op calls `op->queue->ops->orphan(op->queue, op)`, which is a
cancel on both queues and also keeps a stream frozen on the Ring while the backend still holds its
buffer (`P:693-705`, `Rg:1469-1486`); a cancelled op produces no completion on either queue
(`P:502-530`, `Rg:1437-1467`).

The S6 provider's `run()` gets an op from the core on its own frame (`H:217`), so its event cannot
own the op the way a TIMER does. A bailout out of the tick while `run()` is parked unwinds that frame
(the `zend_try` around a coroutine's body, `coroutine.c:347-373`) before the finalize unlinks
(`:394-396`), and the queue would then hold a pointer into a dead frame. M12's answer, a `zend_try`
around the park inside `run()`, needs Edmond's word (a `zend_try` on a hot path); S6.2 decides it,
and S4.2's tests cover a bailout out of the tick for S4's own waits.

The zend_try-free option to put before Edmond in S6.2: the provider's event owns a heap op, copied
from the core's at submit, and copies the result back after the wake, the TIMER pattern; the frame
then holds nothing the queue points to.

**Dispatch.** `reactor_poll(deadline)` takes completions one at a time:
`queue->ops->wait(queue, &completion, 1, deadline)` until it returns 0, with the given deadline on
the first call and a non-blocking one (0) after. For each, under a reference the dispatch holds:
`result` is written, then `complete(event)` runs, by default marking the event `CLOSED`, taking it
off the `waits` list and running `async_callbacks_notify()` in scheduler context. One
completion per call is the rule because a notify may orphan another event's op (a woken coroutine's
unlink) whose completion would already sit in a batch; both queues answer from their ready list
without a system call (`P:634-636`, `Rg:1943-1944`), and the Poll queue still reaps up to
several descriptors per system call into an event buffer that grows to the `max` asked (`P:628-631`;
one completion per call keeps it at `PHP_IO_POLL_MIN_EVENTS`, `P:785`). The Ring's wait calls `getpid()` and
a progress pass on every call; S4.4 measures that cost with D26's N waiters of one deadline. An
exception left by a notify becomes the exit exception, as one left by a microtask (`scheduler_tick`).

### 3.3 Where the scheduler polls and parks

- **The tick** (`scheduler_tick`, the suspending fiber's and the scheduler coroutine's) polls once
  without blocking after the microtasks when a queue exists and 100 ms passed since its last poll on
  `CLOCK_MONOTONIC_COARSE` (`zend_hrtime()` elsewhere): TrueAsync's throttle (`scheduler.c:1547-1565`,
  `REACTOR_CHECK_INTERVAL`, `php_async.h:56`). A coroutine that yields in a loop therefore delays a due
  timer by up to 100 ms, as in TrueAsync.
- **The context loop** (`run_coroutines`, `scheduler_loop`) polls without blocking once per coarse
  clock tick, as TrueAsync's `fiber_entry` loop, so a run queue that never empties still sees its
  timers.
- **The idle wait** is in `scheduler_loop`, the one place where nothing is queued and no microtask is
  left: with either list of 3.4 non-empty it calls `reactor_poll(infinite)` and loops; with the
  lists empty it goes to `registry_waiting_count()` and the deadlock resolution of S3.8 as today. A
  suspend with an empty run queue already switches into the scheduler coroutine (S3.md 5), so there
  is one blocking site; TrueAsync also blocks inside the suspending fiber's tick
  (`scheduler.c:1563-1565`), which saves one switch on a path that blocks anyway.
- **`EDEADLK`** from the wait (the Poll queue's answer when no op has a descriptor or a finite
  deadline, `P:640-644`) goes to the deadlock resolution as an empty list does.
- **Interrupts.** Before it blocks, the idle wait checks `php_io_interrupt_pending()` (`Hk:38-41`:
  `EG(vm_interrupt)` or pcntl's pending flag). The wait itself returns `EINTR` only when a signal
  interrupted it and that check holds (`Pc:581-593`, `Rg:1979`), so it cannot spin. With
  `EG(vm_interrupt)` set and nothing runnable no opcode would run it (M5), so the loop starts an
  internal coroutine (the core's `internal_entry`, as the GC coroutine is started) that does what the
  VM's interrupt helper does (`zend_vm_def.h:10718-10730`): clears the flag, then `zend_timeout()` when
  `EG(timed_out)`, else `zend_interrupt_function()`. A pcntl handler therefore runs in a coroutine and
  may wait, and `max_execution_time` ends a request whose coroutines all wait. One such coroutine runs
  at a time: a signal during its handler sets the flag again, and the next idle pass starts the
  next. A signal that lands
  between the check and the system call waits for the next wake; closing that window needs the core
  to block with the signal mask (`ppoll`, `io_uring_enter` with a mask), an S8 candidate. With only
  pcntl's own pending flag (`pcntl.async_signals` off) nothing is started: the script dispatches its
  signals itself, as without async. TrueAsync never sees `EINTR`: libuv retries it
  (`src/unix/linux.c:1486`).

### 3.4 The external-wait lists and deadlock

The reactor's state is one struct in `ASYNC_G(reactor)`: the queue, the `NotifyHandle` and its
event, the time of the last poll, and two intrusive lists of waits that something outside the run
queue will end. `waits` holds the IO events whose op is submitted and waited for (TIMER, an armed
TIMEOUT, an S6 op); `triggers` holds the triggers with a waiter (3.6), which the wakeup also walks.
The reactor's own ops (the wakeup POLL, the D16 timer) are on neither, as TrueAsync's `HIDDEN`
events never count. Together they answer what TrueAsync's `ZEND_ASYNC_ACTIVE_EVENT_COUNT` answers
(`scheduler.c:1849`). The `waits` list also gives the fork rebuild what to take off (3.1) and RSHUTDOWN what to orphan (3.7), which a counter could not; their
emptiness is the deadlock test, so no counter is kept. Linking and unlinking cost what a counter's
increment and decrement cost, on arm and disarm, never on the notify path.

Deadlock resolution therefore runs when nothing is queued, no microtask is left and both lists are
empty, or when the wait answers `EDEADLK`. The queue's own `count_pending()` cannot decide it: the
permanently armed wakeup op keeps it above 0 (M5), a Ring keeps orphans until the backend frees them,
and the Poll queue's `EDEADLK` rule is about descriptors. A Future, a channel or a coroutine is never
on a list, so a coroutine awaiting a Future nobody can complete is a deadlock at once, as in
TrueAsync.

### 3.5 Timers

`delay($ms)` allocates a TIMER event with `php_io_op_timer(&event->op,
php_io_deadline_from_ms(ms))` (`H:130, 413-448`), links one record of kind TIMER, submits (phase 4),
puts the event on the `waits` list and parks. The fire closes the event and wakes the waiter; a cancel
unlinks, and the TIMER kind's `unlink` orphans the op. The deadline is absolute on `zend_hrtime()`
(`CLOCK_MONOTONIC_RAW` where it exists); the Poll queue keeps it in its timer heap (`P:315-320`), the
Ring converts it to a relative `ior_prep_timeout` at submit (`Rg:822-828`).

The Timer event is the base of S5's Timeout: an `async_io_event_t` inside the `Timeout` object, armed
by the TIMEOUT kind for the remainder of the deadline fixed by `timeout()` (D32) and disarmed by its
`unlink` (2.3); S5.4 writes it on this event.

**The D16 deadline.** When `exit()` (or an exit exception) starts the graceful shutdown and other
coroutines exist, the scheduler submits one Timer op of 5 s, on no list, so a deadlock during
the shutdown is still resolved at once. When it fires and coroutines are still alive, every one of
them is cancelled with the engine's graceful exit (`zend_create_graceful_exit()`, as S3.9 closes a
dropped Fiber) with `PROTECTED` cleared, so a `protect()` block does not hold the request: finally
blocks run and no `catch` sees it. It is orphaned at RSHUTDOWN when it has not fired.

### 3.6 Cross-thread wakeup

The core has no wakeup op, but it has `Io\Poll\NotifyHandle`: an eventfd, or a pipe or a socket pair
where there is none (`Ip:624-737`), with a public constructor that takes no argument
(`Ip:1371-1393`), `php_poll_notify()` that is thread-safe and async-signal-safe
(`ext/standard/io_poll.h:45-46`), and `php_poll_handle_get_fd()` (`main/poll/poll_handle.c:100`).
Its class entry is static (`Ip:52`), so the reactor finds the class by name and constructs one
handle per thread on the first trigger. A reactor-owned IO event holds a POLL op on the handle's
descriptor; its completion calls the handle's `clear()`, submits the op again (POLL ops are one-shot
on the Poll queue) and notifies every trigger whose pending flag is set.

A trigger is TrueAsync's trigger event (`libuv_reactor.c:4471-4584`): an `async_event_t` with an
atomic pending flag, owned by its thread. `trigger()` from any thread sets the flag and calls
`php_poll_notify()`; its owner keeps it alive while other threads may call it, as TrueAsync's
channels do under their mutex. It is edge-triggered: one wake per set of the flag, cleared by the
owner before the notify, so a `trigger()` during the notify wakes the next waiter. The TRIGGER kind
puts the trigger on the reactor's `triggers` list when its first record links and takes it off when the last
leaves, so a coroutine that waits for another thread is no deadlock and a trigger nobody waits for
keeps nothing alive. S4.5 files the RFC change in `RFC-CHANGES.md`: a C constructor for an owned
`NotifyHandle` (or a thread-safe `wake` entry in `php_io_queue_ops`), after which the lookup by name
goes.

### 3.7 Request end and bailout

At RSHUTDOWN, after the scheduler's last drain: every event on the `waits` list and the
reactor's own ops (the wakeup POLL, the D16 Timer) are orphaned, the `NotifyHandle` released, and the
queue destroyed. S4.2 moves U6's unlink (`scheduler.c:2030`) before `zend_fiber_destroy_context`
(`:2027`), so no record is still linked when its coroutine's context goes. A bailout needs nothing
more from the reactor: `scheduler_bailout_all` unwinds every parked coroutine through U4, which
aborts and unlinks its wait, main last (S3.md 4.5). After `ZEND_ASYNC_DEACTIVATE` nothing submits:
`delay()` returns without a current coroutine, and S6's `run()` answers Unsupported (M13).

### 3.8 Windows

With ior (the CI `windows` job builds it, `.github/workflows/ci.yml:249-252`) the queue is the Ring on
IOCP, which has Timer and POLL ops (`ior_iocp.c:144, 2232-2358`; POLL through a WSAPoll thread, so on
sockets only); without ior it is the Poll queue on WSAPoll with its timer heap. Timers and the
`NotifyHandle` (a socket pair there) work on both. Pipes and the console do not reach `php_io` on
Windows: the plain wrapper reads them with `PeekNamedPipe` and `read()`
(`main/streams/plain_wrapper.c:620-667`), so the pipe groups P3.2 makes mandatory need a core change,
which S6.2 decides and files; WaitPid has a Ring form there (`ior_prep_waitpid`, `Hk:1789-1847`) and
none on the Poll queue. No signals, so no `EINTR` path.

## 4. Departures from TrueAsync

| What | TrueAsync | S4 | Why |
|---|---|---|---|
| Per-type behaviour | 8 method pointers in each event (`F:902-930`) | a const kind table on the record (D28, D30) | the wake function is per subscriber already; 64 B fewer per event |
| Records past two | one `emalloc` per record (`Fc:1136-1147`) | one block per wait, the stage's own | N − 1 allocations fewer; S5's context lives in it |
| `delay(<0)` | about 49 days | `ValueError` | an unsigned cast, no test relies on it |
| Idle wait | also in the suspending fiber's tick | only in the scheduler coroutine's loop | one blocking site; the extra switch is on a blocking path |
| Deadlock input | `ZEND_ASYNC_ACTIVE_EVENT_COUNT` | the reactor's `waits` and `triggers` lists | the lists are needed for fork and RSHUTDOWN anyway; no counter on the notify path |
| `EINTR` | never returned (libuv retries) | an internal coroutine runs the VM interrupt | the queue returns it, and with nothing runnable nobody else would run it (M5) |
| Fork | `fork()` refused with other coroutines alive | the queue rebuilt on `EPERM`; the parent's waits end in the child's deadlock report | the RFC core has no fork hook; a wait does not run twice |
| Cross-thread wakeup | one `uv_async_t` per trigger | the core's `NotifyHandle` per thread, a flag per trigger | the core has no wakeup op; libuv scans its async handles the same way |

Each departure gets a `DECISIONS.md` line in the commit that writes its code (P1.4: how it is better,
how its correctness is checked).
